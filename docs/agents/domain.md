# Domain Docs

BaboJUBot의 도메인 문서를 읽고, 도메인 언어를 코드·이슈·문서에 적용하는 규칙입니다.

## 탐색 전에 읽을 것

- [`GLOSSARY.md`](../../GLOSSARY.md): 공식 도메인 용어집입니다. 이 repository는 **단일 컨텍스트**이며 용어집은 이 파일 하나입니다.
- `docs/adr/`: 작업 영역에 닿는 ADR을 읽습니다. 아직 ADR이 없으면 그대로 진행합니다.

컨텍스트별 `GLOSSARY.md`와 이를 잇는 `GLOSSARY-MAP.md`는 [Bounded Context](#bounded-context)의 분리 조건이 확인되고 사용자가 결정한 뒤에 만듭니다.

## 지식이 기록되는 곳

기록 위치와 문서별 경계는 [문서 지도](../README.md)를 따릅니다.
이 문서는 도메인 언어의 적용·충돌 처리와 ADR 작성 조건을 담당합니다.

## Ubiquitous Language

이슈 제목, 코드 이름, 테스트 이름, 계약 필드, 문서와 보고에서 도메인 개념을 부를 때 `GLOSSARY.md`의 용어를 씁니다. `_Avoid_`에 적힌 표현은 쓰지 않습니다. 코드·계약 식별자에는 용어 옆 괄호의 영문 표기(`Organization`, `Worker`, `Task` 등)를 씁니다.

같은 단어를 다른 뜻으로 재사용하지 않습니다. 예를 들어 **연구 목표**는 조직 단위의 상위 목표이고 그 안의 개별 업무는 **작업**이며, **결과 제출**과 **최종 완료**는 서로 다른 단계입니다.

필요한 개념이 `GLOSSARY.md`에 없으면 두 경우 중 하나입니다. 프로젝트가 쓰지 않는 말을 새로 만들고 있다면 기존 용어로 다시 표현합니다. 실제로 빠진 개념이라면 아래처럼 보고합니다.

## 모호성과 충돌 보고

다음을 발견하면 임의로 한쪽을 고르지 않고, 근거 위치와 함께 사용자에게 명시적으로 보고합니다.

- 요청·이슈·코드가 `GLOSSARY.md` 정의와 다른 뜻으로 용어를 쓰는 경우
- 한 용어가 두 개념을 가리키거나, 두 용어가 한 개념을 가리키는 경우
- 구현에 필요한 개념이 `GLOSSARY.md`에 없는 경우

> _용어 충돌: 이 요청의 "작업"은 한 번의 실행 시도를 가리키는 것으로 보이지만, `GLOSSARY.md`의 **작업 (Task)**은 조직 안의 개별 업무입니다. 실행 시도를 별도 용어로 정의할까요?_

`GLOSSARY.md` 정의의 추가·변경은 사용자가 해석을 확정한 뒤 바로 반영합니다. 형식은 기존 항목처럼 굵은 용어, 한두 문장의 정의, 필요하면 `_Avoid_`입니다. 용어 정리와 ADR 작성에 `domain-modeling` skill을 쓸 수 있다면 사용합니다.

## 도메인 용어와 설계 결정 구분

`GLOSSARY.md`는 개념이 **무엇인지**만 정의합니다. 저장 방식, 상태 전이 형식, framework, 데이터 형식, 메모리 제품 같은 구현 선택은 넣지 않습니다.

| 도메인 용어 (`GLOSSARY.md`) | 설계 결정 (이슈·ADR) |
| --- | --- |
| **조직 기억**은 다른 조직에 자동으로 공유되지 않는다 | 기억의 저장·검색 기법과 엔진 |
| **결과 제출**과 **최종 완료**는 다른 단계다 | 상태 전이와 식별자 형식 |
| **연구 지도**는 문제·가설·검증·실험·결과의 관계를 기록한다 | 엄격한 트리 또는 graph 표현, 템플릿 스키마 |

설계 결정을 용어 정의에 섞은 문장을 발견하면 결정 부분을 해당 이슈나 ADR로 옮기자고 보고합니다.

## Bounded Context

현재 BaboJUBot은 하나의 언어를 공유하는 단일 컨텍스트입니다. 다음은 같은 용어집을 쓰는 **책임 경계**이며 별도 Bounded Context가 아닙니다.

- `orchestration` / `research-harness`: 기능 책임 분류입니다 ([`docs/features.md`](../features.md)).
- 코드 module: 책임 단위입니다.

**연구 조직**의 격리는 데이터·실행·기억을 조직별로 나누는 제품 불변 조건입니다. 모든 조직이 같은 용어를 쓰므로 언어 경계인 Bounded Context와 다릅니다.

같은 용어가 영역마다 다른 정의를 실제로 필요로 하는 사례를 발견하면, 사례와 근거를 보고하고 컨텍스트 분리 여부를 사용자 판단으로 남깁니다. 분리가 결정되기 전에는 `GLOSSARY.md` 안에서 서로 다른 용어로 나누는 방법을 먼저 제안합니다.

## ADR

ADR은 아래 세 조건이 모두 참이고 사용자가 결정을 확정했을 때만 만듭니다.

1. **되돌리기 어렵다**: 나중에 바꾸는 비용이 의미 있게 크다.
2. **맥락 없이는 의외다**: 이후 읽는 사람이 "왜 이렇게 했지?"라고 물을 만하다.
3. **실제 trade-off의 결과다**: 진지한 대안이 있었고 이유를 갖고 골랐다.

한 이슈 안에서 끝나는 결정은 그 이슈에 기록합니다. ADR은 `docs/adr/NNNN-slug.md`로 번호를 이어 붙이고, 맥락·결정·이유를 한두 문단으로 적습니다. 첫 ADR이 필요할 때 디렉터리를 만듭니다.

변경이 기존 ADR이나 확정 문서와 충돌하면 조용히 덮어쓰지 않고 충돌을 드러냅니다.

> _ADR-NNNN(<결정 제목>)과 충돌합니다. 그래도 재검토할 이유는 …_
