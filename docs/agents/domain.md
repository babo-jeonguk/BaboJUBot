# 도메인 문서 규칙

작업에 해당하는 [GLOSSARY](../../GLOSSARY.md)와 [ADR](../adr/)을 읽습니다. 기록 위치는 [문서 지도](../README.md)를 따릅니다.

## 용어 적용

- 이슈·코드·테스트·계약·문서·보고에 GLOSSARY 용어를 쓰고 `_Avoid_` 표현은 피합니다. 식별자는 괄호의 영문 표기(`Organization`, `Task` 등)를 따릅니다.
- 한 단어는 한 개념을 가리킵니다. 불필요한 새 용어는 기존 용어로 표현하고, 실제로 빠진 개념은 아래 절차로 확정합니다.
- GLOSSARY는 **무엇인가**를 정의합니다. 저장·상태 전이·framework·데이터 형식·제품 선택은 이슈/ADR에 둡니다. 정의에 설계 결정이 섞였으면 이동을 제안합니다. 용어 정리·ADR 작성에는 사용 가능한 `domain-modeling` skill을 씁니다.

## 모호성과 충돌 보고

요청·이슈·코드와 용어 정의가 다르거나, 한 단어가 두 개념/두 단어가 한 개념을 뜻하거나, 필요한 개념이 없으면 **근거 위치와 해석 차이를 사용자에게 보고**합니다. 임의로 뜻을 고르지 않습니다.
사용자가 해석을 확정하면 GLOSSARY를 즉시 갱신합니다. 형식은 굵은 용어·1~2문장 정의·필요한 `_Avoid_`입니다. 기존 ADR·확정 문서와의 충돌도 근거와 재검토 이유를 드러냅니다.

## 컨텍스트 경계

현재는 **단일 컨텍스트·루트 GLOSSARY 하나**입니다. module 및 `orchestration`/`research-harness`는 책임 경계이고, 연구 조직 격리는 데이터·실행·기억 경계입니다.
영역마다 같은 단어의 다른 정의가 실제로 필요하면 사례를 보고하고, 먼저 한 용어집 안에서 용어를 구분하는 방안을 제안합니다. 사용자 결정 후에만 컨텍스트별 GLOSSARY와 `GLOSSARY-MAP.md`를 만듭니다.

## ADR 작성 조건

**사용자 확정**과 다음 세 조건을 모두 충족할 때만 작성합니다: **되돌리기 어렵다 / 맥락 없이는 의외다 / 실제 대안 사이 trade-off가 있다**.
이슈 안에서 끝나는 결정은 이슈에 둡니다. ADR은 `docs/adr/NNNN-slug.md`의 연속 번호로 맥락·결정·대안과 선택 이유·결과를 짧게 기록합니다. 첫 ADR이 필요할 때 디렉터리를 만듭니다.
