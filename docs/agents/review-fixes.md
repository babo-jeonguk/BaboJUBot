# 리뷰 반영

리뷰 수정·반영 요청에 적용합니다. 리뷰만 요청받으면 결과만 전달합니다.

## 1. 지적 검증

- PR·base/head·리뷰 SHA와 현재 코드를 대조합니다. finding별 고정 ID·Standards/Spec 축·위치·실패 조건·영향·명세/표준 근거를 확인합니다.
- 아래 판정별 근거·다음 처리를 기록합니다. 사용자 결정에 의존하는 변경은 대기하며, 이월만으로 blocker를 해소하지 않습니다.
- 성립하는 지적은 영향으로 **이번 회차에 고칠지** 먼저 정합니다. 리뷰어의 심각도 표시나 제안한 해결책은 근거일 뿐 결정이 아닙니다. 이슈 완료 조건·확정 결정 위반, 이 PR이 만들거나 키운 문제, 이 PR이 바꾼 코드의 보안·데이터 손실·되돌릴 수 없는 영향은 이번에 고칩니다. 그 밖은 근거(예: base에서도 같음)와 함께 후속 처리로 두고 지금 고칠지 사용자에게 묻습니다.
- 설계 권고는 채택 이유를 판단하고 자동 수정 blocker로 삼지 않습니다. 코드 모양으로 판정할 수 있는 지적은 자동 검사 후보로 회차 기록에 남깁니다. 이슈·PR 게시는 [이슈 운영 규칙](issue-tracker.md)과 [게시문 검사](issue-tracker.md#게시문에-쓰는-경로)를 따릅니다.

| 판정 | 근거 |
| --- | --- |
| 수정 | 재현·수정 SHA·회귀 검사 |
| 반증 | 코드·계약·재현상 성립하지 않는 이유 |
| 의도된 동작 | 요구·확정 결정 링크 |
| 사용자 결정 필요 | 상충 근거·선택지·영향 |
| 후속 처리 | 회귀/기존 결함 구분·이월 이유·이슈·남은 위험 |

**완료:** 모든 finding의 판정·근거·다음 처리와 미해결 blocker가 드러납니다.

## 2. 원인 수정과 실패 유형 검증

- 현상만 지우는 수정이나 리뷰가 제안한 방법을 그대로 따르지 않습니다. 증상에서 "왜"를 거슬러 그 문제를 허용한 설계(빠지거나 중복된 책임, 흩어진 규칙, 잘못된 순서 등)를 찾아 없애고, 그 원인 때문에 붙였던 guard·예외 처리도 지웁니다.
- 가능한 경우 수정 전 실패를 재현하고, 같은 원인의 다른 위치·인접 실패 경로까지 확인해 원인 경계에서 고칩니다. 범위는 해당 원인·계약에 한정합니다.
- 회귀 테스트를 먼저 커밋한 뒤 제품 코드 수정을 [코드 worker](worker.md)에 맡깁니다. parent와 worker의 역할 나눔은 [worker 역할](worker.md#1-역할)을 따릅니다.
- 회귀 테스트로 수정 전 실패·수정 후 통과를 확인합니다. 제품에 없는 재시도·깨우기를 helper로 추가해 결함을 가리지 않습니다. 재현이 어려우면 한계를 남깁니다.
- 검사는 [검증 기준](verification.md)의 시점·범위대로 하고, 재검토 수렴 후 문서·검증 근거를 갱신합니다. 기존 PR은 같은 브랜치에 커밋·push하고 CI를 확인합니다.

**완료:** 원인·같은 실패 유형의 처리 범위와 현재 코드의 검증 근거가 연결됩니다.

## 3. 재검토와 수렴

- 이전 검토 이후 diff와 기존 finding 상태를 먼저 확인합니다. 권한·상태 전이·공유 계약 변경은 호출자까지 추적하고, 전체 재검토가 필요하면 이유를 남깁니다. 같은 지적을 중복 등록하지 않습니다.
- **지적 접수 → 검증·수정 → 재검토 결과 확인**이 1회입니다. 3회에도 수렴하지 않으면 다음 수정 전에 근거·반복 원인·범위·접근을 재점검해 사용자에게 보고합니다. 미해결 blocker는 유지합니다.
- 수정으로 범위·검증·위험이 바뀌면 PR 본문도 `/pr`로 [PR 양식](../../.github/PULL_REQUEST_TEMPLATE.md)대로 다시 씁니다.
- 수정이나 finding 판정이 바뀐 회차는 회차·검토/수정 SHA·finding 상태와 근거·자동 검사 후보 표시를 PR 댓글로 남기고 세션이 바뀌어도 이어갑니다. 바뀐 것 없이 통과한 회차와 CI 결과는 따로 댓글을 달지 않고 다음 회차 기록이나 병합 후 댓글에 합칩니다. PR 생성 전에는 로컬 기록을 쓰고, 재검토 수렴 후 [완료 검사](verification.md#완료-검사)로 이어갑니다. PR 생성 시 로컬 기록을 옮깁니다.
- 기존 PR의 외부 리뷰 수정은 아래 자료를 전달하면 인계 완료입니다. 병합은 별도 요청 후 [병합 절차](pr-merge.md)를 따릅니다.

**완료:** 재검토 범위·회차·finding 상태·다음 판단이 추적 가능합니다. 외부 리뷰 대기 시 수정·인계 완료로 보고합니다.

## 외부 리뷰 요청 형식

아래를 실제 값으로 채워 **백틱 5개의 단일 블록**으로 전달합니다. 링크는 고정 SHA·결정 댓글을 쓰고 자격 증명·실제 연구 데이터는 제외합니다.

`````text
mattpocock-skills v1.3.2의 code-review 방식으로 Standards와 Spec을 분리해 검토해 주세요.
https://github.com/mattpocock/skills/blob/v1.3.2/skills/engineering/code-review/SKILL.md
Repository / PR: <주소>
Spec·확정 결정 / 저장소 표준: <링크; 이슈 없는 작업은 승인된 요구를 기재> / CODING_STANDARDS.md 「anti-pattern」 절(<고정 SHA 링크>#anti-pattern)
Base / Head SHA: <각 SHA>
전체 diff: git diff <base>...<head>
커밋: git log <base>..<head> --oneline
회차 / 이전 검토 SHA·재검토 diff: <N / 첫 리뷰는 이전 값 없음>
수정 전후 동작 / 위험: <내용>
검증: <명령·SHA 또는 CI run·결과> / 미검증 범위: <내용>
기존 finding: <ID·축·판정·수정 SHA/검사 또는 결정/반증 근거> / blocker: <내용 또는 없음>
지적에는 위치·실패 조건·영향·명세/표준 근거를 포함하고 확정 위반과 설계 권고를 구분해 주세요.
코드 모양만으로 판정할 수 있는 지적은 "자동 검사 후보"로 표시해 주세요.
같은 원인에서 나오는 반례는 이번 회차에 모두 찾아 한꺼번에 적어 주세요. 하나씩 나눠 다음 회차로 넘기지 마세요.
권장 수정은 같은 종류를 한 번에 닫는 단순한 설계(아는 모양만 통과, 나머지는 판정할 수 없음)로 제시해 주세요. 외부 도구의 문법을 더 흉내 내거나 예외를 하나 더 막는 덧붙이기는 권하지 마세요.
리뷰 대응으로 늘어난 코드에 새 anti-pattern(외부 해석기 흉내, 전역·객체 바꿔치기, 공용 도움 복사본, 라이브러리 내부 동작에 기댄 판정)이나 범위 확장이 있는지 함께 판정해 주세요.
저장소에 실제 호출·경로가 없는 이론상의 반례는 확정 위반과 따로 "이론상 경로"로 분류하고, 병합을 막는지 밝혀 주세요.
재리뷰는 변경 diff·기존 지적을 먼저 확인하고, 권한·상태·공유 계약의 영향 경로와 검토 범위를 밝혀 주세요.
`````
