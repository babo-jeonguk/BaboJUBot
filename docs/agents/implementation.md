# 구현

`implement`·구현 요청은 아래 작업 브랜치에서 구현·검증·리뷰·커밋·push·PR 생성까지 진행합니다.
사용자가 지정한 범위·전달 방식이 우선이며, 병합은 별도 요청 후 [병합 절차](pr-merge.md)를 따릅니다.

## 1. 착수와 원문 확인

- base SHA·현재 branch/worktree·미커밋 변경을 확인합니다. 새 작업은 최신 원격 base에서 작업 브랜치를 만들고, 이어가는 작업은 기존 브랜치를 씁니다. 기존 변경을 보존하고 겹치면 [Paseo worktree workspace](dev-orchestration.md#1-세션-구성)를 씁니다.
- 이슈 본문·댓글·parent·blocker와 [확정 기능](../features.md)을 확인합니다. 이슈 없는 작업은 사용자가 승인한 요구를 기준으로 합니다.
- `reference-first`의 receipt·조사 문서에서 **채택할 근거의 원문 링크를 직접 열어** 코드·공식 문서를 읽습니다. UI 근거는 실제 화면을 조작하고 캡처도 직접 확인합니다. 요약만으로 채택하지 않습니다.
  확인한 URL·SHA/파일/절과 적용·배제 이유를 구현 기록에 남기고, 열지 못한 자료는 미확인으로 보고합니다. 조사 권고와 확정 결정을 구분하고 부족한 근거만 보강합니다.

**완료:** 기준 SHA·작업 위치·요구·열린 결정이 식별됐고, 구현자가 채택 근거를 원문에서 확인해 적용·배제 이유를 기록했습니다.

## 2. 구현과 검증

- [코드 지도](code-map.md)의 호출·계약을 따라 원인을 소유한 경계에서 구현하고, 영향받는 문서를 [문서 지도](../README.md)에 맞춰 갱신합니다. 미해결 제품 결정은 사용자에게 묻고 독립 작업은 이어갑니다.
- 구현은 `/tdd` 원칙으로 나눈 슬라이스마다 아래 순서로 한 번에 하나씩 진행합니다. 맡기는 방법·인수는 [코드 worker](worker.md), Paseo 배치는 [개발 오케스트레이션](dev-orchestration.md)을 봅니다. 모든 모델이 한도이거나 worker가 수렴하지 않으면 parent가 직접 고치고 이유를 남깁니다.
  1. **RED(parent):** 시험을 쓰고 그 파일의 lint·타입 검사를 통과시킨 뒤, 의도한 이유로 실패하는 것을 확인하고 시험만 커밋합니다.
  2. **GREEN(worker):** 그 커밋을 base로 brief를 주고, worker가 제품 코드를 고쳐 시험·정적 분석을 통과시킵니다.
  3. **인수(parent):** [변경을 검토](worker.md#6-검토인수)해 받아들이기로 판단하면 제품 코드를 커밋합니다.
- 검사는 [검증 기준](verification.md)의 시점·범위대로 직접 실행합니다.
- 로컬 리뷰 시작 시 [리뷰 반영](review-fixes.md) 전체를 읽고 적용합니다.
- 커밋 메시지는 [커밋 규칙](commit-messages.md)을 따르며, 커밋 후 3단계로 이어갑니다.

**완료:** 요구별 검증 근거·미검증 범위가 있고 구현·문서가 일치하며, 작업 범위만 커밋됐습니다.

## 3. Push·PR·외부 리뷰 인계

- 작업 브랜치를 push하고 base를 확인해 PR을 생성·갱신합니다. 본문은 `/pr`을 호출해 [PR 양식](../../.github/PULL_REQUEST_TEMPLATE.md)대로 쓰고, 완료한 이슈만 `Closes #N`으로 연결합니다. PR 생성·본문 수정은 [게시문 검사](issue-tracker.md#게시문에-쓰는-경로)를 거칩니다.
- 필수 CI를 확인·해결하고 본문을 현재 head에 맞춥니다.
- [외부 리뷰 요청 형식](review-fixes.md#외부-리뷰-요청-형식)을 사용자에게 전달합니다.

**완료:** PR·최종 head·CI 결과·리뷰 처리·외부 요청 자료가 전달됐습니다. 미완료 항목·blocker는 구분해 보고합니다.
