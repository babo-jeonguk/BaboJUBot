# 구현

`implement`·구현 요청은 아래 작업 브랜치에서 구현·검증·리뷰·커밋·push·PR 생성까지 진행합니다.
사용자가 지정한 범위·전달 방식이 우선이며, 병합은 별도 요청 후 [병합 절차](pr-merge.md)를 따릅니다.

## 1. 착수와 원문 확인

- base SHA·현재 branch/worktree·미커밋 변경을 확인합니다. 새 작업은 최신 원격 base에서 작업 브랜치를 만들고, 이어가는 작업은 기존 브랜치를 씁니다. 기존 변경을 보존하고 겹치면 별도 worktree를 씁니다.
- 이슈 본문·댓글·parent·blocker와 [확정 기능](../features.md)을 확인합니다. 이슈 없는 작업은 사용자가 승인한 요구를 기준으로 합니다.
- `reference-first`의 receipt·조사 문서에서 **채택할 근거의 원문 링크를 직접 열어** 코드·공식 문서를 읽습니다. UI 근거는 실제 화면을 조작하고 캡처도 직접 확인합니다. 요약만으로 채택하지 않습니다.
  확인한 URL·SHA/파일/절과 적용·배제 이유를 구현 기록에 남기고, 열지 못한 자료는 미확인으로 보고합니다. 조사 권고와 확정 결정을 구분하고 부족한 근거만 보강합니다.

**완료:** 기준 SHA·작업 위치·요구·채택 근거·열린 결정이 식별됐습니다.

## 2. 구현과 검증

- 코드 지도의 호출·계약을 따라 원인을 소유한 경계에서 구현하고, 영향받는 문서를 [문서 지도](../README.md)에 맞춰 갱신합니다. 미해결 제품 결정은 사용자에게 묻고 독립 작업은 이어갑니다.
- 개발 중 관련 테스트·타입 검사를 실행합니다. 완료 검사는 [공통 검증 기준](../../README.md#검증-기준)을 따르며, 커밋 대상만 있는 환경에서도 확인합니다.

**완료:** 요구별 검증 근거·미검증 범위가 있고 구현·문서가 일치합니다.

## 3. 로컬 리뷰와 커밋

- 고정 base 대비 미커밋 파일까지 `code-review`의 Standards·Spec으로 검토합니다. 지적이 있으면 [리뷰 반영](review-fixes.md)의 검증·수정·재검토를 거쳐 이 단계로 돌아옵니다.
- blocker 해소 후 이번 파일·hunk만 [커밋 규칙](commit-messages.md)에 따라 커밋합니다. hook의 변경·실패 원인을 확인하고 필요한 검사를 다시 실행합니다.

**완료:** 작업 범위만 커밋됐고 리뷰 대상·후속 변경의 검증 근거가 연결됩니다.

## 4. Push·PR·외부 리뷰 인계

- 작업 브랜치를 push하고 base를 확인해 PR을 생성·갱신합니다. 본문에 최종 범위·수정 전후 동작·검증 SHA/결과·미검증 범위·위험을 적고, 완료한 이슈만 `Closes #N`으로 연결합니다.
- 필수 CI를 확인·해결하고 본문을 현재 head에 맞춥니다.
- [외부 리뷰 요청 형식](review-fixes.md#외부-리뷰-요청-형식)을 사용자에게 전달합니다.

**완료:** PR·최종 head·CI 결과·리뷰 처리·외부 요청 자료가 전달됐습니다. 미완료 항목·blocker는 구분해 보고합니다.
