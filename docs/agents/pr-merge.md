# PR 병합

사용자의 PR 병합 요청은 대상 확인부터 관련 기록 동기화, 검증, 병합, 기존 관련 이슈 갱신,
로컬 base 동기화와 브랜치 정리까지 포함합니다. 아래 순서를 마쳐야 완료입니다.
이 문서는 개발 저장소의 병합 절차이며, 제품의 연구 승인·최종 완료 권한은 [AGENTS.md](../../AGENTS.md)의 제품 불변 조건을 따릅니다.

## 1. 대상과 현재 상태 확인

- PR 번호가 없으면 현재 브랜치의 PR을 찾습니다. 대상이 하나로 정해지지 않을 때만 사용자에게 묻습니다.
- `gh pr view`, `gh pr diff`, git으로 repository, base/head 브랜치와 SHA, 변경 파일·커밋,
  연결 이슈, 본문·댓글·리뷰, CI와 병합 가능 상태를 확인합니다.
- 시작 branch/worktree와 기존 미커밋 변경을 기록하고 보존합니다. 무관한 변경을 commit이나 정리에 섞지 않습니다.
- head를 base로 쓰는 열린 stacked PR과 다른 worktree에서 사용 중인 브랜치를 확인합니다.

**완료 조건:** 병합 대상·시작 상태·미해결 blocker와 보존할 작업을 설명할 수 있습니다.

## 2. 구현 결과와 기록 동기화

연결 이슈의 조사·결정·완료 조건과 최종 diff를 대조해 다음을 판단합니다.

1. 요구한 문제를 해결했는가? 사용자에게 보이는 수정 전후 동작은 무엇인가?
2. 원인을 소유한 위치에서 고쳤는가? 제품 불변 조건을 해당 코드 경계가 강제하는가?
3. 추가 변경이 섞였는가? 계약·저장 형식·의존성·배포 순서에 어떤 영향이 있는가?
4. 현재 검증과 알려진 한계로 병합할 수 있는가?

변경한 개념·경로·상태를 기준으로 README, GLOSSARY, 관련 `docs/`, 연결 이슈와 parent/epic·후속·의존 이슈를 검색합니다.
각 관련 기록을 **갱신**, **유지**(역사적 기록 또는 권위 문서로의 링크), **후속 처리**로 판정합니다.
기록 위치와 중복·누락 점검은 [문서 지도](../README.md)의 작성·갱신 기준을 따릅니다.
코드 진입점·책임 위치·검증 위치가 달라졌다면 [코드 지도](code-map.md)도 고칩니다.

- 저장소 문서는 PR head에서 수정하고 diff를 확인합니다. 새 코드 수정이 필요하면 해당 변경의 검토·검증을 거칩니다.
- PR 본문은 최종 범위·검증·한계를 설명하도록 다시 씁니다. 교정 이력은 댓글에 남기고 본문의 취소선·낡은 설명은 정리합니다.
- 기존 관련 이슈에 합의된 결정과 구현 결과를 반영합니다. 구현이 확정 계약과 충돌하면 그 차이를 해소한 뒤 진행합니다.
  병합·완료를 전제로 하는 상태 변경은 병합 성공 뒤에 합니다.
- 범위 밖 결함은 이번 변경의 회귀, 기존 결함, 환경 문제를 근거로 구분합니다. 새 제품 결정은 사용자에게 확인하고,
  새 이슈 게시는 [이슈 운영 규칙](issue-tracker.md)을 따릅니다.

**완료 조건:** 구현과 기록이 일치하고, 주요 유지·후속 처리 판단과 병합할 이유를 설명할 수 있습니다.

## 3. 최종 head 검증

검사 명령과 환경은 [README의 개발 시작](../../README.md#개발-시작)을 따릅니다.

- 모든 변경에서 `git diff --check`와 `pnpm check`를 확인합니다. 문서만 바뀌었다면 이것을 기본 검증으로 삼습니다.
- 제품 코드가 바뀌면 `pnpm test`, `pnpm typecheck`, `pnpm lint`와 변경 계약에 필요한 검사를 확인합니다.
  빌드·실행 환경 변경은 `pnpm build`, 브라우저 동작 변경은 관련 E2E와 실제 화면·조작 결과를 포함합니다.
- 조직 상태·승인·조직 분리 계약을 건드리면 해당 시나리오의 검증 근거를 확인합니다. 실행하지 않은 환경과 시나리오는 명시합니다.
- 검사마다 검증한 SHA, 명령 또는 CI run, 결과를 PR 본문에 남깁니다. 이전 SHA의 근거를 쓸 때는 이후 diff와 적용 가능한 이유를 밝힙니다.
- [CI job](../../.github/workflows/scaffold.yml)이 실제 실행하는 검사를 확인하고, 빠진 제품 검증 근거를 별도로 확인합니다.
- 실패한 필수 검사, 미해결 review blocker, 충돌을 먼저 해소합니다. 단순한 재실행으로 결함을 덮지 않고 실패 원인과 재검증 결과를 기록합니다.

검증 뒤 수정·동기화 commit이 생기면 변경 영향을 판단해 필요한 검사를 다시 확인합니다.
base가 움직였다는 이유만으로 rebase를 반복하지 않습니다. 충돌·계약 변화·필수 검사 정책상 통합 검증이 필요할 때 동기화하고,
그 최종 head에 맞는 근거를 확보합니다.

**완료 조건:** 최종 head와 검증 근거가 연결되고, 필수 CI와 리뷰에 병합 blocker가 없습니다.

## 4. 병합 실행

1. 최종 head SHA, base, 병합 후 수행할 이슈 actions와 삭제·보존할 브랜치를 정합니다.
   stacked PR이 있으면 base 변경과 예상 diff를 먼저 정합니다.
2. 실행 직전에 PR identity·head·base와 blocker를 다시 확인합니다. 달라졌다면 관련 판단을 갱신합니다.
3. **merge commit**으로 개별 커밋을 보존합니다. `gh pr merge <번호> --merge --match-head-commit <최종-head-SHA>`를 사용합니다.
   squash·rebase merge, admin bypass, force push는 사용하지 않습니다. 브랜치는 아래 정리 단계에서 삭제합니다.
4. PR이 `MERGED`이고 merge commit이 생겼는지 확인한 뒤에만 병합 후 처리를 시작합니다.

**완료 조건:** 확인한 head의 병합과 merge SHA가 확인됐습니다.

## 5. 기록 마감과 로컬 정리

- 연결 이슈가 자동으로 닫혔는지 확인합니다. 완료 조건을 충족한 이슈에 결과와 PR 링크를 남기고 필요한 상태를 갱신합니다.
  parent/epic은 이번 완료와 남은 작업을 반영하고, 전체 완료 조건을 충족했을 때만 닫습니다.
- 승인된 stacked PR의 base를 조정하고 예상한 변경만 남는지 확인합니다. 열린 PR이 쓰는 브랜치는 유지합니다.
- 시작 worktree의 기존 변경을 보존할 수 있는 상태에서 로컬 base(보통 `main`)를 remote에 fast-forward로 동기화합니다.
  로컬 고유 커밋이나 미커밋 변경 때문에 불가능하면 강제로 덮어쓰지 않고 이유를 보고합니다.
- 삭제 대상 브랜치가 base에 완전히 포함되고 열린 PR의 base/head나 다른 worktree에서 쓰이지 않는지 확인합니다.
  확인된 로컬 브랜치는 `git branch -d`, 이 저장소의 원격 브랜치는 `git push origin --delete`로 정리합니다. 외부 기여자의 fork 브랜치는 유지합니다.
- `git fetch --prune` 뒤 로컬 base와 remote SHA, worktree, PR·주요 이슈 상태, 삭제·보존 브랜치를 확인합니다.
- 병합 전 검증한 코드의 전체 테스트는 기본적으로 반복하지 않습니다. 새 통합 변경·실패 조사 등 재검사 이유가 있으면 명령과 결과를 기록합니다.
  base push CI는 확인 시점의 상태를 보고하며, 종료 대기는 사용자의 요청이나 구체적 조사 이유가 있을 때 수행합니다.

병합 뒤 일부 처리가 실패하면 병합 성공 사실과 미완료 항목을 구분합니다. 원인을 확인한 뒤 안전하게 이어갈 수 있는 처리만 수행하고,
추가 판단이 필요한 항목은 정확한 blocker와 현재 상태를 남깁니다.

**완료 조건:** 관련 기록·로컬 base·worktree·브랜치 정리 결과가 확인됐습니다. 미완료 항목이 있으면 부분 완료로 보고합니다.

## 완료 보고

- PR 링크, merge 방식과 SHA, 사용자에게 달라진 동작과 병합 판단 근거.
- 갱신한 문서·이슈와, 조사했지만 유지한 주요 기록의 이유.
- 검증한 head와 검사 결과, 미실행 범위, 병합 후 재검사 여부·이유, 확인 시점의 base CI 상태.
- 로컬 base 동기화·worktree·브랜치 삭제·보존 결과와 남은 blocker·후속 작업.

최종 PR 본문에는 범위·검증·한계를 모으고, 병합 후 PR 댓글에는 결과와 merge SHA를 간결하게 남깁니다.
이슈에는 해당 완료 조건과 후속 상태를 기록하고, 상세 근거는 PR로 연결합니다.
