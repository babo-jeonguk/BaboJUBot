# PR 병합

병합 요청은 아래 5단계와 보고까지 포함합니다. 구현·PR 생성은 [구현](implementation.md), finding 처리는 [리뷰 반영](review-fixes.md)을 따릅니다.

## 1. 대상과 현재 상태 확인

- 번호가 없으면 현재 브랜치의 PR을 찾고, 대상이 모호할 때만 묻습니다. `gh pr view`·`gh pr diff`·git으로 저장소, base/head와 SHA, diff·커밋, 연결 이슈, 본문·댓글·리뷰, CI·병합 가능 상태를 확인합니다.
- 시작 branch/worktree·미커밋 변경을 보존하고, head를 base로 쓰는 열린 stacked PR과 다른 worktree의 사용 브랜치를 확인합니다.
- 외부 리뷰의 SHA·finding 처리 근거·회차를 PR 기록 및 현재 head와 대조합니다([재검토 기준](review-fixes.md#3-재검토와-수렴)).

**완료:** 대상·미해결 blocker·보존할 작업이 식별됐습니다.

## 2. 구현 결과와 기록 동기화

- 이슈의 조사·확정 결정·완료 조건과 최종 diff를 대조합니다. 사용자 동작의 전후 차이, 원인을 소유한 경계의 수정·불변 조건 강제, 추가 변경·계약·저장 형식·의존성·배포 영향을 판단합니다.
- 변경한 개념·경로·상태로 README·GLOSSARY·관련 docs·연결 이슈·parent/epic·후속·의존 이슈를 검색하고 **갱신 / 유지(역사 또는 기준 문서 링크) / 후속 처리**로 분류합니다. 기록 위치는 [문서 지도](../README.md), 경로 변경은 [코드 지도](code-map.md)에 반영합니다.
- 문서는 PR head에서 수정하고 diff를 확인합니다. 추가 코드 수정도 리뷰·검증합니다. PR 본문은 최종 범위·검증·한계로 갱신하고 교정 이력은 댓글에 둡니다.
- 기존 이슈에 합의·결과를 반영하고 확정 계약과의 충돌을 해소합니다. 병합·완료 상태 변경은 병합 성공 뒤에 합니다. 범위 밖 결함은 회귀·기존 결함·환경 문제로 구분하고, 새 제품 결정은 사용자에게, 새 이슈 게시는 [이슈 규칙](issue-tracker.md)에 따릅니다.

**완료:** 구현·기록이 일치하고, 유지·후속 처리 및 병합 판단의 근거가 있습니다.

## 3. 최종 head 검증

- [검증 기준](verification.md)의 검사·근거와 현재 코드의 모든 필수 CI 성공을 확인합니다. 미실행·취소·실패는 통과가 아닙니다. CI 밖의 검증도 확인합니다.
- 필수 검사 실패·review blocker·충돌의 원인을 해소하고 재검증합니다. 검증 뒤 commit이 추가되면 영향에 맞게 재검사합니다.
- base 이동만으로 rebase를 반복하지 않습니다. 충돌·계약 변화·검사 정책상 통합 검증이 필요할 때 동기화하고 최종 head의 근거를 확보합니다.

**완료:** 최종 head와 검증 근거가 연결되고 필수 CI·리뷰 blocker가 없습니다.

## 4. 병합 실행

1. 최종 head SHA·base, 병합 후 이슈 actions·브랜치 삭제/보존을 정합니다. stacked PR은 base 변경과 예상 diff도 정합니다.
2. 직전에 PR identity·head·base·blocker를 다시 확인하고 달라진 판단을 갱신합니다.
3. `gh pr merge <번호> --merge --match-head-commit <최종-head-SHA>`로 **merge commit**을 만듭니다. squash·rebase merge·admin bypass·force push는 사용하지 않으며 브랜치는 5단계에서 정리합니다.

**완료:** PR의 `MERGED` 상태와 merge SHA를 확인했습니다. 이후에만 후처리합니다.

## 5. 기록 마감과 로컬 정리

- 자동 close 여부를 확인하고 완료 조건을 충족한 이슈에 결과·PR 링크·상태를 반영합니다. parent/epic은 남은 작업도 기록하며 전체 조건 충족 때만 닫습니다.
- 승인된 stacked PR의 base를 조정하고 예상 diff를 확인합니다. 열린 PR의 base/head나 다른 worktree가 쓰는 브랜치는 보존합니다.
- 기존 변경을 보존하며 로컬 base를 remote로 fast-forward합니다. 고유 커밋·미커밋 변경이 막으면 덮어쓰지 않고 보고합니다. base에 완전히 포함된 미사용 브랜치만 로컬 `git branch -d`, 원격 `git push origin --delete`로 정리하며 외부 fork는 보존합니다.
- `git fetch --prune` 후 base의 로컬/원격 SHA, worktree, PR·주요 이슈, 브랜치 삭제/보존 결과를 확인합니다.
- 새 통합 변경·실패 조사 등 이유가 있을 때만 병합 후 검사를 반복합니다. base push CI는 확인 시점의 상태를 보고하고, 종료 대기는 사용자 요청이나 구체적 조사에 필요할 때 합니다.

**완료:** 기록·로컬 base·worktree·브랜치 결과가 확인됐습니다. 후처리 실패 시 병합 성공과 미완료를 구분하고 안전한 처리를 이어가며 blocker를 남깁니다.

## 완료 보고

PR 링크·merge 방식/SHA, 동작 변화·병합 근거, 문서/이슈 갱신·주요 유지 이유, 검증 head·결과·미실행 범위·병합 후 재검사 이유·base CI 상태, 로컬 정리·남은 작업을 보고합니다.
PR 본문은 범위·검증·한계, 병합 후 PR 댓글은 결과·merge SHA, 이슈는 완료 조건·후속 상태를 맡고 상세 근거는 PR로 연결합니다.
