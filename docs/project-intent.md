# BaboJUBot: 프로젝트 목표와 인터뷰 기록

최초 기록: 2026-10-12 (Asia/Seoul)

이 문서는 인터뷰 당시의 배경·요구·미결 사항과 이후 변경을 보존한 기록입니다.
본문의 구현 상태와 승인 정책은 당시 기준이며, 후속 인터뷰에서 바뀐 내용도 함께 남아 있습니다.
현재 기능 범위는 [features.md](features.md), 구조는 [architecture.md](architecture.md), 구현 요약은 [README](../README.md)를 따릅니다.

## 사용자가 명시한 목표

- PaperclipAI처럼 AI agent로 이루어진 organization을 만든다.
- 여러 agent의 협력으로 research를 자동화하는 orchestration bot을 만든다.
- 특정 연구 분야에 종속되지 않고 연구 전반에 폭넓게 사용할 수 있는 프로젝트를 만든다. 아래 모델 개발 사례는 활용 예시이며 제품 범위를 ML로 제한하지 않는다.
- 상위 연구 목표 하나마다 Paperclip의 organization에 해당하는 독립 연구 조직을 만든다. 각 조직에는 별도의 Research Lead와 작업자 팀을 둔다.
- PaperclipAI, Hermes Agent 등에서 필요한 기능을 선별해 참고하거나 재사용한다.
- xAI Grok Bot, Meta Muse, OpenAI dots 등 실제 상용 서비스와 유명 개인 프로젝트를 폭넓게 조사하고, 구현 원리를 분석해 필요한 기능을 구현한다.
- 진행 순서: (1) Paperclip 조사와 사용자 인터뷰로 요구 구체화 → (2) 기능별 실제 서비스 구현 조사/분석 → (3) 기능을 하나씩 구현.
- 기본 운영과 구현 기능의 범위를 합의했고 공개 코드 구조를 참고해 프로젝트 골격과 GitHub 백로그를 초기화했다. 제품 기능은 아직 구현하지 않았다. 최신 기능 기준선은 `features.md`를 참조한다.

## 아직 결정되지 않은 사항

- 연구별 완료 기준을 표현·수정하는 방식과 최종 검토에서 수정 요청을 처리하는 방식. 목표 설정 때 Lead와 기준을 정하고 사용자 최종 검토로 완료하는 원칙은 확정했다.
- 실행 단위: 요청별 작업, 정기 모니터링, 장기 연구 프로젝트.
- 재계획·재조사의 세부 권한. ‘큰 목표 변경’의 판단 기준과 agent 구성 변경 권한은 7차 인터뷰의 승인 정책으로 정리했다.
- 여러 연구 조직의 목록·상태를 보는 상세 화면, 조직별 목표 설정과 계획 수립 과정, 연구 중단·재개의 세부 의미. agent별/연구 전체 중단·재개 기능은 구현 대상으로 합의했다.
- 실행 환경과 연구별 도구를 연결하는 방식, 요청별 예산·시간 상한의 설정 방식. 지금 특정 GPU, 데이터, 모델, 연구 기간을 정할 필요는 없다.
- 메시지 앱 선택, 화면 배치·디자인, 조직 공통/agent별 기억의 저장·공유 방식. 웹 채팅과 메시지 앱의 순서와 화면 지도는 7차 인터뷰에서 정했다.
- 비교 서비스별 공개 자료로 확인할 수 없는 내부 구조 및 실제 계정에서 관찰할 동작 범위.

## 인터뷰 1차 — 사용자 답변으로 확정

### 실제 연구 예시

1. TeamFight Manager2의 밴픽 자동화 모델 개발. 최적의 밴픽 과정을 강화학습으로 훈련한다.
2. NTIRE의 Image/Video compression 분야에서 rank 1 모델 개발.

사용자는 2차 답변에서 두 사례가 예시일 뿐임을 명확히 했다. 시범 과제 선택과 해당 과제의 환경 확정은 현재 개발의 선행 조건이 아니다. 연구 범위는 자료 조사, 분석, 모델 개발 및 실험 등으로 넓게 열어 둔다. 특정 대회 연도·트랙 또는 게임 환경에 의존하는 제품 요구사항을 만들지 않는다.

### 산출물

- 모델 개발 예시에서는 모델 결과. 범용 시스템에서는 연구 요청에 맞는 산출물을 정의해야 한다.
- Top-Down, MECE 형식으로 작성된 보고서.
- 다음 행동 제안은 선택 사항.
- 연구별 전달 형태, 재현 요건, 지표, 시간·비용 목표는 해당 연구를 요청할 때 지정하거나 Lead와 보완할 수 있도록 하는 방식을 검토한다.

### 자율성과 사용자 관계

- 사용자가 요청과 예산을 주면 계획부터 완료까지 자동 진행한다.
- Research Lead agent가 중간중간 사용자에게 보고하거나 질문한다.
- 사용자는 보고/질문에 피드백을 전달한다.
- 사용자는 진행 중에도 Research Lead에게 새로운 task를 전달할 수 있다.
- 새 task나 피드백이 들어오면 Lead가 현재 연구와의 관계·우선순위를 판단해 반영한다.
- 큰 목표 변경이나 추가 예산이 필요하면 Lead가 사용자에게 질문한다.
- 초기 계획과 팀 구성을 사용자에게 함께 승인받은 뒤 연구를 실행한다.
- 주요 진행·문제·결정이 생기거나 사용자가 요청할 때 보고한다. 정기 보고는 기본 요구로 확정하지 않았다.
- 완료 기준은 목표 설정 때 Lead와 정하며, 기준 충족 후 결과를 제출하고 사용자 검토·최종 완료 결정을 기다린다. (2026-10-27 변경: [판 1 피드백](#판-1-피드백--목표는-생성-dialog에서-2026-10-27-사용자-확정))

## 인터뷰 2차 — 사용자 정정과 확정 답변

- 사용자는 특정 연구 과제 선정과 구체적인 GPU/서버/예산 확정을 지금 요구하는 것에 반대했다. 예시를 근거로 특정 연구에 치우친 구현이 되는 것을 원하지 않는다.
- 이전 기록의 ‘ML 연구 조직으로 범위 확정’과 ‘첫 시범 연구·자원부터 선정’은 agent의 잘못된 해석이며 철회한다.
- 새 요청 처리 정책은 ‘Lead 판단 후 반영, 큰 목표 변경·추가 예산은 질문’으로 확정했다.

## 인터뷰 3차 — 사용자 답변으로 확정

### 팀 구성과 자율성

- 기본적으로 처음 연구 목표를 설정할 때 작업자 팀을 새로 구성한다.
- 연구 진행 중 새로운 작업자가 필요하면 Research Lead가 사용자의 허락을 받고 추가한다.
- 연구의 특성 등에 따라 다른 운영 방식도 가능해야 하며, 어느 정도의 자율성을 보장한다.
- 최초 팀 승인과 조직별 Lead는 4차 인터뷰에서 확정했다. 구체적으로 어떤 운영 규칙을 바꿀 수 있는지는 아직 미정이다. 답변을 모든 agent 변경에 승인이 필요하다는 뜻으로 확대하지 않는다.

### 협력

- Lead가 작업을 분담·조정한다.
- 작업자끼리 직접 질문하고 결과를 공유할 수 있다.
- 직접 질문·공유와 연구 목표 변경·작업자 추가의 권한은 별개로 다룬다. 공유 범위와 담당 작업 변경 권한의 세부 사항은 미정이다.

### 사용자 접점

- 메신저 봇과 웹 관리 화면을 함께 사용한다.
- 이후 6차 답변에서는 웹 대시보드에서도 진행할 수 있고 메신저도 후보라고 보완했다. 장기적으로 두 접점을 고려하되 첫 버전에 두 접점을 동시에 구현하는 것을 필수 요구로 고정하지 않는다.
- 구체적인 메신저와 각 화면의 기능 분담은 미정이다.

## 인터뷰 4차 — 사용자 답변으로 확정

### 연구 목표와 조직의 단위

- 연구 목표마다 별도의 Lead와 작업자 팀을 구성한다. 사용자는 이것이 Paperclip에서 하나의 organization을 만드는 것과 같은 의미라고 명시했다.
- 여기서 연구 목표는 ‘TeamFight Manager 2의 밴픽 강화학습 모델 개발’ 또는 ‘NTIRE의 Image/Video compression 분야의 1등 모델 개발’ 같은 상위 목표이다.
- 위 예시는 용어의 규모를 설명하며 제품의 연구 분야를 제한하지 않는다. 개별 조사·실험·보고서 작성 작업마다 새 조직을 만든다는 의미가 아니다.
- 공통 용어 정의는 루트 `CONTEXT.md`(현재 `GLOSSARY.md`)에 기록했다.

### 최초 팀 구성

- Lead가 최초 팀 구성을 제안하고 사용자가 승인한 뒤 연구를 시작한다.
- 연구 진행 중 신규 작업자 추가도 사용자 승인을 받는다.
- 초기 연구 계획도 최초 팀과 함께 승인하는 것으로 5차 인터뷰에서 확정했다. 반려·수정 절차는 미정이다.

### 기억과 공유

- 기억은 연구 조직별로 분리한다.
- 사용자가 지정한 내용만 다른 연구 조직에 공유한다. 조직 간 자동 기억 공유를 기본 동작으로 하지 않는다.
- 공유 대상·내용·시점의 지정 방식과 변경/회수 정책은 미정이며 구현되지 않았다.

## 인터뷰 5차 — 사용자 답변으로 확정

### 시작 승인

- Lead가 제안한 초기 연구 계획과 팀 구성을 함께 사용자에게 승인받는다.
- 승인 후 연구를 실행한다. 제안에 필요한 계획 수립과 실제 연구 실행을 구분한다.

### 중간 보고

- 주요 진행·문제·결정이 생기면 Lead가 보고한다.
- 사용자가 요청할 때도 보고한다.
- 정기 요약은 사용자 답변에 포함되지 않았으므로 기본 요구사항으로 확정하지 않는다.

### 완료 판단

- 목표 설정 때 Lead와 완료 기준을 정한다. (2026-10-27 변경: [판 1 피드백](#판-1-피드백--목표는-생성-dialog에서-2026-10-27-사용자-확정))
- 기준을 충족하면 Lead가 결과를 보고한다.
- 사용자가 검토하고 최종 완료를 결정한다. 기준 충족 또는 agent의 결과 제출을 자동 최종 완료로 취급하지 않는다.
- 검토 중 수정 요청, 기준 변경, 검토 대기 중 새 작업 처리의 세부 방식은 미정이다.

## 인터뷰 6차 — 사용자 접점과 조사 대상 보완

- 메신저는 미정이다. 사용자는 Paperclip처럼 웹 대시보드에서 진행해도 좋으며 Telegram/Slack/Discord 같은 메신저 앱도 괜찮다고 했다.
- 첫 버전의 접점을 지금 선택하거나 두 접점을 동시에 구현해야 한다고 가정하지 않는다.
- ‘grok bot’은 xAI에서 낸 정식 Grok Bot을 가리키며, Meta Muse와 OpenAI dots 같은 상용 서비스의 맥락으로 명확해졌다.
- 해당 제품을 Grok Build CLI, Grok API 또는 제3자 봇과 혼동하지 않는다. API와 CLI도 별도 비교 대상으로는 검토할 수 있다.

## 백로그 재분류 — 2026-10-13 사용자 확정

- 프로젝트 목적은 AI agent로 구성된 organization이 자율 연구할 수 있는 환경을 만드는 것입니다. 연구 전략과 다음 행동의 판단은 Lead와 작업자가 담당합니다.
- 백로그는 `orchestration`(조직·실행·협력·human interaction 환경)과 `research-harness`(연구 역할·skills·절차·근거·실험·평가 지원)로 구분합니다.
- 혼합 책임 #5·#6·#14·#15·#16·#19는 기존 번호를 추적용 부모로 유지하고 두 책임을 하위 이슈로 분리합니다. 구현 선행 조건은 필요한 구현 하위 이슈를 참조합니다.
- Agent용 조직 도구/API, 연구 역할·skills, 결과 검토·연구 반복을 독립 이슈로 추가합니다.
- #20은 환경 통합 검증과 연구 하네스 검증을 별도 하위 이슈로 분리합니다.
- 메모리 기법 선정과 실제 모델 호출은 이번 백로그 정리의 범위가 아닙니다. 해당 구현 시 조사·계정·자격 증명·비용 권한을 확인합니다.

## 기본 운영 흐름 — 요구사항 요약

후속 기능 확정 답변에서 웹 관찰 대시보드의 높은 우선순위, agent별 pause/resume/heartbeat와 연구 전체 중단/재개, ROLE.md/SOUL.md 형태의 설정, 조직 공통/agent별 기억 분리 방향과 나중에 기법 선정, 예산·시간 정책, 문제→가설→검증 방법→실험→결과의 연구 지도와 템플릿 지원을 추가했다. 메모리 기법 조사는 이번 init에서 수행하지 않는다. 상세 기능의 현재 기준선은 `features.md`이다.

목표·예산 전달 → Lead와 완료 기준 설정 → 초기 연구 계획·팀 제안 → 사용자 승인 → 자율 연구/직접 협력 → 기준 충족·결과 제출 → 사용자 검토·최종 완료.

진행 중 피드백·새 작업은 Lead가 관계/우선순위를 판단해 반영한다. 신규 작업자 추가, 큰 목표 변경 또는 추가 예산은 사용자에게 승인/판단을 요청한다. 사건 발생 또는 사용자 요청에 따라 보고한다. 위 흐름은 제품 요구사항이며 실제 상태 이름과 저장·실행 방식은 아직 설계하지 않았다.

## 검증 시나리오 후보 — 아직 실행하지 않음

- 두 조직에서 이름이 같은 작업을 실행해도 작업·메시지·기억이 서로 섞이지 않는지 확인한다.
- 최초 계획·팀의 승인 전에는 제안 준비와 실제 연구 실행을 구분하고, 승인 대상이 수정되면 어떤 버전에 승인이 적용되는지 확인한다.
- 신규 작업자가 승인 대기 중에는 실제 연구에 참여하지 않으며, 기존 작업자끼리의 직접 협의가 이 승인 절차를 우회하지 않는지 확인한다.
- 사용자가 지정한 내용만 다른 조직에 전달되고, 공유하지 않은 기억은 검색·대화 맥락에 포함되지 않는지 확인한다.
- 진행 중 새 요청을 받아 우선순위를 조정하되, 큰 목표 변경이나 추가 예산은 사용자 판단으로 연결되는지 확인한다.
- 완료 기준을 충족해 결과를 제출한 시점과 사용자가 최종 완료를 결정한 시점을 구분하는지 확인한다.

이 시나리오는 요구사항에서 도출한 검증 제안이다. 구체적인 저장 구조·상태 이름·테스트 도구는 아직 확정하지 않았다.

## 인터뷰 이후의 진행 원칙

- 조직·협력·기억·보고·개입·작업 상태 등 범용 운영 요구사항을 먼저 구체화한다.
- 연구별 완료 기준·자원·도구는 각 연구 요청의 설정으로 다룬다. 공통 기능 검증에 사용할 예시는 제품 범위를 제한하는 요구사항과 구분한다.
- 폭넓은 서비스 조사 목록과 첫 버전에 필요한 심층 조사 목록을 구분해 관리한다.
- Paperclip을 그대로 채택해야 한다고 미리 가정하지 않는다.
- 사용자 답변이 들어오면 이 문서에 확정 사항과 미결 사항을 갱신한다.

## 인터뷰를 위한 초기 설계 가설 — 미확정

- 위 기본 운영 흐름을 공통 엔진으로 표현하고, 실제 연구 작업의 단계와 도구는 연구마다 설정하거나 확장한다. 고정된 ML 절차를 공통 엔진에 내장하지 않는다.
- Paperclip에서 참고할 후보는 역할/위임, 명시적 작업 상태, 작업 독점 처리, 이벤트 기반 실행, 실행 기록과 세션 재개, 예산/사용자 개입 기능이다.
- 연구 기능에는 출처와 개별 주장 연결, 원문/버전 기록, 상충하는 근거 처리, 독립적인 검증, 완료 기준과 재조사 한도 등이 추가로 필요할 수 있다.
- 장시간 외부 작업의 상태·결과 추적은 공통 기능 후보이다. ML 연구의 GPU 작업·체크포인트·실험 기록은 연구별 연동의 예시이며 필수 기본 기능으로 확정하지 않는다.
- 연구 목표마다 독립 조직과 전용 Lead를 둔다. 나머지 역할, 직함, agent 수와 구성 제안 방식은 미정이다.
- 작업자 간 질문/결과 공유는 같은 조직 안에서 지원한다. 초기 계획·팀 구성, 연구 중 신규 작업자 추가와 사용자 최종 완료 결정에는 명시적 승인/검토 상태를 연결하는 설계를 검토한다. 이는 요구사항을 구현할 후보이며 아직 구현되지 않았다.
- 조직 간 기억 공유는 사용자 지정 내용으로 제한한다. 작업자의 직접 소통 권한이 이 조직 경계를 넘는 자동 공유 권한을 뜻하지는 않는다.
- 연구별 운영 규칙을 설정하는 방식은 자율성과 기본 승인 정책을 함께 표현하기 위한 설계 후보이다. 실제로 바꿀 수 있는 규칙과 변경 권한은 인터뷰·비교 조사로 정한다.
- 위 내용은 인터뷰용 가설이며 사용자의 확정 요구사항이 아니다.

## 인터뷰 7차 — 전체 구조와 상호작용, 2026-10-13 사용자 확정

사용자는 구현할 것을 세 영역으로 보았다. ① agent들이 상호작용하며 자동으로 연구할 환경(orchestration, memory 등), ② agent들이 연구에 쓸 하네스(skill, role, soul, 연구 철학, 흐름 템플릿), ③ 대시보드 감시와 메시지 앱을 통한 명령·인터럽트. 결과 구조는 [`architecture.md`](architecture.md), 기능 범위는 [`features.md`](features.md), 구조를 고른 이유는 [`adr/`](adr/)에 기록했다. 아래는 사용자의 판단과 이전 기록을 바꾸는 내용이다.

- Paperclip은 그대로 채택하지 않는다. 필요한 기능만 독립 구현하되 Paperclip, Hermes, OpenClaw와 자동 연구 프로젝트에 구현된 기능을 많이 참고해 가져와 붙인다.
- agent 실행 방식과 agent 간 상호작용은 기존 멀티 에이전트 프로젝트의 방식을 따르도록 조사 후 정했다. 조사: [실행 방식](research/agent-runtime-models.md), [상호작용 방식](research/agent-interaction-models.md).
- 사용자는 Lead의 자율성을 기본으로 원한다. 대시보드 설정의 체크박스(기본 꺼짐)로 사용자 허락을 받아야 할 행동을 고른다. 3차·5차 기록의 "신규 작업자 추가도 사용자 승인을 받는다"는 이 승인 정책으로 대체한다. 초기 연구 승인과 최종 완료만 항상 사용자 결정이다.
- 연구 지도는 엄격한 트리일 필요가 없다. 마인드맵이나 Obsidian 문서 링크처럼 여러 부모를 허용하고, 보조 연결은 연하게 그린다. 대시보드에서 보기 쉽고 손쉽게 고칠 수 있어야 한다.
- 사용자도 대시보드에서 연구 중 Role·Soul·Skill과 연구 지도를 바꿀 수 있다.
- 연구 환경 설정은 중요하다. 명세는 초기 승인 대상이고 구성은 승인 후 첫 작업으로 한다.
- 예산 한도에 닿으면 진행 중인 외부 job도 기본으로 취소하고, 설정으로 유지를 고를 수 있다.
- 대시보드는 Paperclip의 거의 모든 기능을 가져오고 OpenClaw·Hermes 등에서 필요한 것을 더한다. 조사: [Paperclip 대시보드](research/paperclip-dashboard.md), [기타 대시보드](research/dashboard-references.md).
- 사용자는 기본적으로 Lead와 대화하지만 작업에 댓글을 달 수도 있다.
- 메시지 앱은 두 번째 판에 붙이되, 첫 판에 그 자리를 구현해 둔다. (당시 인터뷰의 순서 표현. 2026-10-23 확인한 [현재 로드맵](architecture.md#구현-순서)은 실제 실행기 연결이 판 2, 메시지 앱 연결이 판 3이다.)
- 사용자는 self-host하는 한 명이다.

## 판 1 피드백 — 목표는 생성 dialog에서, 2026-10-27 사용자 확정

사용자는 처음 Lead 대화를 `목표: …`·`완료 기준: …` 형식으로 시작해야 하는 흐름을 원하지 않았다. 그럴 바에는 Lead 대화가 아닌 별도 창에서 목표와 완료 기준을 적게 해야 한다고 보았다. 완료 기준은 빈 칸도 허용하고, 비우면 Lead가 기준을 세워 사용자에게 허락받는다. 1차·5차 기록의 "목표 설정 때 Lead와 완료 기준을 정한다"는 이 방식으로 대체한다. 현행 기준은 [기능 범위](features.md)의 초기 계획과 팀·완료 항목이다.
