# 구현 기능 기준선

기준: 사용자 인터뷰와 최신 기능 확정 답변. 이 문서는 기능 범위이며 구현 여부는 각 이슈에서 확인합니다. module 구조와 불변 조건 강제 위치는 [`architecture.md`](architecture.md)에, 이슈별 상세 조사·결정·검증 항목은 GitHub 이슈에 기록합니다.

| 영역 | 확정 범위 | 아직 결정할 것 |
|---|---|---|
| 조직 | 연구 목표별 독립 조직, 전용 Lead와 팀, 7단계 조직 생애주기 | 구체적인 데이터 형식, 생애주기 하위 상태 |
| 웹 대시보드 | 높은 우선순위. 아래 [화면 지도](#웹-대시보드-화면-지도) | 후속 화면의 상세 배치와 디자인. UI 스택은 [ADR-0004](adr/0004-paperclip-aligned-stack.md)에서 확정 |
| 초기 계획과 팀 | Lead가 초기 연구 계획·팀 구성·연구 환경 명세를 제안하고 사용자가 함께 승인한 뒤 실행. 반려·수정 요청은 Lead를 깨워 재계획 | — |
| 구성원 | agent별 Role·Soul·Skill(`AGENTS.md`/`SOUL.md`/`SKILL.md` 관례). 사본은 에이전트마다 따로 두고 새 에이전트는 하네스 라이브러리에서 복사. 신규 작업자 추가는 승인 정책에 따름. Lead와 사용자가 연구 중 사본을 조정하고 저장마다 revision을 남김 | 파일 세부 형식 |
| 승인 정책 | 조직별 체크박스, 기본 꺼짐. 켜진 행동은 제품이 승인 요청으로 바꿈. 초기 연구 승인과 최종 완료는 항상 사용자 결정 | 정책 항목 전체 목록 |
| 실행 | 작업 분해·분담, 깨우기와 병합, agent별 선택적 heartbeat, agent별 일시정지·재개, 조직 전체 일시정지·재개·중단 | 재시도 정책 |
| 외부 job | 실행 시도와 분리된 장시간 작업 기록. 종료 시 시작한 agent를 깨움. 일시정지 중 유지, 중단 시 취소, 서버 재시작 후 재조정 | 실행 수단(로컬·SSH·클라우드) |
| 연구 환경 | 명세는 초기 연구 승인 대상. 구성은 승인 후 첫 작업들. 사용자만 할 수 있는 일은 사용자 할 일로 요청 | 자격 증명 저장·주입 방식 |
| 협력 | 같은 조직 안에서 영속 기록과 깨우기로 직접 질문·결과 공유, Lead 조정, 하위 작업 완료 시 부모 담당자를 깨움 | 담당 변경 규칙 |
| 사용자 개입 | Lead 대화와 작업 댓글. 실행 중 입력은 다음 실행 시도에 반영(기본), Lead 대화의 steer, `중단하고 반영` 선택. 제어 명령은 즉시 효력. 연구 지도와 Role·Soul·Skill 직접 편집 | — |
| Lead 채팅 | 목표 설정·질문·피드백·추가 작업을 대화로 수행. 판 1은 웹 대시보드 채팅, 판 3에 메시지 앱을 같은 명령 경로로 연결([구현 순서](architecture.md#구현-순서)) | 메시지 앱 선택 |
| 기본 연구 흐름 | 문제 식별·목록화 → 가설/아이디어 → 검증 방법 → 실험/검증 → 결과 평가·반복 | 단계별 상세 규칙 |
| 연구 지도·템플릿 | 주 연결(노드당 최대 1개)과 보조 연결의 그래프. 주 연결로 트리 배치, 보조 연결은 연하게 표시. 대시보드에서 편집. 연결 종류와 연구 철학은 템플릿이 정의 | 템플릿 스키마 |
| 기억 | 연구 기록 위의 회수 계층. 조직 기억과 agent 기억 구분, 조직 간 격리와 사용자 지정 공유 | 기법·저장·검색·회수. 해당 조사 이슈에서 결정 |
| 예산·시간 | 조직 단위 예산, 모델 비용·job 비용·경과 시간 집계, 한도 도달 시 자동 일시정지와 추가 예산 요청, 진행 중 job은 설정에 따라 취소(기본)·유지 | 비용 집계 세부 |
| 보고·산출물 | 주요 진행·문제·결정 및 사용자 요청 시 보고, 연구별 산출물, Top-Down/MECE 보고서. 메시지 앱 알림은 Lead 보고·질문, 승인 요청, 사용자 할 일, 결과 제출, 오류·예산·job 경고로 한정 | 품질·근거 검증 상세 방식. 다음 행동 제안은 선택 |
| 완료 | 목표 설정 시 완료 기준 합의, 결과 제출 후 사용자 검토로 최종 완료, 수정 요청 시 연구 진행으로 복귀 | 완료 기준 변경 처리 |
| Agent용 조직 도구/API | 실행 시도별 토큰으로 범위가 묶인 하나의 도구 계약으로 작업·협력·기억·연구 기록·산출물·승인 요청·외부 job을 호출, 실행 맥락 구성 | 노출 형식·맥락 선택/크기 |
| 연구 역할·skills | 목표/계획·조사·가설·검증·검토·종합의 지침·입출력·필요 도구·검증 계약, 조직별 조합 | 첫 역할 구성·적용 방식 |
| 결과 검토·연구 반복 | agent가 근거를 평가하고 가설 수정·후속 검증·재계획·결과 제출을 판단, 선택과 근거를 기록 | template별 반복·진전 없음 처리·평가 분담 |

## 웹 대시보드 화면 지도

Paperclip 대시보드의 대부분을 연구 조직 개념에 맞게 가져오고 연구 화면을 더합니다. 근거는 [Paperclip 대시보드 조사](research/paperclip-dashboard.md)와 [기타 대시보드 조사](research/dashboard-references.md)입니다. 모든 화면은 Event stream으로 실시간 갱신합니다. `첫 판` 열은 첫 walking skeleton에 넣을 범위이고, 나머지는 판을 거듭하며 채웁니다. 체크 표시는 목표 범위이며 구현 완료 표시가 아닙니다. 현재 구현 요약은 [README](../README.md), 개별 완료 근거는 해당 이슈·PR을 따릅니다.

| 화면 | 내용 | 첫 판 |
|---|---|---|
| 공통 셸 | 연구 조직 목록·상태 사이드바, 조직 생성 dialog(이름만 받고 Lead 대화로 이동), command palette와 검색 연산자, 단축키, 토스트, 조직 범위 전문 검색, 쓰기 대상 조직 표시 | 사이드바와 조직 생성 |
| 홈 | 전체 조직 개요: 주의 필요·실행 중·조직 수, 조직 카드(주의 필요 → 진행 중, 끝난 조직은 접음; 단계·목표·실행 중 수·마지막 활동). 근거 [홈 조사](research/home-references.md) | ✅ |
| Inbox | 승인 요청·사용자 할 일·결과 제출·실패한 실행 시도·예산 경보를 한 대기열로. 주의 필요·전체·읽지 않음·보관됨 필터, 열면 읽음·체크해 읽음, 보관은 끝난 항목(실패한 실행 시도)만 | ✅ |
| 조직 › 대시보드 | 지표, 14일 차트, 실행 중인 agent, 최근 활동, 일시정지·재개·중단 | ✅ |
| 조직 › Lead 대화 | 웹 채팅 | ✅ |
| 조직 › 활동 | 실행 시도·도구 호출 요약·메시지·상태 변화 stream, agent별 필터 | ✅ |
| 조직 › 작업 | 목록·칸반·그룹·필터, 상세(자기 보고 요약, 댓글 thread, 문서, 산출물, 연구 노드·외부 job 속성) | 목록과 상세(요약·댓글 thread·산출물·연결 노드) |
| 조직 › 연구 지도 | 그래프, 노드 상세 패널(계획·지표·그림·연결 작업), 반복별 지표 추이 | 보기와 간단 편집, 노드 위치 드래그 |
| 조직 › 에이전트 | Lead·작업자 팀 뷰와 상태 | ✅ |
| 조직 › 에이전트 상세 | 상태·최근 실행 시도, 일시정지·재개, heartbeat 켜기·간격, timeout, 그 에이전트의 Role·Soul·Skill 사본 편집기(revision 목록·보기·되돌리기·diff) | timeout과 revision 되돌리기·diff 빼고 ✅ |
| 조직 › 실행 시도 상세 | transcript(결과 접기), 하위 실패 표시, 컨텍스트 구성 분해. 모델 추론은 provider가 공개로 반환한 것만 | 단순 |
| 조직 › 외부 job | 상태·로그·비용, 이 job만 중지 | — |
| 조직 › 산출물 | 목록, 단건 보기, 문서 revision, 갤러리 | 단건 보기만 |
| 조직 › 정기 작업 | 일정, 실행 이력, Test run | — |
| 조직 › 비용·예산 | agent·모델별 비용, 추정치와 실제 청구 분리, 예산 정책·incident | — |
| 조직 › 감사·Timeline | 제어 명령을 포함한 모든 변경 feed, 외부 job 구간을 포함한 Gantt | — |
| 조직 › 결과 검토 | 결과 제출 → 수정 요청 또는 최종 완료 | ✅ |
| 조직 › 기억·명시적 공유 | 기억 이슈에서 내용 결정 | — |
| 조직 › 설정 | 승인 정책 체크박스, 예산, job 한도 처리, 연결 채널 | 정책 항목 하나 |
| 전역 설정 | 실행기 adapter, 연구 환경 템플릿, 비밀값, 메시지 앱 연결 | 자리만 |

목록에서 들어가는 상세(작업·에이전트·산출물·실행 시도·Inbox 항목)는 별도 경로의 페이지로 열고, 오른쪽 패널은 Inbox만 씁니다. 연구 지도의 노드 상세 패널만 예외입니다. 조직 화면 목록은 화면이 늘어도 훑을 수 있게 묶음으로 나눕니다.

가져오지 않는 것: 다중 사용자 기능(Members·Invites·Access·Board claim), Projects·Goals(연구 지도로 대체), Paperclip 실험 기능(Cases·Pipelines·Status cards), Team catalog marketplace, Experimental 플래그, Auto Review, 만료되는 승인 세션, 사용자와 작업자의 직접 대화(작업자에게는 작업 댓글로만 말하고 연구 방향은 Lead와 이야기함). Plugins와 회사 Import/Export는 나중 후보입니다.

## 환경과 연구 하네스의 구분

- `orchestration`: AI organization의 조직·실행·협력·기억 접근·사용자 interaction 환경. 조직 경계·승인·예산·실행 제어를 제품에서 강제합니다. [`architecture.md`](architecture.md)의 Surface·Control Plane·Agent Runtime·Memory port에 해당합니다.
- `research-harness`: Lead와 작업자의 자율 연구를 지원하는 역할·skills·절차·근거·실험·평가·보고 도구. 연구 전략과 다음 행동의 판단은 agent가 담당하며 다른 연구 철학의 템플릿을 적용할 수 있습니다.

## 범위 원칙

- 특정 게임·대회·모델·GPU는 활용 예시이며 공통 엔진의 전제 조건이 아닙니다.
- 사용자는 self-host하는 한 명입니다. 다중 사용자 권한 모델은 범위 밖입니다.
- GitHub blocker는 기능 구현의 선행 조건입니다. 이슈의 자료 조사와 설계 검토는 선행 구현 완료 전에 수행할 수 있습니다.
- 역할 문서나 agent 프롬프트만으로 승인·조직 경계를 강제했다고 판단하지 않습니다.
