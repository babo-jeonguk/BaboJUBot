# 전체 구조

2026-10-13 합의한 목표 구조입니다. [용어](../GLOSSARY.md)·[결정 이유](adr/)·[스택](adr/0004-paperclip-aligned-stack.md)을 따르며, 미정 사항은 [후속 결정](#다음-단계로-넘긴-결정)에 둡니다.

## Module

```text
Surface ⇄ Control Plane ⇄ Agent Runtime(실행기·job runner adapter)
               ↕                  ↑ 실행 시도 조립 때 로드
           Memory port      Research Harness
```

| Module | 책임 |
|---|---|
| Surface | 웹 대시보드·메시지 채널. 비즈니스 규칙 없이 같은 명령 경로·Event stream 사용 |
| Control Plane | 연구 기록의 원본·상태 변경의 유일한 주체. 조직·에이전트·작업·메시지·승인·예산·지도·산출물·job·사용자 할 일·Event log 및 제품 불변 조건 강제 |
| Agent Runtime | 실행 시도·외부 job을 실행 수단에 위임. 자체 agent loop 없음([ADR-0001](adr/0001-adapter-control-plane.md)) |
| Memory port | 연구 기록 위의 회수 계층. 기법·엔진은 기억 이슈에서 결정 |
| Research Harness | 버전 관리하는 연구 내용물·전용 도구. 연구 판단은 에이전트 담당 |

사용자 요구의 ① 연구 환경은 Control Plane·Runtime·Memory, ② 연구 하네스는 Harness, ③ 감시·개입은 Surface에 대응합니다.

## 패키지 구성

현재 구현은 [README](../README.md), 실제 코드·테스트는 [코드 지도](agents/code-map.md)를 따릅니다.

| 위치 | 담는 것 | Module |
|---|---|---|
| `apps/server` | HTTP·WebSocket API·실행 시도. 첫 판은 한 프로세스, 필요할 때 worker 분리 | Control Plane, Agent Runtime |
| `apps/web` | 대시보드 | Surface |
| `packages/core` | 생애주기·승인 정책·조직 경계 규칙. 웹 프레임워크·DB 의존 없음 | Control Plane |
| `packages/contracts` | seam별 zod 스키마: 제어 명령, 사용자 메시지, Event, 실행 시도, 조직 도구 | 모든 seam |
| `packages/db` | Drizzle 스키마와 migration | Control Plane |
| `packages/runtime` | 실행기 adapter(가짜부터), job runner adapter, 채널 adapter | Agent Runtime, Surface |
| `harness/` | Role·Soul·Skill·연구 흐름 템플릿·연구 철학 내용물 | Research Harness |

Memory port의 첫 판은 core interface·db 단순 구현입니다.

## Seam

### Surface ↔ Control Plane

Surface가 보내는 것:

- **제어 명령**: 승인·반려·수정 요청, 결과 검토·최종 완료, 에이전트/조직 일시정지·재개·중단, 예산·승인 정책 변경. 즉시 효력·감사 기록.
- **사용자 메시지**: Lead 대화·작업 댓글. `다음 실행 시도에 반영`(기본), `steer`(Lead 대화·실행기 지원 시), `중단하고 반영` 중 선택. 마지막은 중단 명령·메시지를 각각 기록합니다.
- **사용자 편집**: 연구 지도·에이전트별 Role·Soul·Skill 사본. 즉시 반영·편집자 기록·Lead 깨우기. 연구 노드 삭제는 `폐기` 전이입니다.
- **조회**: 화면에 필요한 조직 범위 데이터.

Surface가 받는 것:

- **Event stream**: 조직 ID가 붙은 상태 변화·실행 시도 활동. 모든 화면이 실시간 구독합니다.
- **알림 outbox**: Lead 보고·질문, 승인 요청, 사용자 할 일, 결과 제출, 오류·예산·job 경고. 채널 adapter가 전송하고 답장·버튼 입력은 같은 명령 경로로 돌립니다. 첫 판은 가짜 채널이며 Lead 대화 메시지·승인 요청·결과 제출·실패한 실행 시도만 쌓습니다(사용자 할 일·예산·job 경고는 후속). 전송 의도는 사건 기록과 같은 transaction에 남고, Event 알림은 전송을 앞당기는 신호일 뿐 원본이 아닙니다. 전송 성공은 Inbox 읽음·승인을 대신하지 않습니다.

### Control Plane → Agent Runtime: 실행 시도

| 방향 | 모양 |
|---|---|
| 요청 | 신원(조직·에이전트·실행 시도), 실행 시도별 토큰, 깨우기 사유 묶음, 맥락 묶음, 지침 bundle 버전, workspace, 이전 세션 상태 |
| 진행 | 관찰 가능한 활동 이벤트 stream. 모델 추론은 provider가 공개로 반환한 것만 담습니다. |
| 종료 | usage·비용 추정, 다음 세션 상태 또는 세션 초기화, 요약, 종료 사유 |
| 제어 | 취소 |

지침 bundle 버전 변경 시 새 세션으로 시작합니다(재개 세션의 지침 교체를 지원하지 않는 실행기 대응). 가짜 실행기로 전체 계약을 검증한 뒤 [판 2](#구현-순서)의 실제 실행기 adapter를 붙입니다. 실제 모델 호출 전 계정·자격 증명·비용 권한을 확인합니다.

### Agent → Control Plane: 조직 도구

실행 시도별 토큰을 쓰는 단일 도구 계약입니다. 조직·에이전트 범위는 토큰에서만 정하고 입력으로 조직을 선택할 수 없습니다.

도구 범주: 작업, 메시지(같은 조직 안), 산출물, 연구 지도, 기억, 승인 요청, 사용자 할 일, 외부 job, 결과 제출, 팀·하네스 사본 조정. 정책상 승인 대상 호출은 제품이 승인 요청으로 전환하고 사용자 승인 뒤 실행합니다.

### Control Plane ↔ job runner

- 요청: job 명세(조직·시작한 에이전트·작업, 실행 내용, 한도).
- 보고: 상태, 로그 끝부분, 지표, 비용, 산출물.
- 제어: 취소, 서버 재시작 후 상태 재조정.

실행 수단(로컬·SSH·클라우드)은 adapter로 둡니다.

### Research Harness → Control Plane · Agent Runtime

- 라이브러리는 Role·Soul·Skill·흐름 템플릿·연구 철학을 `AGENTS.md`/`SOUL.md`/`SKILL.md` 관례로 담으며 실행기와 독립적입니다.
- 초기 연구 승인 제출 시 팀 Role·Soul·Skill·흐름 템플릿을 snapshot으로 고정하고 승인 때 그 snapshot에서 복사합니다. 반려·수정 요청 후 재제출은 직전 요청을 참조하는 새 요청으로 남겨 이전 내용·결정을 보존합니다.
- Lead Role·Soul은 조직 생성 시 라이브러리에서 복사합니다. 초기 승인 시 흐름 템플릿은 조직 사본, 팀 Role·Soul·Skill은 에이전트별 사본으로 만듭니다. 이후 추가 에이전트도 라이브러리에서 별도 사본을 받습니다. 같은 Role이어도 사본 수정은 서로 독립적이며 Lead·사용자가 조정합니다. 사본 저장마다 바뀌지 않는 revision(번호·편집자·시각·전체 본문)을 남기고, 지침 bundle 버전은 revision 번호가 아니라 사본 내용에서 정합니다. 라이브러리는 사용자가 개선합니다.
- 흐름 템플릿은 노드·연결 종류를 선언합니다. Control Plane은 구조를 검증하고 연구 판단은 에이전트에 둡니다.

### Memory port

`write(scope, entry, 출처)`·`recall(scope, query)`. 조직/에이전트 scope와 출처는 실행 시도 신원에서 정하고 Control Plane의 명시적 공유 기록을 따릅니다. 첫 구현(core port·db 구현)은 특정 기법 없이 저장과 최근순·글자 그대로의 문자열 회수만 합니다.

## 상호작용 규칙

협력은 영속 기록과 깨우기로 합니다([ADR-0002](adr/0002-durable-records-and-wakes.md)).

- 깨우기 원인: 작업 할당·메시지·하위 작업 완료·승인 결정(승인/반려/수정)·사용자 편집·외부 job 종료.
- 에이전트별 대기 깨우기는 한 실행 시도로 합칩니다. 실행 중 입력은 다음 시도로 미루며 예외는 위 메시지 전달 방식뿐입니다.
- Heartbeat는 에이전트별로 켜는 주기적 깨우기입니다. 간격은 Role 기본값을 사용자가 조정합니다.
- 하위 작업 완료는 부모 담당자를 깨웁니다. 하위 결과는 검증 대상인 자기 보고로 표시합니다.
- 사용자는 기본적으로 Lead와 대화합니다. 작업 댓글은 해당 담당자만 깨우고 Lead는 기록으로 봅니다.
- job 종료는 시작한 에이전트를 깨웁니다. 실패는 Lead 깨우기 대신 대시보드·알림에 표시합니다.

## 조직 생애주기

`목표 설정` → `계획 수립` → `승인 대기` → `연구 진행` ⇄ `일시정지` → `결과 검토 중` → `최종 완료`

- **목표 설정**: 사용자와 Lead가 대화로 연구 목표와 완료 기준을 합의합니다.
- **계획 수립**: Lead는 읽기 전용 탐색과 계획 초안만 할 수 있고, 별도 소액 한도 안에서 실행합니다. 작업자 생성·작업 배정 도구는 열리지 않습니다.
- **승인 대기**: 초기 연구 계획, 팀 구성, 연구 환경 명세를 함께 승인받습니다. 반려·수정 요청은 계획 수립으로 돌아가며 Lead를 깨웁니다.
- **연구 진행**: 첫 작업들로 연구 환경을 구성합니다. 사용자만 할 수 있는 일은 사용자 할 일로 요청하고, 자격 증명은 에이전트가 값을 보지 않도록 제품이 실행 때 주입합니다.
- **결과 검토 중**: 수정 요청이면 연구 진행으로 돌아갑니다.
- 일시정지·중단은 최종 완료 전 어느 단계에서든 가능합니다. 일시정지는 직전 단계를 기억해 재개 때 되돌리고, 중단은 되돌릴 수 없습니다. 일시정지 중 단계를 바꾸는 사용자 결정(초기 연구 승인·결과 검토)은 조직을 함께 재개합니다.

세부 하위 상태는 구현 이슈에서 정합니다.

## 제품 불변 조건 강제 위치

| 불변 조건 | 강제 위치 | 방식 |
|---|---|---|
| 조직 경계 | 조직 도구, Memory port, 메시지 전달 | 실행 시도별 토큰에서 범위를 정합니다. 에이전트 간 메시지는 같은 조직 안에서만 오가고, 다른 조직 내용은 명시적 공유 기록이 있을 때만 읽습니다. |
| 초기 연구 승인 | 조직 생애주기, 도구 노출 | 승인 전에는 계획 수립 권한만 줍니다. 항상 필요하며 끌 수 없습니다. |
| 최종 완료 | 결과 검토 제어 명령, 실행 시도 admission | Lead는 결과 제출만 하고, 완료 상태는 사용자 결정으로만 바뀝니다. 항상 필요합니다. 최종 완료 조직은 어떤 깨우기 사유로도 새 실행 시도를 시작하지 않습니다. |
| 사용자 제어 명령의 주체 | 사용자 API 실행 위치(로컬 신뢰 운영) | 사용자 API에는 로그인이 없고 서버·DB를 loopback에만 엽니다. 그 기기를 쓰는 사람을 사용자로 믿는 Paperclip `local_trusted`와 같습니다. 에이전트는 실행 시도별 토큰으로 조직 도구만 쓰지만, 같은 기기·같은 OS 사용자로 임의 HTTP·DB 연결을 하는 프로그램은 사용자와 구별되지 않습니다. 실제 모델 실행기를 붙일 때 실행 환경 격리와 함께 다시 정합니다([조사](research/issue-57-references.md#사용자-api-신뢰경계-추가-조사)). |
| 승인 정책 | 조직 도구, 사용자 제어 명령 | 사용자가 켠 항목의 도구 호출을 승인 요청으로 바꿉니다. 기본은 모두 꺼짐이고 정책은 사용자 제어 명령으로만 바꿉니다([ADR-0003](adr/0003-configurable-approval-policy.md)). 도구 쓰기는 조직 행 잠금 아래에서 최신 정책을 읽고, 정책 변경은 이미 기다리는 승인 요청을 바꾸지 않습니다. 첫 판 항목은 작업자 추가입니다. |
| 일시정지·중단 | 실행 시도 admission, 취소 | 새 실행 시도를 시작하지 않고 진행 중인 실행 시도를 끊습니다. 취소 요청은 실행 시도 행에 남겨 그 순간 토큰을 닫고, commit 뒤 실행기에 보내며, 실행기 등록 직후 다시 읽어 등록 전 요청도 받습니다. 실행기가 정리를 끝내 종료를 저장할 때까지 그 에이전트의 실행 슬롯은 비지 않습니다. 행 잠금 순서는 조직 → 에이전트 → 실행 시도입니다. 에이전트 일시정지는 조직 일시정지와 따로 저장합니다. 일시정지 중 외부 job은 계속 돌고, 그 사이 생긴 깨우기는 재개 때 전달합니다. 중단은 job 취소까지 요청합니다. |
| 예산 | 실행 시도 admission, job 보고 | 조직 단위로 모델 비용·job 비용·경과 시간을 집계합니다. 한도에 닿으면 조직을 자동으로 일시정지하고 추가 예산 요청을 띄웁니다. 진행 중 job은 설정에 따라 취소(기본) 또는 유지합니다. 비용 추정에 기반하므로 정확한 절대 상한이 아닙니다. |
| 관찰 가능성 | Event log, 실행 시도 활동 stream | 모든 상태 변화와 관찰 가능한 활동을 기록합니다. 비공개 모델 추론은 공개 로그로 가정하지 않습니다. |
| 연구 판단의 자율성 | Research Harness | 역할 문서와 skill은 지침입니다. 위 강제 수단을 대신하지 않습니다. |

## 연구 지도

- 연구 노드는 주 부모를 최대 하나 갖고, 보조 연결은 개수 제한 없이 맺습니다. 주 부모가 없는 노드도 허용합니다.
- 대시보드는 주 연결로 트리 배치를 잡고 보조 연결을 연하게 겹쳐 그립니다.
- 주·보조 지정은 노드를 만든 에이전트나 사용자가 정하고 나중에 바꿀 수 있습니다.
- 작업은 연구 노드 0~1개에 연결합니다. 작업 결과는 산출물과 결과 노드로 지도에 반영합니다.
- 그래프는 React Flow(`@xyflow/react`)로 그리고 Dagre(`@dagrejs/dagre`)로 배치합니다. 근거와 화면 결정 전체는 [#51 결정](https://github.com/babo-jeonguk/BaboJUBot/issues/51#issuecomment-6209365865)에 있습니다.
  - 배치 입력은 보이는 노드와 주 연결만입니다. 보조 연결 추가나 제목·상태 수정은 노드 위치를 바꾸지 않습니다.
  - 연결은 관계 ID를 그대로 그래프 edge ID로 씁니다. 라이브러리의 연결 중복 제거·부모 노드(`parentId`)·삭제를 연구 기록에 연결하지 않습니다.
  - 노드를 고르면 오른쪽 상세 패널이 열리고, 편집은 그 패널의 명시 폼으로 합니다.
  - 노드 위치 드래그는 보기 상태입니다. 편집자 기록이나 Lead 깨우기를 만들지 않고 주 부모도 바꾸지 않습니다.
- 삭제는 `폐기` 상태 전이이며 자손·연결·작업을 그대로 둡니다. 편집마다 편집 기록이 남고, 사용자 편집은 Lead를 깨웁니다. 사용자 편집은 초기 연구 승인 뒤 최종 완료·중단 전까지 받습니다(#56).
- 화면의 순환·후손 제외 검사는 빠른 피드백일 뿐입니다. 조직 경계·주 부모 최대 하나·주 연결 순환 금지·템플릿 종류는 Control Plane이 강제합니다.

## 구현 순서

각 판은 처음부터 끝까지 동작합니다. 아래는 단계별 목표이며 상세 명세·구현 순서는 각 판을 구체화할 때 정합니다.

1. 가짜 실행기와 가짜 채널로 조직 생성 → Lead 대화로 목표·완료 기준 → 계획·팀 제안 → 초기 연구 승인 → 작업 생성 → 작업자 실행 시도가 산출물과 연구 노드 생성 → 결과 제출 → 최종 완료. 승인 정책 항목 하나, heartbeat, 일시정지·재개를 포함합니다. 대시보드 첫 판 범위는 [`features.md`](features.md#웹-대시보드-화면-지도)에 있습니다.
2. 실제 실행기 adapter. Claude Code·Codex·Antigravity·OpenCode를 공통 실행 시도 계약에 연결해 실제 에이전트가 연구를 수행하도록 합니다. 실행기별 연결 방식(전용 adapter·ACP 등), 지침·도구 주입, 세션 재개·취소·활동/사용량 보고의 지원 범위와 구현 순서는 판 2 구체화 때 조사·결정합니다.
3. 메시지 앱 채널 adapter.
4. 외부 job, 기억, 예산을 깊게.
5. 연구 흐름 템플릿 교체.
