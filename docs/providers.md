# 실제 프로바이더 연결

서버는 기본적으로 가짜 연결만 등록한다. 실제 연결은 `BABOJUBOT_PROVIDERS=claude,codex,opencode,antigravity pnpm dev`로 추가한다. `claude:work`처럼 쓰면 같은 프로그램의 다른 계정 연결이 되고 제품 폴더도 따로 쓴다. 전역 설정에서 사용할 연결을 선택하고 저장한다. 프로그램 설치와 제품 로그인은 사용자가 한다. 실제 모델 호출은 구독 사용량이나 비용을 쓴다.

| 연결 | 시험한 판 | 실행 방식 | 지침 | 끼워 넣기 |
| --- | --- | --- | --- | --- |
| Claude Code | 2.1.317 | 실행마다 duplex stream-json | 기본 지침에 파일로 append | 살아 있는 입력 큐에 전달 |
| Codex | 0.166.0 | app-server 기본, `BABOJUBOT_CODEX_MODE=exec` 선택 | developerInstructions | app-server 턴 ACK; exec 미지원 |
| OpenCode | 2.2.5, 2.2.6 | 실행마다 `serve --stdio`로 HTTP 서버 시작, 조직 도구 호출 키 plugin | 기본 지침 유지, session instructions API 추가 | `delivery: steer` 응답 |
| Antigravity | 1.5.4(가짜 상류로 합성 확인) | 실행마다 `agy acp`(Agent Client Protocol) 세션 하나 | 첫 입력 앞에 추가 | 미지원 |

판을 제한하지 않는다. 설치된 프로그램을 그대로 쓰며, 표의 판은 실제 호출로 시험한 기준이다. 프로토콜이 어긋나면 준비 확인이나 실행 시도가 실패로 드러난다. OpenCode 1.x는 서버 방식이 달라 동작하지 않는다.

Linux·macOS·Windows를 지원한다. 실제 호출은 Linux(WSL)에서만 시험했고, macOS·Windows는 CI에서 프로그램 연결·조직 경계 읽기·서버 기동 자동 검사만 돈다. 서버 기동은 두 OS 모두 내장 DB로 확인한다(강제 종료 뒤 남은 DB의 정상 정지 포함). 내장 DB는 `pg_ctl`로 켜므로 Windows 관리자 계정에서도 뜬다. 일반 권한 Windows는 미검증이다. Windows에는 프로세스 그룹이 없어, 프로그램이 스스로 끝난 뒤 남은 자식 프로세스는 찾지 못한다. 취소 때는 프로세스 트리를 끝낸다.

## 설정

연결 이름의 영문·숫자를 대문자로 쓰고 나머지는 `_`로 바꾼다. `claude:work`면 연결 ID는 `claude-work`, 설정 이름은 `BABOJUBOT_CLAUDE_WORK_...`이다.

| 환경 변수 | 뜻 |
| --- | --- |
| `BABOJUBOT_<연결>_COMMAND` | 프로그램 위치. PATH에 없을 때 쓴다 |
| `BABOJUBOT_<연결>_PASS_ENV` | 그 연결에 넘길 환경 변수 이름(쉼표로 구분). API 키·Bedrock·Vertex 같은 다른 로그인에 쓴다. 격리 실행(컨테이너)에는 넘기지 않는다 |
| `BABOJUBOT_<연결>_ADDITIONAL_MODELS` | Claude 연결의 모델 목록에 더할 모델. `[{"id":"…","label":"…"}]` 형식의 JSON |

프록시·인증서·언어 변수는 항상 넘긴다. 그 밖의 환경 변수는 적은 것만 넘긴다. 쓰는 줄 모르고 다른 계정으로 과금되지 않게 하기 위해서다.

모델은 목록을 받아 오면 그 목록으로 확인한다. 목록이 비었거나(받아 오지 못한 때 포함) Claude처럼 제품에 담긴 목록을 쓰는 연결은 API에서 다른 모델 ID도 받고, 틀린 모델은 실행 시도의 실패로 드러난다. 받아 온 목록에 이름이 빈 모델이 있으면 ID를 이름으로 보인다. OpenCode에서 모델을 정하지 않으면 무료 모델을 먼저 고르고, 없으면 그 연결이 제공하는 첫 모델을 쓴다. 특정 무료 모델의 지속 제공을 보장하지 않는다.

Claude의 모델 목록은 제품에 담겨 있고(`packages/runtime/src/providers/claude-models.ts`) 새 모델이 나오면 제품 판과 함께 갱신한다. 그 전에 쓰거나 일부 계정만 쓰는 모델은 위 설정으로 더한다. 새 ID는 끝에 붙고, 내장 목록과 같은 ID는 그 자리에서 이름이 바뀐다. 내장 목록의 항목을 빼는 설정은 없다. 형식이 틀리거나 이름이 빈 항목은 경고하고 건너뛴다. 설정을 바꾸면 서버를 다시 시작한다. 예전 에이전트에 저장된 `opus` 같은 별칭은 그대로 동작하고, 고르는 칸에 그 값 그대로 보인다.

OpenCode는 시스템 설정을 끌 방법이 없어, `/etc/opencode`가 있으면 경고하고 함께 읽는다.

## 제품 로그인

제품 폴더는 `BABOJUBOT_HOME`으로 정한다. 지정하지 않으면 저장소의 Git 제외 로컬 데이터 폴더를 쓴다. 개인 설정·로그인 파일을 복사하지 않는다. 저장소 루트에서 실행한다.

```bash
pnpm provider:login claude   # codex, opencode, antigravity, claude:work
```

실행 시도와 같은 환경으로 프로그램의 로그인을 띄운다. 로그인은 연결 폴더(`providers/<연결>`)에 하며 모든 조직이 그 로그인을 쓴다(아래 조직별 제품 폴더). Claude는 화면에 나온 토큰을 붙여 넣으면 연결 폴더에 0600으로 저장한다. 입력이 터미널이면 붙여 넣는 토큰은 화면에 보이지 않고, 끝나면 터미널을 원래 상태로 되돌린다. 빈 입력은 저장 없이 건너뛰고, Ctrl-C는 저장 없이 `Login cancelled.`와 종료 코드 130으로 끝난다. 파이프로 넣은 입력은 그대로 읽는다. 토큰은 명령 인수·Git·이슈에 넣지 않는다. 무료 모델 제공자는 OpenCode 로그인 없이 쓸 수 있다.

로그인 여부는 파일 위치를 가정하지 않고 프로그램의 응답으로 판단한다. Claude는 `claude auth status`, Codex는 `codex login status`, Antigravity는 `agy models`를 쓰고, 그 전에 조직 실행과 같은 링크로 로그인을 읽게 맞춘 뒤 로그인 원본을 다시 쓸 수 있는지도 본다(못 쓰면 `준비안됨`). Claude와 Antigravity는 실행 시도도 파일 없이 시작하고, 거절되면 로그인 필요로 알린다. Antigravity는 로그인이 없으면 결과 없이 오류 문구만 남기고 끝나며, 이것도 로그인 필요로 알린다.

제품 HOME/XDG와 환경 변수 허용 목록은 개인 설정의 자동 유입을 막는 경계다. 호스트 파일·네트워크 접근은 아래 격리 실행을 켰을 때만 막는다. 사용자 홈·자격 증명·연구 원본은 Git에 추가하지 않는다.

## 조직별 제품 폴더

같은 연결이라도 실행 시도는 조직마다 따로 둔 제품 폴더 `providers/<연결>/organizations/<조직>`을 HOME·설정 폴더로 쓴다. 설정·세션 기록·확장(hook·plugin)은 그 조직 안에만 쌓이므로 한 조직의 에이전트가 써 둔 설정을 다른 조직의 프로그램이 읽어 그 조직의 실행 시도 토큰을 내보낼 수 없다. 격리 실행을 켜든 끄든 같다. 끈 경우에는 에이전트가 이 컴퓨터의 다른 폴더도 열 수 있어 보안 경계가 아니며, 다른 조직의 설정이 실수로 섞이는 것을 막는다.

연결 폴더 `providers/<연결>`은 로그인 원본·준비 확인·모델 목록·프로세스 기록에만 쓰고 컨테이너에 넣지 않는다. 로그인은 연결마다 한 번 하고 모든 조직이 같이 쓴다.

| 연결 | 조직이 로그인을 쓰는 방법 |
| --- | --- |
| Claude | 연결 폴더의 토큰을 실행 시도마다 환경 변수로 넣는다. 격리 실행에는 넣지 않고 인증 중계가 붙인다([인증 중계](#인증-중계)) |
| Codex | 원본은 로그인 전용 폴더 `providers/<연결>/login/auth.json`이고, 연결 폴더와 조직 폴더의 `auth.json`은 그 원본을 가리키는 링크다. Codex는 링크를 따라 원본 자리에서 바꿔 쓴다. 연결 폴더의 자리에 보통 파일이 있으면 가장 최근 로그인(예전 연결 폴더 로그인)으로 보고 원본으로 옮긴다. 조직 폴더의 자리는 격리 실행의 에이전트도 쓸 수 있으므로, 거기 남은 보통 파일은 로그인으로 가져가지 않고 `<자리>.set-aside`로 치운다(#148). 격리 실행에는 로그인 전용 폴더를 넣지 않는다([인증 중계](#인증-중계)). 두 조직이 같은 순간에 로그인을 갱신하면 하나가 실패해 다시 로그인해야 할 수 있다. 링크를 먼저 만들어 본 뒤에 로그인을 옮기므로, 링크를 만들 수 없는 컴퓨터(일반 권한 Windows, 링크를 모르는 파일 시스템)는 로그인을 연결 폴더에 그대로 두고 경고한 뒤 연결 폴더로 돈다(격리 실행은 실패). 링크를 만들 수 있는지는 실행·준비 확인마다 다시 보고, 이미 있는 조직 링크도 그 판정을 따른다. 링크를 만들 수 없으면 모든 조직이 연결 폴더로 돌고, 연결 폴더 자리에서 로그인을 읽을 수 없을 때만(원본만 로그인 전용 폴더에 있는 경우 등) 원본을 그 자리로 옮긴다. 복사하지 않으므로 로그인은 하나다. 여러 조직이 한꺼번에 시작해도 로그인 옮기기는 하나씩 한다 |
| OpenCode | 로그인과 세션이 한 DB에 있어 로그인만 공유할 수 없다. 같은 제품 폴더의 서버는 하나씩 띄운다(새 폴더에 둘이 함께 뜨면 DB를 함께 만들다 하나가 끝난다, 2.2.6 확인 #147). 띄운 뒤의 실행 시도는 함께 돈다. 조직 폴더에 로그인이 하나도 없으면 실행 시도 시작 때 연결의 로그인 목록을 옮겨 넣는다(`auth import`와 같은 규칙, 같은 ID는 건너뜀, 세션은 옮기지 않음). API 키 로그인은 그대로 쓸 수 있고, 갱신되는 계정 로그인은 복사본끼리 어긋나 그 조직에서 다시 로그인이 필요할 수 있다. 격리 실행에서는 옮겨 넣지 않고, 조직 폴더에 옮겨 둔 로그인이 남아 있으면 시작하지 않는다 |
| Antigravity | Codex와 같은 방식이다. 키링이 없는 컴퓨터·컨테이너에서 agy는 HOME의 `.gemini/antigravity-cli/antigravity-oauth-token`으로 로그인하므로, 원본은 로그인 전용 폴더 `providers/<연결>/login/antigravity-oauth-token`이고 연결 폴더와 조직 폴더의 그 자리는 원본을 가리키는 링크다. agy는 로그인을 갱신하면 링크를 따라 원본 자리에 덮어쓴다(1.5.3 확인). 예전 연결 폴더 로그인은 원본으로 옮기고, 격리 실행에는 로그인 전용 폴더를 넣지 않는다. 동시 갱신·링크를 만들 수 없는 컴퓨터의 처리는 Codex와 같다. 키링에 로그인을 둔 컴퓨터에서는 이 컴퓨터의 조직 실행이 키링을 그대로 쓰고, 컨테이너 안에서는 키링이 보이지 않아 로그인 필요로 실패할 수 있다(미확인) |

이 배치 전의 세션 기록은 연결 폴더에 남고 조직 폴더로 옮기지 않는다. 네 연결 모두 이전 세션을 찾지 못하면 새 세션으로 시작한다. 근거와 선택지는 [조사](research/org-product-folders-references.md)에 있다.

## 격리 실행

전역 설정의 `격리 실행` 스위치(기본 꺼짐)를 켜면 실제 연결의 실행 시도와 Claude 미리 압축을 실행 시도마다 Docker 컨테이너 하나에서 돌린다. 꺼져 있으면 지금처럼 이 컴퓨터에서 돈다. 스위치는 누르면 바로 저장되고 다음 실행 시도부터 따른다. 이미 돌고 있는 실행 시도는 그대로 끝낸다. 가짜 연결은 프로그램을 띄우지 않으므로 상관없다.

- 컨테이너: 서버를 띄운 사용자의 uid:gid, 권한(capability) 모두 제거, `no-new-privileges`, 네트워크 없음(`--network none`, loopback만). 이미지는 받아 오지 않는다(`--pull never`).
- 폴더(#149): 서버가 정한 신원(조직·에이전트)의 자리만 넣는다. 조직 폴더(`organizations/<조직>/shared`)와 자기 개인 폴더(`agents/<자기>`)는 읽기·쓰기, 같은 조직 동료 개인 폴더는 읽기만, 그 조직의 제품 폴더(`providers/<연결>/organizations/<조직>`)는 읽기·쓰기, 토큰이 든 실행 시도 전용 파일은 임시 폴더의 `babojubot-attempt-*`(이 사용자만 접근)에서 읽기로만 넣는다. 자리마다 경로 끝의 조직·에이전트 ID가 신원과 같아야 하고, 그 위(서버가 만든 데이터 폴더)는 실제 경로로 푼 뒤 자리의 칸마다 링크가 아닌 폴더인지 본다. 링크·없음·종류 다름·다른 조직·다른 에이전트·자리 밖(사용자 홈, `/var/run` 등)·겹치는 폴더·자리 밖 작업 폴더는 프로바이더를 띄우기 전에 거부하고 실행 시도는 `격리 실행에 넣을 폴더가 권한과 맞지 않아 …(mount_link 등)`로 실패한다(이 컴퓨터 경로는 넣지 않는다). 작업 폴더를 따로 넣는 예전 동작은 없다. 넣는 폴더의 부모와 그 칸들은 어느 컨테이너에도 들어가지 않으므로 에이전트가 확인과 mount 사이에 바꿀 수 없다. 격리를 끈 채 이 컴퓨터에서 도는 에이전트는 이 전제 밖이다(서버와 같은 사용자). 연결의 로그인 원본(로그인 전용 폴더·토큰 파일, [인증 중계](#인증-중계))·연결 폴더·다른 조직·서버 데이터·사용자 홈·Docker socket은 넣지 않는다.
- 시작 환경(#149): 프로바이더는 이미지의 프로그램을 신뢰된 PATH(`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`, 모두 이미지 소유라 컨테이너 사용자가 쓸 수 없음)로 찾는다. 시작 스크립트는 `LD_PRELOAD`·`NODE_OPTIONS`·`PYTHONPATH`·`BASH_ENV` 같은 시작 때 다른 코드를 끌어들이는 값을 지우고, HOME의 Python 사용자 패키지(`PYTHONNOUSERSITE`)와 git `core.fsmonitor`를 자동으로 쓰지 않는다. 서버도 그 값들을 컨테이너에 넘기지 않는다. 조직 폴더의 가상환경(`shared/.venv`)은 더 이상 만들거나 PATH에 넣지 않으며, 이미 있는 것은 지우거나 옮기지 않는다. 연구 패키지는 개인 폴더의 가상환경을 연구 명령이 직접 골라 쓴다(`python3 -m venv "$BABOJUBOT_PERSONAL/.venv"` 뒤 `"$BABOJUBOT_PERSONAL/.venv/bin/python"`). 개인 가상환경은 격리 장치가 아니며, 공유 폴더의 코드를 일부러 실행하는 것까지 안전하게 만들지는 않는다. 남는 신뢰 범위: 같은 조직·같은 연결의 제품 폴더(HOME)와 작업 폴더의 프로바이더 설정(Claude `.claude/settings.json`의 hook, OpenCode `opencode.json`, Codex 설정, `AGENTS.md`·`CLAUDE.md`)과 HOME의 셸 시작 파일(`~/.bashrc`·`~/.profile` 등, 프로바이더의 셸 도구가 읽으면 그 안의 PATH 변경도 따른다)은 그 조직의 에이전트가 함께 쓰는 프로바이더 상태라 다른 에이전트가 바꿀 수 있고, 프로바이더가 그 설정대로 명령을 돌릴 수 있다. 저장소 hook은 commit 같은 명령을 실행할 때만 돈다.
- 환경: 제품 폴더 환경과 인증 중계 값은 이름만 명령에 적고 값은 docker 프로그램의 환경으로 넘긴다. GitHub 토큰(`GH_TOKEN`·`GITHUB_TOKEN` 등)·`BABOJUBOT_<연결>_PASS_ENV`에 적은 변수·이 컴퓨터의 `PATH`·임시 폴더·프록시 설정은 넘기지 않는다. 컨테이너에는 GitHub 로그인이 없다.
- 통신(#149): 실행 시도마다 이 컴퓨터의 임시 폴더에 중계 폴더(`babojubot-relay-*`)를 열고 컨테이너의 `/run/babojubot`에 읽기로 넣는다. 그 안의 파일 소켓만 바깥으로 이어지며, 이미지의 시작 프로그램(`docker/runner/relay.mjs`)이 컨테이너 loopback 포트를 그 소켓에 잇는다.
  - 외부: `HTTP(S)_PROXY=http://127.0.0.1:39280`(Node fetch도 따르게 `NODE_USE_ENV_PROXY=1`). 실행 시도 밖의 중계가 CONNECT·절대 주소 HTTP 요청만 받아 목적지마다 정책을 다시 읽고, 이름을 이 컴퓨터에서 풀어 모든 주소를 확인한 뒤 확인한 주소로만 연결한다. 프록시 환경을 지우거나 `NO_PROXY`·직접 socket·다른 DNS·IPv6·UDP(QUIC)를 써도 네트워크가 없어 나갈 길이 없다. SOCKS·업그레이드·프록시 안의 다른 방식은 거부한다. 이 컴퓨터의 상위 프록시 설정은 쓰지 않는다(직접 연결).
  - 열리는 목적지: 연결마다 정한 필수 모델·로그인 목적지(네 연결 모두 인증 중계에 붙어 없음 — 모델 통신은 조직 도구 연결의 인증 중계로만 나간다)와 운영자가 서버 시작 때 더한 `BABOJUBOT_MODEL_DESTINATIONS`는 늘 열린다(초기 연구 승인 전 Lead 계획 수립 포함). 원격 측정 목적지는 넣지 않았다. 조직의 `외부 연결 허용 목록`(조직 › 설정)은 초기 연구 승인 뒤(연구 진행·결과 검토, 그 단계의 일시정지)에만 더해진다. 새 조직의 목록은 비어 있어 연구 목적지는 모두 거부되고 `*`로 자동 허용하지 않는다. 목록은 사용자만 바꾸며 조직 도구가 없다. 항목은 이름(`example.com`, 하위 이름 전체 `*.example.com`) 또는 IP와 포트 하나다.
  - 금지 주소: 허용한 이름이라도 loopback·미지정·사설망(RFC 1918)·CGNAT·link-local(클라우드 metadata 포함)·멀티캐스트·broadcast·예약·문서용, IPv6 loopback·ULA·link-local·site-local·멀티캐스트·Teredo, IPv4를 담은 IPv6 표기(mapped·NAT64·6to4)의 그 IPv4, 이 컴퓨터의 주소로 풀리면 거부한다. 주소가 여럿이면(A/AAAA) 하나라도 금지면 거부한다. 내부 모델·데이터 서버가 필요하면 그 목적지 항목에 허용할 내부 주소를 하나씩 적는다(예: `models.lan:8000`에 `10.0.0.5`). 대역(`10.0.0.0/8`·`0.0.0.0/0`)은 저장하지 않고, 입력 검사를 거치지 않은 목록에 있어도 판정에서 무시한다. 사용자 API·DB 포트는 그 예외로도 열리지 않는다. 다른 조직 컨테이너는 네트워크가 없어 주소가 없다.
  - 거부: 중계는 403과 `X-BaboJUBot-Refusal`(`destination_not_allowed`·`address_not_allowed`·`not_resolved`·`protocol_not_supported`·`policy_unavailable`)로 답하고, 실행 활동에 `외부 연결 거부: <이름>:<포트>. <이유와 설정 방법>`을 남긴다(실행 시도마다 같은 목적지·이유는 한 번, 최대 50개). 사용자가 목록을 고치면 다음 연결부터 따른다. 목록을 줄이거나(주소 예외만 지운 경우 포함) 조직 단계가 바뀌어(최종 완료·중단 등) 더 이상 허용되지 않는 열린 연결은 바로 끊는다(`policy_changed`). 다시 볼 때는 새 연결과 같은 규칙으로 이름·포트와 실제로 연결한 주소를 보며, 이름은 다시 풀지 않는다. 판정 도중에 목록이 바뀐 연결은 열기 전에 새 목록으로 한 번 더 본다.
  - 허용한 사이트를 통한 데이터 반출까지 막지는 않는다. TLS 내용은 보지 않는다.
  - 조직 도구: 컨테이너 안 `http://127.0.0.1:39281`이 그 실행 시도의 `tools.sock`으로 이어진다. 중계가 요청에 그 실행 시도·조직 신원을 덮어써 넣고, 서버는 토큰의 실행 시도·조직과 다르면 401로 거부하므로 다른 실행 시도의 토큰은 이 중계로 쓰지 못한다. 사용자 API와 DB는 loopback에 그대로 두고, 이 컴퓨터에 조직 도구 listener를 따로 열지 않는다(호스트 방화벽을 열 필요가 없다). 인증 중계(`/api/relay/<연결>`)도 이 경로에 있다.
  - OpenCode 제어: 컨테이너 안 서버(0.0.0.0:4096)는 이미지의 시작 프로그램이 `inbound.sock`에 미리 붙여 둔 연결로만 부른다. 서버는 이 컴퓨터 loopback의 임시 포트로 그 연결을 잇고, 실행마다 만든 비밀번호로 인증한다. 컨테이너가 이 컴퓨터 쪽에서 여는 소켓은 없다.
  - 수명: 프로그램이 끝나면 중계부터 닫아 열린 연결·소켓을 모두 회수하고, 그다음 컨테이너를 지운다. Docker가 컨테이너를 늦게 지우거나 못 지워도 그 사이 컨테이너는 바깥·조직 도구에 닿지 못한다. 상태 점검 컨테이너도 같은 순서다. 서버가 중계에 정책을 붙이기 전이나 닫은 뒤에는 중계를 열지 않아 실행 시도가 시작하지 않는다. 중계를 열지 못하면 컨테이너를 멈춘다. 직접 bridge·host 네트워크로 대신 돌리지 않는다.
- 안전 확인: 스위치를 켰을 때·서버 시작·전역 설정 화면·`다시 확인` 때 먼저 같은 컴퓨터의 Linux Docker Engine인지(`DOCKER_HOST`가 unix가 아니면, Docker Desktop·rootless·Windows engine이면 거부)와 이미지가 이 제품의 시작 프로그램 판(`babojubot.runner` label 2)인지 본다. 그 뒤 실행 시도와 같은 권한·네트워크 없음·중계의 시험 컨테이너로 loopback 밖 네트워크 장치가 없는지, 이 컴퓨터의 주소(127.0.0.1과 각 인터페이스)의 사용자 API·DB 포트에 직접 닿지 않는지, 그 포트를 중계 목록에 올려 두고도 중계가 거부하는지, 중계를 거친 조직 도구에는 닿고 프록시 환경이 정해졌는지(양성 대조) 본다. 장치가 있거나 닿거나 중계가 열면 실제 연결은 모두 `준비안됨`(`격리 경계 열림`), Docker·이미지를 확인하지 못하거나 조직 도구에 닿지 않거나 확인이 60초 안에 끝나지 않으면 `준비안됨`(`격리 환경 없음`)이다. 연결의 준비 확인 시한(30초)은 이 확인 뒤의 연결 확인에만 쓴다. 확인을 통과하지 않으면 실행 시도는 컨테이너에서도 이 컴퓨터에서도 시작하지 않고 실패로 끝난다. 이 컴퓨터로 대신 돌리지 않는다.
- 정리: 취소 공통 순서(프로토콜 중단 → 2초 → TERM → 2초 → KILL)로 프로그램이 끝나면 위 수명대로 중계를 먼저 닫고, 마지막에 컨테이너를 지워 없어졌는지 확인한다. 지우지 못하면 서버 기록에 남기고, 서버 시작 때 이 제품 폴더가 띄운 컨테이너(`babojubot.owner` label)만 지운다.

공통 이미지는 `pnpm runner:build`(`docker/runner`)로 만든다. Node 24, git, Python, 기본 도구와 Claude Code·Codex(npm)·OpenCode 2.x(GitHub 릴리스, 기본 2.2.5, build arg OPENCODE_VERSION), 시작 프로그램(`entry.sh`·`relay.mjs`)을 담는다. #149 전의 이미지는 시작 프로그램 판이 맞지 않아 `격리 환경 없음`이므로 다시 만든다. Antigravity CLI는 공개 설치 경로를 정하지 않아 `docker build --build-arg ANTIGRAVITY_INSTALL="<설치 명령>"`으로 넣는다. 설정은 `BABOJUBOT_DOCKER_COMMAND`·`BABOJUBOT_CONTAINER_IMAGE`(기본 `babojubot-runner`)·`BABOJUBOT_MODEL_DESTINATIONS`(JSON 배열, 예 `[{"host":"models.lan","port":8000,"addresses":["10.0.0.5"]}]`)이다. 예전 `BABOJUBOT_CONTAINER_NETWORK`와 전용 bridge 네트워크(`babojubot`)는 쓰지 않는다. 남은 네트워크는 `docker network rm babojubot`으로 지워도 된다.

지원 환경은 Linux Docker Engine이다. Windows에서는 Docker 격리를 지원하지 않는다(2026-11-09 결정). 격리 관문이 Docker를 부르지 않고 `격리 환경 없음`으로 정하므로, 격리를 켜면 실제 연결은 `준비안됨`이고 이 컴퓨터로 대신 돌리지 않는다. 격리를 끈 Windows의 에이전트는 서버와 같은 사용자로 이 컴퓨터에서 돌고 폴더 경계는 지침으로 지킨다. 산출물 파일을 읽는 폴더 고정도 Windows에서는 완전하지 않다. Windows는 작업 폴더를 경로 문자열로 기억하고, Node에는 폴더 핸들 기준으로 여는 기능이 없기 때문이다. Windows 격리를 지원하려면 Go `os.Root`처럼 핸들 기준으로 여는 도구가 먼저 필요하다. Docker Desktop·rootless·다른 컴퓨터의 daemon은 이 컴퓨터에서 확인한 폴더와 중계 소켓이 그대로 컨테이너에 들어간다고 볼 수 없어 안전 확인에서 `준비안됨`(`격리 환경 없음`)이며 이 컴퓨터로 대신 돌리지 않는다. 조직의 제품 폴더는 그 조직에서 같은 연결을 쓰는 에이전트 컨테이너가 함께 읽고 쓴다. 그래서 실행 시도 토큰이 든 파일은 제품 폴더·조직 폴더 밖 실행 시도 전용 폴더에 두고 그 컨테이너에만 읽기로 넣는다. 서버가 강제로 끝나면 남은 컨테이너는 다음 시작 때 지운다. 서버를 root로 띄우면 컨테이너도 root uid로 돈다(권한은 모두 뗀다). 준비 확인(로그인 상태)과 모델 목록은 이 컴퓨터의 프로그램으로 한다.

### 인증 중계

격리 실행의 컨테이너에는 연결의 로그인 원본도, 원본 토큰을 담은 환경 변수도 넣지 않는다(#148, [조사](research/issue-148-references.md)). 프로그램은 실행 시도 하나에 묶인 권한 값을 자기 인증 값으로 받고, 모델 요청을 서버의 인증 중계(조직 도구 경로의 `/api/relay/<연결>`, 컨테이너 안에서는 그 실행 시도의 `tools.sock`으로 이어지는 `http://127.0.0.1:39281`)로 보낸다. 중계는 상류로 보낼 때 실행 시도 신원 header(`x-babojubot-relay-*`)도 뺀다. 중계는 컨테이너 밖에서 다음 순서로 처리한다.

1. 권한 확인: `Authorization: Bearer`·`x-api-key`·`x-goog-api-key`에 실린 값 가운데 이 중계가 발급한 권한을 찾는다(서로 다른 권한 둘이면 401). 발급한 연결·조직·실행 시도의 권한인지, 거두거나 만료(최대 12시간)되지 않았는지 본다. 권한은 서버 메모리에만 있어 서버를 다시 시작하면 모두 사라진다. 요청의 다른 값(조직 ID·Host·계정 header)은 보지 않는다. 다른 연결의 권한, 없는 권한은 401이다.
2. 허용 작업 확인: 연결마다 정한 메서드·경로만 받는다(아래 표). 경로마다 상류 경로와 붙일 인증이 정해져 있고, 원본을 쓰지 않는 경로(OpenCode Zen 무료 모델의 공개 키)는 원본을 읽지 않는다. 그 밖은 403이다. 여기까지 통과해야 원본을 읽는다.
3. 전달: 요청의 인증·쿠키·전달 경로 header와 연결마다 정한 계정 지정 header(Codex `chatgpt-account-id` 등)를 빼고 원본 인증을 붙여 고정 상류로 보낸다. 응답은 stream 그대로 돌려주되 쿠키는 빼고, 다른 곳으로 보내는 응답(3xx)은 따라가지도 넘기지도 않는다(502). 상류에는 압축하지 않은 응답을 요청하고, 그래도 압축해 오거나 응답 header에 붙인 비밀값(원본에서 꺼내 붙인 토큰·키. 계정 ID처럼 비밀이 아닌 값은 빼고)이 그대로 들어 있으면 넘기지 않는다(502). 본문에 그 값이 그대로 나오면 그 앞에서 연결을 끊는다. 원본의 앞부분일 수 있는 끝 조각만 다음 조각까지 잡아 두므로 보통 stream은 늦어지지 않는다. 인코딩하거나 잘라 낸 반향은 막지 못한다.
4. 회수: 실행 시도를 중단하면 그 순간 권한을 거둬 새 요청을 거부하고 진행 중 stream을 끊는다. 실행 시도가 끝나면(완료·실패) 바로 거둔다.
5. 장애: 원본을 읽지 못하거나, 원본을 요청에 넣을 수 없거나(줄바꿈이 낀 값 같은 잘못된 형식), 권한을 확인한 요청을 상류가 401로 거부하면(원본 로그인 거부) 그 연결의 모든 권한을 먼저 거두고(프로그램이 스스로 다시 시도해도 상류에 닿지 않음) 진행 중 실행 시도를 이유와 함께 실패로 끝낸다. 연결은 `준비안됨`(`인증 중계 실패`)이 되고 새 격리 실행을 막는다. 준비 확인은 원본을 다시 읽어 실패할 때와 다른 로그인(붙이는 비밀값이 다른 것)이 읽힐 때만 풀어 준다. 그래서 같은 로그인으로는 풀리지 않고, 사용자가 로그인을 고친 뒤 `다시 확인`하면 풀린다. 실패한 요청을 다시 보내지 않는다.

격리를 켰을 때 연결에 중계가 없거나 기존 구독으로 검증되지 않았으면 `준비안됨`(`격리 실행 미지원`)이고 실행 시도를 시작하지 않는다. 원본을 넘기거나 이 컴퓨터·다른 과금 경로로 대신 돌리지 않는다. 조직 제품 폴더에 로그인 기록(Claude `config/.credentials.json`, Codex `auth.json`, Antigravity 토큰 파일이 보통 파일로 남은 것, OpenCode 조직 DB의 `credential`·`account`·`control_account` 행이나 옛 `auth.json`)이 남아 있으면 그 실행 시도도 시작하지 않는다. OpenCode는 서버를 띄우기 전에 DB를 읽기 전용으로 열어 행 수만 센다. 이 컴퓨터의 실행이 남긴, 연결의 로그인 원본을 가리키는 링크와 이 어댑터가 둔 자리 표시(권한 없는 가짜 로그인)는 괜찮다. 다른 곳을 가리키는 링크와 권한 등으로 확인할 수 없는 경로는 로그인 기록으로 본다.

| 연결 | 중계 | 지원 상태 |
| --- | --- | --- |
| Claude | 공식 gateway 경로: `ANTHROPIC_BASE_URL`=중계, `CLAUDE_CODE_OAUTH_TOKEN`=권한 값. `POST /v1/messages`·`/v1/messages/count_tokens`만 받고 setup-token(access token, 갱신 없음)을 붙인다. `PASS_ENV`로 넘기던 `ANTHROPIC_API_KEY` 같은 변수는 컨테이너에 넣지 않는다 | 미검증(격리 실행 미지원). 실제 CLI 2.1.322 + 합성 권한 + 로컬 모의 상류 수동 확인 한 번([기록](research/issue-148-references.md#합성-검증-결과)) |
| Codex | ChatGPT 로그인을 유지하는 사용자 지정 provider(`requires_openai_auth`)를 `-c`로 주고 `base_url`·`chatgpt_base_url`을 중계로 둔다. 컨테이너에는 권한 값만 든 가짜 `auth.json`(갱신 값·계정 없음)을 실행 시도 전용 폴더에서 조직 폴더의 로그인 자리 위에 읽기로 넣고, 조직 폴더에는 권한 없는 자리 표시만 둔다. `POST /responses`·`GET /models`만 받고 원본의 access token과 계정 ID를 붙인다. 갱신 주소(`CODEX_REFRESH_TOKEN_URL_OVERRIDE`)도 중계의 허용하지 않은 경로라 컨테이너는 갱신하지 못한다 | 미검증(격리 실행 미지원). 실제 CLI 0.167.0 + 합성 로그인 + 실제 중계 + 로컬 모의 상류로 한 턴 확인 |

Go의 OpenAI 계열은 `Authorization`, Anthropic 계열은 `x-api-key`로 연결 DB의 Go 키를 붙인다. Zen 무료 모델은 원본 없이 공개 키만 붙인다. Google 계열 Go 모델은 경로가 없어 실패한다 | 미검증(격리 실행 미지원). 실제 CLI 2.2.6 + 합성 키 + 실제 중계 + 로컬 모의 상류로 확인 |

갱신: Claude setup-token과 OpenCode Go 키는 갱신하지 않는다. Codex·Antigravity는 회전하는 로그인이므로 중계가 원본을 읽을 때 곧 끝나면(Codex: access token 만료 10분 전 또는 마지막 갱신 뒤 약 8일, Antigravity: 만료 10분 전) 이 컴퓨터의 공식 프로그램으로 먼저 갱신한다(Codex `app-server`의 `account/read`+`refreshToken`, Antigravity `agy models`). 프로그램이 연결 폴더의 링크를 따라 원본 자리에 새 로그인을 쓴다. 연결마다 한 번에 하나만 하고 그동안 온 요청은 같은 갱신을 기다린다. 갱신한 뒤에도 끝나 가면 위 5의 장애로 처리한다. 격리를 끈 실행의 프로그램도 같은 원본을 스스로 갱신할 수 있어, 두 쪽이 같은 순간에 갱신하면 하나가 실패할 수 있다(위 표의 동시 갱신과 같은 한계).

격리를 끈 실행은 지금처럼 이 컴퓨터에서 연결의 로그인을 쓴다. 이 보호는 격리 실행에만 해당한다. 컨테이너의 외부 통신은 #149의 중계를 거친다. 네 연결 모두 인증 중계에 붙어 프로바이더로 직접 나가는 목적지를 열지 않으므로, 모델 통신이 인증 중계로만 나간다. Antigravity가 실행 전에 하는 Google 로그인 확인과 사용 기록 전송은 중계로 보낼 수 없어 막히며, `agy acp`에서는 막혀도 실행이 이어진다. 실행 중 받은 권한 값 자체는 그 실행 시도 동안 허용 작업을 할 수 있으므로 민감한 값으로 다룬다.

## 세션과 정리

실행 시도마다 별도 프로세스를 만들고 프로토콜 중단(없는 경우 SIGINT) → 2초 → 프로세스 그룹 TERM → 2초 → KILL 순서로 취소한다. 종료 뒤 남은 그룹도 정리하되, 끝나지 않으면 10초 뒤 포기하고 실행 자리를 돌려주되 기록은 남겨 다음 시작 때 다시 본다. 최종 결과를 받았으면 종료 코드와 상관없이 그 결과를 쓰고, 모르는 출력은 건너뛴다. 재시작 때 연결 폴더(`providers/<연결>/processes`)의 기록으로 잔여 프로세스를 정리한다. 기록은 에이전트가 고칠 수 있는 조직 폴더에 두지 않는다. 기록한 시작 시각과 같은 프로세스만 우리 것으로 본다(Linux는 부팅 식별자도 본다). 시작 시각을 남기기 전에 서버가 죽어 기록에 없으면 건드리지 않는다. Windows는 다른 프로그램이 기록을 열어 둔 동안 덮어쓰기를 거절하므로 시작 시각 저장은 약 5초 동안 다시 시도하고, 끝내 실패하면 경고한다. 끝났음을 확인했을 때만 기록을 지우고, 판단할 수 없으면 건드리지 않은 채 기록을 남기고 경고한 뒤 서버는 시작한다. 깨졌거나 이름과 맞지 않는 기록은 어떤 프로세스도 건드리지 않고 지운다.

실행 시도는 프로그램이 스스로 끝날 때 끝난다. Claude는 첫 턴의 결과를 받으면 입력만 닫는다. Claude는 메인 대화가 띄운 백그라운드 명령(`run_in_background`)이 끝나거나 시간 한도(기본 30분, `timeout`으로 최대 2시간)에 닿을 때까지 열려 있다가 그 결과로 한 턴 더 하고 끝나며([Claude 문서](https://code.claude.com/docs/en/headless.md#background-tasks-at-exit)), 실행 시도는 마지막 턴의 결과로 끝난다. 토큰은 턴마다 더하고 비용은 마지막 결과의 누계를 쓴다. 기다리는 동안 활동에 `백그라운드 작업이 끝나기를 기다립니다.`가 보이고, 끼워 넣기는 받지 않으며, 취소는 위 순서대로 백그라운드 명령까지 끝낸다. Codex·OpenCode·Antigravity는 아직 첫 턴의 끝에서 프로그램을 닫으므로 백그라운드로 남긴 명령은 함께 끝나고, 끝났다고 다시 깨우지 않는다(#125). 작업자 지침은 결과가 필요한 명령의 결과를 같은 실행 시도 안에서 받게 하고, 턴을 끝내면 실행 시도가 끝나는 프로바이더도 있음을 알린다. 열린 백그라운드 작업은 Claude가 바뀔 때마다 내는 살아 있는 백그라운드 작업 목록(`background_tasks_changed`)으로 판단하고, 기다리는 서브에이전트 같은 foreground 일은 세지 않는다. 그 목록에 작업이 남은 채 프로그램이 끝나면(종료 코드와 상관없이) 실행 시도를 실패로 끝내고 세션을 저장하지 않는다. 이미 보고된 턴의 사용량과 로그인 문제 판정은 남긴다. 결과를 한 번도 내지 않고 끝났으면 사용량은 아래처럼 Claude가 남긴 비용 행으로 센다.

MCP bearer는 Claude의 임시 0600 파일, Codex·OpenCode의 자식 환경, Antigravity의 ACP `session/new`(`mcpServers`, 입력으로만 전달)로 넘긴다. 명령 인수에는 넣지 않는다. Antigravity는 더 이상 작업 폴더에 `.agents/mcp_config.json`을 쓰지 않는다(agy 1.5.4는 그 파일을 읽지 않는 것으로 보였다, 합성 확인). 예전 판이 남긴 제품 소유 표시가 있는 파일과 임시 파일만 서버 시작 때 지우며, 표시가 없는 파일은 건드리지 않는다. 실제 모델이 그 도구를 부르는지는 실제 구독으로 확인하지 않았다.

OpenCode는 실행마다 설정 폴더(`OPENCODE_CONFIG_DIR`)의 `plugins/`에 제품 plugin을 써 넣는다. plugin은 공개 도구 API(`ctx.tool.transform`)로 조직 도구의 실행만 바꿔, 원래 실행처럼 권한을 확인한 뒤 호출 신원(세션·assistant 메시지·도구 호출 ID)으로 만든 같은 호출 키를 MCP `params._meta`에 넣어 보낸다. 도구 입력은 바꾸지 않고, 호출 신원이 없으면 보내지 않는다. 조직 도구 연결에는 `babojubot-call-key: required` header를 붙여, plugin이 적용되지 않아 키 없이 온 쓰기를 서버가 효과 없이 거부한다. 2.2.6에서 실제 프로그램과 이 컴퓨터의 가짜 모델로 병렬 호출·다음 메시지 호출의 키가 서로 다르고 입력이 그대로임을 확인했다(#150, `apps/server/test/opencode-real-cli.test.ts`). 근거와 보장 범위는 [#150 조사](research/issue-150-references.md)에 있다.

OpenCode 실행이 실패로 끝나면 2.2.6 실패 이벤트(`session.execution.failed`)의 오류 종류와 HTTP 상태만 읽는다. 요청 거부(`provider.invalid-request`)는 제품이 쓴 요청 거부 안내로, 인증 거부(`provider.auth`)는 인증 거부 안내와 제품 로그인 필요로 끝내고, 그 밖의 종류나 모양이 맞지 않는 값은 일반 실패다. 안내에는 100–599의 정수 상태만 붙인다. 모델 서비스의 원문 메시지·응답 본문은 비밀값이나 연구 내용을 담을 수 있어 옮기지 않는다. 실패한 요청은 다시 보내지 않는다(#147).

이전 세션으로 시작하지 못하면 프로그램의 문구와 상관없이 새 세션으로 한 번 다시 시도한다. 로그인 거절은 세션 문제로 보지 않는다. 끝나지 못한 실행 시도는 세션을 지우지 않는다. 공개 활동은 일반적인 시작·재개 실패 안내만 담고 원시 모델 출력이나 내부 추론을 전달하지 않는다. 관찰 가능한 연구 결과는 조직 도구로 기록한다.

Claude는 프로세스가 끝날 때(취소 포함) 세션의 누적 비용·토큰을 세션 기록에 `cost-state` 행으로 남기고, 재개하면 마지막 행의 값부터 이어서 센다(2.1.317에서 확인). 제품은 이 값을 따로 들고 있지 않고, 실행 시도 전에 같은 세션 기록의 마지막 행을 읽어 기준으로 삼는다. 기준과 Claude가 이어 세기 시작하는 값이 같은 행이므로, 압축이나 앞 실행 시도가 쓴 비용은 다음 실행 시도에 붙지 않는다.

- 취소됐거나 결과 없이 끝난 실행 시도(백그라운드 작업이 남아 실패한 경우 포함)는 Claude가 끝날 때 새로 남긴 행과 기준의 차이를 토큰·비용으로 보인다. 새 행이 없으면(강제 종료 등) 그때까지 받은 결과의 토큰·비용을 보이고, 받은 결과도 없으면 `보고 안 됨`이다. 이때 마지막 결과 뒤에 쓴 비용은 Claude의 누적 값에도 남지 않으므로 다음 실행 시도에 붙지 않고 어디에도 집계되지 않는다.
- 행에 없거나 잘못된 항목은 그 항목만 `보고 안 됨`이다(0으로 채우지 않음).
- 이어 간 세션의 기록이나 그 비용 값을 읽지 못하면 비용을 짐작하지 않고 `보고 안 됨`으로 둔다(토큰은 결과에 있는 값).
- 세션 기록은 실행 시도 전후 한 번씩 끝까지 읽는다(2.7 MB 기록에서 약 20–26 ms).

## Claude 미리 압축

전역 설정의 기존 저장 버튼으로 기준 토큰(기본 400,000, 50,000–1,000,000)과 TTL 비율(기본 90%, 50–95%)을 함께 저장한다. 제품 transcript에서 읽은 마지막 주 세션 입력 크기·시각과 캐시 생성 TTL(확인할 수 없으면 1시간)로 예약한다. 해당 metadata가 없으면 추측해서 예약하지 않는다.

일반 실행이 시작되면 그 세션의 예약은 취소된다. 압축과 일반 실행은 에이전트 단위로 배타다. 그 에이전트의 어느 세션이든 압축 중이면 다른 작업의 일반 실행도 기다리고, 다른 세션의 압축은 앞선 압축이 끝난 뒤 진행한다. 압축은 화면에서 취소할 수 없으므로 15분을 넘으면 중단한다(실측값이 아니라 여유 있게 잡은 값이다). 압축도 연결의 동시 실행 상한을 점유한다. 일시정지 중에는 허용하지만 중단·완료 조직에는 실행하지 않는다. 재시작 때 TTL 안의 지난 예약은 다시 확인하고, TTL이 지난 예약은 버린다. 이미 전송한 압축의 결과가 불명이면 자동 재전송하지 않는다.

압축은 저장한 모델·지침·작업 폴더로 같은 세션을 재개한다. MCP 목록은 동일하게 제공하되 별도 정비 토큰은 모든 도구 호출을 거부한다. 일반 Run·Event·활동을 만들지 않는다. compact boundary와 성공 결과, 동일 세션 ID가 모두 확인되어야 성공이다. 중단 신호 뒤라도 이미 성공이 확인된 압축의 결과는 저장한다.

2026-11-09 실측(Claude Code 2.1.317, Haiku 4.5, 구독 계정)에서 측정한 토큰을 API 단가로 환산하면, 압축한 세션은 압축 요청과 이어 가기를 합쳐 압축하지 않은 비교군보다 37% 쌌다(추정 비용이며 구독 한도 차감은 확인하지 않음). 압축 요청은 앞부분이 평소 요청과 같지만, Claude Code가 마지막 답장 직전의 도구 단계를 캐시 표시 뒤에 두어 그 단계를 캐시 없이 읽는다. 측정 세션은 그 단계가 약 9만 2천 토큰이라 적중이 21%였다. 제품 설정으로 바꿀 수 없는 Claude Code 동작이며, 최악이어도 캐시 만료 뒤 전체를 다시 쓰는 것보다 싸다([조사 기록](research/provider-prompt-caching.md#claude-code-압축-요청은-마지막-도구-단계를-캐시-없이-읽는다127)).

## 수동 실제 시험과 재생 검증

실제 호출을 허용할 때만 다음을 직접 실행한다. 각 실행은 60초 후 취소하며, 격리된 임시 조직에서 `get_run_context` 한 번과 `send_message` 한 줄 OK 답장을 요청한다. Claude는 Haiku, OpenCode는 목록의 무료 모델을 쓰며, Codex·Antigravity는 사용자가 현재 계정에서 가장 저렴한 `BABOJUBOT_SMOKE_MODEL`을 지정해야 한다. 모델 자체가 요청을 어떻게 수행할지는 프로바이더 동작에 따른다. 이 스크립트는 CI에서 실행하지 않는다.

```bash
BABOJUBOT_HOME="$product_root" node scripts/provider-smoke.mjs claude --allow-live
# codex, opencode, antigravity도 같은 위치 인수로 선택
# BABOJUBOT_CODEX_MODE=exec 선택; Codex·Antigravity는 BABOJUBOT_SMOKE_MODEL=<가장 저렴한 모델 ID> 지정
```

이 시험은 단건 연결 확인이다. 백그라운드 명령(45초)·세션 재개·끼워 넣기·취소·세션 실패·압축까지 돌리는 시험은 같은 조건으로 `node scripts/provider-live.mjs <연결> --allow-live`이고, `--record`를 붙이면 원본을 Git 밖에 남긴다. 현재 자동 검사는 `packages/runtime/test-fixtures`의 **합성** CLI/HTTP/SSE peer를 쓴다. 실제 녹화로 표현하지 않는다. 재생 형식과 정제 기준은 [fixture 안내](../packages/runtime/test-fixtures/README.md)를 따른다.

## 실모델 장애 검사

실제 OpenCode 실행에서 취소·서버 강제 종료·동시 실행 상한·끼워 넣기·세션 재개가 제품 불변 조건을 지키는지 반복해 본다. 실제 호출을 허용할 때만 사람이 실행하고, CI에서는 `--allow-live`가 있어도 거부한다. 기록 결과는 [#154 검증 기록](research/issue-154-chaos-verification.md)에 있다.

```bash
node scripts/chaos-live.mjs --allow-live                 # 모든 장면
node scripts/chaos-live.mjs --allow-live --scenes=a,b    # 고른 장면만
```

| 장면 | 확인하는 것 |
| --- | --- |
| a 실행 중 취소 | 취소된 실행의 토큰 거절, 프로세스 정리 뒤에야 다음 실행 시작, 받은 입력을 다시 주지 않음 |
| d 조직 간 동시 실행 제한 | 상한 2에서 세 조직이 요청해도 실행 중 2개 이하, 상한까지 찬 동안 온 요청은 자리가 난 뒤 시작(상한까지 차지 않았으면 미실행) |
| e 실행 중 메시지 전달 | 수락은 그 실행에만(추가 실행 없음), 실제 거절·주입한 거절은 다음 실행으로 |
| f 세션 재개와 설정 변경 | 같은 연결·지침에서 재개, 가짜 연결로 바꿨다 돌아오면 새 세션. 모델만 바꾸는 검사는 가짜 연결에서만 한다 |
| b 서버 강제 종료 후 복구 | 서버 SIGKILL 뒤 같은 홈·DB로 재시작, 이전 실행 한 번만 `server_restart`, 깨우기 한 번 재대기, 이전 프로세스 정리 |
| c 재시작 전후 같은 호출 키 | 재시작 뒤 새 실행 토큰으로 같은 호출은 첫 결과(효과·Event·깨우기 추가 없음), 다른 입력·도구는 409, 이전 토큰은 거절 |
| g(선택) 끼워 넣기 중·수락 직후 서버 강제 종료 | 복구 뒤 실행이 메시지를 받음. 노린 순간(수락 직후·결과가 정해지기 전)에 끝내지 못했으면 미실행 |

순서는 기본 검사 → 서버 강제 종료 검사 → 선택 검사이며, 장면마다 새 임시 제품 홈과 서버 자식 프로세스(루프백, 자동 배정 포트)를 쓴다. 일반 장면은 임시 DB, 재시작 장면은 그 홈 아래 일회용 내장 DB다. 조직 생성 깨우기는 가짜 연결로 처리하고 heartbeat를 끈 뒤 Lead를 OpenCode로 바꾼다. 모델은 제품의 무료 모델 선택만 쓴다. 고른 모델이 무료인지 확인할 수 없어 모델을 지정하는 설정은 받지 않는다(`BABOJUBOT_CHAOS_MODEL`·`BABOJUBOT_CHAOS_ALT_MODEL`이 있으면 시작하지 않는다). 서버 안의 실행 관문은 실제 실행마다 OpenCode 준비 확인으로 무료 모델이 있는지 보고(준비됨 결과는 60초 동안 다시 쓴다), 없으면 그 실행을 띄우지 않는다. 무료 모델은 로그인 없이 쓰므로 로그인이 필요한 모델은 지원하지 않는다.

검사와 서버 자식 프로세스는 PATH와 네트워크·인증서·언어·임시 폴더 변수만 이어받는다. `BABOJUBOT_<연결>_PASS_ENV`·`_COMMAND` 같은 제품 설정, API 키, 외부 DB 주소는 넘기지 않으므로 사용자 OpenCode 설정·자격 증명이 실행에 쓰이지 않는다.

- 한도: 실제 실행 전체 `BABOJUBOT_CHAOS_MAX_LIVE_RUNS`(1–24, 기본 24), 장면당 d 10회·나머지 4회, 전체 35분(실제 호출 전 확인 포함, 마지막 정리 몫 90초를 남기고 장면을 멈춘다. 서버 시작 대기도 멈춘다. 넘으면 결과에 초과 시간을 남기고 전체를 실패로 둔다), 장면당 480초, 시험용 긴 명령 90초 이하. 서버 안의 실행 관문이 실제 프로그램을 띄우기 전에 세고, 넘으면 띄우지 않고 그 장면을 멈춘다. 복구·재시도로 시작한 실행도 센다. 입력 토큰 20만은 권고 기준으로 결과에 초과 여부만 남긴다.
- 실행 시도 토큰: 서버 프로세스가 실행 동안만 0600 임시 파일로 둔다(재시작 장면의 같은 호출 키 재생에 쓴다). 사용자 API에 토큰을 꺼내는 경로는 없다.
- 결과: 저장소의 Git 제외 작업 폴더 아래 `chaos/<시각>/results.json`(0600). 실행이 끝나면 경로를 출력한다. 장면·검사마다 통과·실패·미실행과 이유, 출처(`live` 실제 OpenCode·`fake` 가짜 연결·`injected` 거절 주입), Event 종류·개수·상태·소요 시간·실행 수·토큰 수만 남긴다. 쓰기 전에 메시지 본문·토큰·DB 주소 같은 비밀값과 원문 필드를 검사하고, 섞였으면 가린 뒤 전체를 실패로 둔다.
- 종료 코드: 모두 통과 0, 실패 1, 미실행이 있음 3, 입력값·허용 거절 2, 사용자 중단(Ctrl-C) 130. 성공·실패·시간 초과·중단 모두 서버·내장 DB·남은 프로바이더 프로세스·임시 홈을 정리하고, 정리가 끝나지 않으면 그 장면은 실패다. 제품 복구가 우리 것인지 확인하지 못한 프로세스 기록이 남으면 그 홈은 지우지 않고 경로를 터미널에 알린다(사람이 정리). 서버 시작 실패 때 서버 출력은 터미널에만 보이고 결과에는 남기지 않는다.

검사 결과의 미실행은 모델이 지시를 따르지 않았거나 예산·시간이 모자라 확인하지 못한 경우다. 제품이 해야 할 일(기다리는 깨우기로 실행 시작, 복구된 메시지 전달 등)이 시간 안에 일어나지 않으면 실패다.

자동 검사(`apps/server/test/chaos-harness.test.mjs`)는 같은 실행기를 가짜 연결로 돌려 허용 차단·예산·판정·증거 검사와 강제 종료·시간 초과·중단 뒤 정리를 본다. 실제 모델은 부르지 않는다.
