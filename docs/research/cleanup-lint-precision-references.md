# 예외 경로에서 정리가 건너뛰어지는 시험의 정적 분석

[#243](https://github.com/babo-jeonguk/BaboJUBot/issues/243)과 [PR #248](https://github.com/babo-jeonguk/BaboJUBot/pull/248)의 시험용 정리 규칙을 검토한다. 본문 오류 보존과 러너별 정리 동작은 [정리 실패 조사](cleanup-failure-masking-references.md), 제품 코드 적용 범위는 [정적 분석 조사 D02](static-analysis-rules-references.md#D02)를 따른다.

조사일은 2026-11-19다. 비교 기준은 PR 커밋 `a8d3a052435f818a1000072edff88b817999cf37`과 작업 브랜치의 `933f28f691be0476318464bf930cb6e60651a3a1`이다. 아래 내용은 구현 전 권고다.

## 결론

- **공용 정리 훅에서 같은 `try`의 연속 정리와 루프 전체를 감싸는 `catch`를 먼저 검사한다.** 앞 정리 A의 거절로 제어가 `catch`로 옮겨가면 B는 시작하지 않는다. A의 오류를 보관하는 것과 B를 시도하는 것은 각각 검사할 수 있다.
- **이름 확장보다 출처를 확인한다.** 훅·프로세스 API는 import 및 스코프로 확인한다. `new Promise(resolve => server.close(resolve))`는 오류 전달 계약이 확인된 Node 서버에 한해 별도 메시지로 잡을 가치가 있다. 최신 PR에서 해당 구문은 9곳이며 두 곳은 같은 `afterEach`의 반복문 안이다.
- **두 규칙과 정확히 같은 공개 규칙은 조사 범위에서 발견하지 못했다.** CodeQL C#과 SpotBugs OBL은 실패가 후속 해제를 건너뛰는 경로에 가깝다. Unicorn은 JavaScript 정리 예외가 앞 오류를 가리는 경우를 다룬다. CodeQL Go는 정리 호출에서 버린 오류를 찾는다. 이들 규칙의 입력은 각각 자원 획득·해제, 수동 `finally`, 파일 API이며, 시험 러너와 `process.kill`의 ESRCH 정책은 저장소가 모델링해야 한다.

**E01 · 소스 확인.** `no-skipped-cleanup`은 훅 이름과 인라인 블록을 인식한다. 알려진 이름의 직접 `await` 뒤에 다른 `await`가 나오거나 반복문에 있으면 훅당 한 번 보고한다. 뒤에 `removeFolder`만 이어지는 경우에는 예외를 둔다. AST 순회 순서로 뒤 호출을 결정하므로 서로 배타적인 분기까지 이어진 것처럼 볼 수 있다. `scope`는 검사 중인 앞 `await`가 `catch`를 가진 `try` 본문에 있으면 제외하므로 아래 반례가 빠진다. `no-ignored-kill-error`는 문자 그대로 `process.kill`을 찾고 catch 매개변수 참조 수를 본다. `console.warn(e); return false`도 참조가 있으므로 통과한다. 내부 함수에는 들어가지 않지만 내부 `try`에서 처리된 호출은 바깥 `try`의 검색에도 포함될 수 있다. [두 규칙 구현](https://github.com/babo-jeonguk/BaboJUBot/blob/a8d3a052435f818a1000072edff88b817999cf37/scripts/eslint-test-rules.mjs#L535-L750) · [기존 회귀 시험](https://github.com/babo-jeonguk/BaboJUBot/blob/a8d3a052435f818a1000072edff88b817999cf37/scripts/lint-rules.test.mjs#L556-L680)

```js
afterAll(async () => {
  try {
    await server.close();
    await model.close();
  } catch (error) {
    failures.push(error);
  }
});
```

여기서 검사할 사실은 `server.close()` 거절 시 `model.close()`에 도달하는지다. 두 호출이 각각 보호되면 첫 거절에서 다음 시도로 진행할 수 있다. 각 반복 안에서 실패를 모으고 다음 반복으로 진행하는 경우도 같다. 정리 시도가 실제로 자원을 닫았는지, 모은 오류가 마지막에 보고되는지는 별도 실행 계약이다. `await a.close().catch(collect)`는 반환 Promise의 거절을 받을 수 있지만, `a.close()`가 Promise 반환 전에 동기로 던지면 그 처리기는 등록되지 않는다.

**E20 · 실행 확인.** 별도 임시 설치에서 ESLint 10.12.0과 Unicorn 80.0.0을 타입 없이 실행했다. `prefer-dispose`는 인접한 직접·await close와 획득 역순의 close를 제안으로 보고했다. 획득 순서대로 닫기, 매개변수를 닫기, 중간 문장·가드·부가 로그·인수가 있는 close는 대조 입력에서 통과했다. `no-async-promise-finally`는 async 콜백 내부에 catch가 있어도 보고하고, 일반 화살표가 정리 Promise를 반환하는 경우에는 통과했다. 타입 지정 입력에서 `.close()`와 `[Symbol.dispose]()`가 서로 다른 구현이어도 `prefer-dispose`는 전환을 제안했다. Node에서 원본과 제안을 각각 실행하자 호출한 메서드가 바뀌었다. 리소스 관리 프로토콜의 존재는 기존 메서드와의 동치성을 보장하지 않는다.

## 한계와 미확인

- 조회한 공개 소스, 고정 버전 문서와 업스트림 시험 기대값이 외부 분석기의 근거다. E20의 Unicorn 비교 외에는 외부 분석기 실행, 전체 시험 실행 및 OS별 종료 경로 실행을 하지 않았다.
- 전수 수치는 AST 프로브가 지원하는 직접 구문에 한정한다. 프로브는 계산된 멤버, 동적 import, 구조 분해 별칭, 래퍼가 반환하는 함수, 이름이 재정의된 훅, 파일을 넘는 factory 소유권 및 helper 안의 경로를 일반화하지 않는다. `kill`은 단순 import·전역과 상수 멤버에 한정했고 가장 가까운 catch를 단순 후보로 셌다.
- typed lint의 전체 적용 시 진단 수와 실행 시간, 사용자 정의 CFG의 비용은 미측정이다. 타입을 붙여도 안전한 자원 순서와 예외의 허용 정책은 지원 함수 및 실행 사례에서 확인해야 한다.
