# 시험의 원래 실패와 정리 실패를 함께 보고하는 방법

이 문서는 시험 본문과 정리가 함께 실패할 때 각 러너가 무엇을 보여 주는지, 여러 정리를 어떻게 이어서 실행하는지 비교한다. 저장소의 시험 작성 규칙은 [코드 작성 기준](../../CODING_STANDARDS.md#정리)에 있다.

조사일 2026-11-18. 저장소 기준 커밋 `d2cb3048321b1ae4f5ff2f0b8892858808139081`. 조사 판은 Vitest 5.0.5, Playwright 1.65.1, Node.js 24.21.0, TypeScript 6.0.3, Vite 8.3.4다. 아래에서 실행 결과와 고정 소스에서 읽은 동작을 구분한다. ## 결론 요약

- **여러 프로젝트에서 자원을 얻은 직후 정리를 등록한다.** Go와 pytest는 등록 역순으로 정리를 이어 가고, JUnit은 본문 오류와 정리 오류를 함께 남긴다. 정리 순서와 출력 형식은 각 러너의 계약에 따른다. VS Code는 lint로 정리 도우미 등록을 확인한다. [다른 프로젝트의 시험 정리 관행](#다른-프로젝트의-시험-정리-관행)
- **시험 한 건이 직접 만든 자원은 정리를 러너에 바로 등록한다.** Vitest에서는 시험 컨텍스트의 `onTestFinished`에 독립 정리를 하나씩 등록하면, 본문이 실패해도 등록 역순으로 모두 시도하고 각 오류를 기록한다. Playwright에서는 수명을 재사용하는 자원을 시험 범위 fixture에서 열고 `await use()` 뒤에 정리한다. 시한이 남아 있으면 한 fixture가 실패해도 의존 순서에 따라 다음 fixture 정리를 시도하고 오류를 쌓는다. [Vitest 훅 설명](https://github.com/vitest-dev/vitest/blob/7a825db43e2beca0b219d2eadaec334cb81af0c7/docs/api/hooks.md#L372-L446) · [Playwright fixture 실행 순서](https://github.com/microsoft/playwright/blob/bbd948344ea9a60bf1e6f125c02ca99b2b51593b/docs/src/test-fixtures-js.md#L632-L642)
- **러너와 무관한 시험 지원 함수와 `node:test`에서는 오류를 직접 모은다.** 본문이나 준비에서 던진 값은 보관하고, `finally`에서 각각의 정리를 시한 안에서 기다리며 실패를 모은다. 본문만 실패하면 그 값을 다시 던지고, 둘 다 실패하면 `AggregateError`의 `errors`에 원래 실패를 첫 항목으로, 정리 실패를 뒤에 두고 `cause`에도 원래 값을 연결할 수 있다. 정리만 실패해도 시험은 실패해야 한다. `node:test`의 `t.after`와 `afterEach`만으로는 두 오류를 모두 보고할 수 없다. 일부 출력은 배열을 펼치지 않으므로 최상위 메시지에도 실패한 단계가 드러나게 한다. [서버 시작 실패 처리](../../apps/server/test/support.ts#L198) · [Node의 오류 선택](https://github.com/nodejs/node/blob/955266bfdd854cd280dffd47548673914484e4c0/lib/internal/test_runner/test.js#L1426-L1444)
- **lint는 시험 코드와 시험 지원 코드에서 범위를 좁혀 시작한다.** `finally`에서 곧바로 부르는 알려진 정리 호출을 한 개여도 검사한다. 같은 블록에 이어진 여러 정리는 뒤 작업이 건너뛰어질 수 있으므로 함께 살핀다. `clearTimeout(timer)` 같은 단순 해제까지 막으면 손볼 곳이 불필요하게 늘어난다. [현재 시험 lint 범위](../../eslint.config.js) · [ESLint 구문 선택자](https://github.com/eslint/eslint/blob/a438ec39512c3381f4785a1f3058982ce9845970/docs/src/rules/no-restricted-syntax.md#L12-L29)

현재 `startTestServer`의 시작 실패 처리는 오류를 모으며, 서버 종료를 확인하지 못하면 그 서버의 폴더를 남긴 이유도 기록한다. 반환된 `close()`는 소켓, 서버, DB, 자체 폴더 순서로 진행해 앞 단계가 실패하면 뒤 단계에 닿지 않는다. `createTestDatabase().close()`는 `finally`에서 DB 삭제를 시도하므로 연결 닫기가 실패해도 삭제까지 가지만, 삭제도 실패하면 연결 오류가 가려진다. 독립 단계는 앞 실패 뒤에도 시도하고, 실행 중인 서버가 쓰는 폴더 삭제처럼 선행 조건이 있는 단계는 그 조건을 확인한 뒤 실행하는 것이 맞다. [서버 시험 지원 코드](../../apps/server/test/support.ts#L317) · [DB 시험 지원 코드](../../packages/db/src/testing.ts#L85)

### 언어 기능과 변환기

Explicit Resource Management(ERM)는 TC39의 최종 채택 단계인 Stage 4에 도달했고 ECMAScript 2027 초안에 들어 있다. [TC39 채택 목록](https://github.com/tc39/proposals/blob/c688b97e056142da3c05a9b7552f14cc77d0ff94/finished-proposals.md#L3-L11) · [ECMAScript 초안](https://tc39.es/ecma262/#sec-disposeresources)

- JavaScript의 `finally`는 본문이 던진 뒤에도 실행되지만, 거기서 다시 던지면 `finally`의 예외가 남는다. 거절된 Promise를 `await`하는 경우도 같다. ERM은 정상 종료와 예외 종료 양쪽에서 `Symbol.dispose` 또는 `Symbol.asyncDispose`로 등록한 자원을 정리한다. 비동기 정리는 `Symbol.asyncDispose`로 등록하고 `await using`으로 기다린다. 두 정리 B, A가 역순으로 모두 실패하면 가장 바깥 `error`는 마지막 정리 A의 오류, `suppressed`는 앞서 만들어진 B의 오류와 본문 오류의 묶음이다. `error`와 `suppressed`는 기본 열거 대상에서 빠진다. [`try`의 실행 규칙](https://github.com/tc39/ecma262/blob/b1eaed82fc5e8a511c5b2007f194b16c8f7e5ea6/spec.html#L23492-L23506) · [정리 알고리즘](https://github.com/tc39/ecma262/blob/b1eaed82fc5e8a511c5b2007f194b16c8f7e5ea6/spec.html#L7242-L7285) · [`SuppressedError` 생성 규칙](https://github.com/tc39/ecma262/blob/b1eaed82fc5e8a511c5b2007f194b16c8f7e5ea6/spec.html#L32474-L32485)
- 기존 `close()`는 `DisposableStack` 또는 `AsyncDisposableStack`의 `defer`로 등록할 수 있다. 스택에 직접 `dispose()`를 부르면 스택 안의 정리 실패만 모인다. 본문까지 보존하려면 스택을 `using` 또는 `await using`으로 선언해 범위를 나갈 때 정리한다. [동기 스택](https://github.com/tc39/proposal-explicit-resource-management/blob/38c13295dc20c2273ba0a6ed82555f1fabb37764/spec.emu#L4552-L4561) · [비동기 스택](https://github.com/tc39/proposal-explicit-resource-management/blob/38c13295dc20c2273ba0a6ed82555f1fabb37764/spec.emu#L4746-L4763)
- Node.js는 24.0.0부터 별도 V8 플래그 없이 지원한다. TypeScript는 5.2부터 구문과 타입을 지원하고 낮은 출력 목표에 맞춰 변환할 수 있다. 이 저장소의 ES2023 설정과 설치된 Node 타입을 사용한 소형 TypeScript 6.0.3 타입 검사도 통과했다. ### 정리 규칙을 어디서 강제하는가

VS Code는 지정한 시험 파일에서 최상위 `suite`가 누수 확인 도우미를 호출하는지 lint로 확인한다. Node의 시험 lint는 `assert.rejects()`를 기다리지 않아 단언 결과를 놓치는 모양 등을 검사한다. pytest 저장소에서 활성화한 Ruff `B012`는 `finally` 안의 `return`, `break`, `continue`를 잡는다. 이 규칙들은 정리 함수 내부에서 예외가 나거나 앞 정리 실패로 뒤 정리가 빠지는지 판정하지 않는다. 조사한 공개 설정에서 그 경우까지 일반적으로 막는 규칙을 확인하지 못했다. 두 오류가 남는 동작은 위의 러너 구현과 회귀 시험에서 확인했다. 프로젝트의 리뷰 관행 전체는 이 자료로 확인할 수 없다. ### 동기 정리 호출

- `process.kill()`은 동기 호출이다. Node 자체 시험은 이미 끝난 자식에 신호를 보내면 `ESRCH`를 던지는지 확인한다. 정리의 목표가 대상이 사라지는 것이라면 `ESRCH`만 정상으로 처리할 수 있다. 존재 확인과 신호 전송 사이에도 대상이 끝날 수 있으므로 호출을 감싸서 판정한다. 이 저장소의 `signalGroup`도 `ESRCH`만 넘기고 나머지 오류는 다시 던진다. [Node의 `ESRCH` 시험](https://github.com/nodejs/node/blob/955266bfdd854cd280dffd47548673914484e4c0/test/parallel/test-child-process-detached.js#L28-L43) · [저장소의 `signalGroup`](../../scripts/boot-check.test.mjs#L443)
- Node의 공용 임시 폴더 도우미는 프로세스 종료 때 `fs.rmSync`를 호출하고 실패하면 정리 경로와 남은 파일을 출력한다. `force: true`는 경로가 이미 없는 경우를 허용하며 권한 오류 등을 모두 무시하는 옵션은 아니다. `recursive: true`와 한정된 `maxRetries`를 함께 쓰는 것도 Node 도우미에서 확인했다. 이 저장소에서 폴더를 지울 때는 기존 `removeFolder` 규칙과 선행 종료 확인을 적용한다. [Node 임시 폴더 도우미](https://github.com/nodejs/node/blob/955266bfdd854cd280dffd47548673914484e4c0/test/common/tmpdir.js#L22-L81) · [Node `fs.rmSync` 옵션](https://github.com/nodejs/node/blob/955266bfdd854cd280dffd47548673914484e4c0/doc/api/fs.md#L6869-L6885) · [저장소 정리 기준](../../CODING_STANDARDS.md#정리)
- 정리 호출을 검사할 때는 알려진 동기 호출에도 같은 기준을 적용한다. `finally`의 `process.kill()`이나 `rmSync()`는 `await`가 없어도 앞 오류를 가릴 수 있다. 정리를 하나씩 실행하는 지원 함수 안에서 호출과 대기를 모두 `try…catch`로 감싸면 동기 예외와 Promise 거절을 같은 경로에서 모을 수 있다. 시험의 준비나 본문에서 같은 이름의 함수를 호출하는 경우까지 막으면 검사 범위가 불필요하게 넓어진다.

이 절은 고정 판의 소스, 회귀 시험, 공개 lint 설정을 읽어 비교했다. 여기에 추가한 프로젝트의 시험은 별도로 실행하지 않았다.

첫 적용에서는 알려진 서버·DB `close()`와 `removeFolder()`가 `finally`에서 오류를 그대로 내보내는 모양을 잡는다. 같은 본문에서 여러 정리를 차례로 기다리는 모양은 뒤 정리 누락 가능성도 드러낸다. 검사 예로 한 호출, 두 호출, `if` 안의 호출, `try…catch`로 오류를 모으는 호출, `clearTimeout`을 둘 수 있다. 메서드 이름만 같다고 해서 같은 자원은 아니므로 가능한 곳은 import나 알려진 지원 함수의 반환값에 연결한다. 함수가 어디에서 동기 예외를 던지거나 Promise를 거절하는지, 잡은 오류가 실제 보고까지 이어지는지, 선행 조건이 필요한지는 문법만으로 보장하기 어렵다. 실패를 삼키는 빈 `catch`를 고치는 방법으로 안내하면 정리 실패가 사라지므로 오류를 모으거나 러너에 별도 정리를 등록하도록 안내한다.

## 조사 범위와 미확인

- **실행 확인.** 저장소 밖 작은 시험에서 본문과 정리를 일부러 실패시켰다. Vitest의 `onTestFinished` 두 개는 역순으로 모두 실행됐고 본문·정리·`onTestFailed`의 오류가 각각 남았다. `onTestFinished`만 실패해도 `onTestFailed`가 호출됐다. 본문이 실행 중 `skip()`을 부른 별도 재현에서는 이미 등록된 `onTestFinished`가 실행됐지만 그 오류는 JSON에 남지 않았고 결과는 건너뜀으로 기록됐다. 기본 `afterEach` 두 개는 마지막에 등록한 훅의 실패 뒤 앞 훅에 닿지 않았다. 의존 fixture 두 개에서는 앞서 닫는 fixture의 오류가 JSON에 두 번 기록됐고 나머지 fixture는 정리되지 않았다. Playwright JSON에는 본문과 정리 두 건이 모두 남았다. Node `spec`과 `tap`은 본문과 훅이 함께 실패하면 본문 오류만 보여 줬고, 훅만 실패한 시험은 훅 오류로 실패했다.
- **출력 확인.** 직접 묶은 `AggregateError`의 본문·정리 오류는 Vitest 기본 출력, Playwright JSON, Node `spec`에서 확인했다. Node `tap`에서는 최상위 메시지만 보였다. `SuppressedError`는 Vitest의 자세한 텍스트 출력에서 안쪽 필드로 보였고, Vitest와 Playwright의 JSON 오류 메시지 및 Node `spec`에서는 안쪽 오류가 별도 실패 메시지로 나오지 않았다. 시험 한 건의 데이터 구조에 남는 것과 사람이 읽는 실패 요약에 나오는 것은 출력 방식에 따라 다르다.
- **미확인.** 위 오픈소스 시험은 원문을 읽었다. 저장소의 전체 시험, 브라우저를 띄우는 E2E, Windows·macOS의 실제 자원 정리, 모든 재시도·취소·강제 종료 경로와 보고 형식은 조사 실행에 포함하지 않았다. 시한 만료 뒤 정리 대상이 실제로 멈췄는지는 별도 확인이 필요한 영역이다.
