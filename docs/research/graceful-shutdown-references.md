# graceful-shutdown 레퍼런스 조사: Node 서버의 종료 신호 소유권

조사일: 2026-11-05. 대상: 사용자 조사 의뢰 Q1–Q4. 구현 전 기술 권고이며 확정 계약이나 구현 결과가 아니다. 상세 후보·원문·재확인 기록: `.reference-cache/graceful-shutdown/`(기존 `.gitignore`의 무시 대상).

## Brief

- 해결할 문제: 의존성의 import 부작용이 앱의 종료 순서를 가로채는 상황에서, 실행 시도·실제 CLI 프로세스·최종 DB 기록·DB의 수명을 조정한다. 사용자가 제공한 현상·측정·로컬 호출 순서는 전제로 사용하며 재현·재진단하지 않았다.
- 동종 문제: 여러 자원 제공자가 하나의 프로세스 종료를 독립적으로 실행하여, 소비자가 끝나기 전에 의존 자원이 사라지는 수명 충돌.
- 고정된 결정: 조사만 수행한다. 제품 코드·테스트·설정·git을 변경하지 않는다. 조직 경계와 초기 승인·최종 완료 불변 조건도 변경 제안의 대상이 아니다. 공개 자료만 사용하고 모델·실제 연구 데이터·DB를 실행하지 않는다.
- 핵심 판단: **정상 종료의 조정자는 앱 하나여야 한다. 현재는 hook 등록 자체를 막는 버전 고정 패치가 가장 검토하기 쉬운 해법이다. 다만 패치만으로 비정상 종료·Windows·Ctrl+C까지 해결됐다고 판정할 수는 없다.** 아래 사실과 이 판단을 분리했다.

Q1의 결론은 **강제된 Node 규약과 설계 권고를 구분**해야 한다는 것이다. 유명 라이브러리의 공식 지침으로 Nest는 shutdown listener를 기본 비활성화하고 앱이 enableShutdownHooks로 켜도록 설명한다([공식 lifecycle 가이드](https://docs.nestjs.com/fundamentals/lifecycle-events), 문서 주장). 라이브러리 작성자 전체를 구속하는 단일 신호 소유권 규범은 이번 조사에서 찾지 못했다. Node는 라이브러리의 handler 설치를 금지하지 않는다. 그러나 반환 Promise를 기다려 주지 않는 계약(E02), 앱 정리 지침(E03), 실제 충돌·수정(E04–E08), 아래 명시적 활성화 API를 합치면, 프로세스 종료 결정은 앱에 두고 라이브러리는 명시적 close와 선택 가능한 안전장치를 제공하는 편이 조합 가능하다는 권고가 나온다(추론). `removeListener`로 **자기가 설치한 참조**를 제거하는 것과 제3자의 내부 closure를 찾아 제거하는 것은 다르다.

## 구현 참고 — 단일 권고안

**버전을 고정한 pnpm patch로 embedded-postgres의 import 종료 hook 등록을 제거하고, 앱 최상위 coordinator가 정상 종료를 단독 소유한다. DB adapter에는 명시적 close와 동기 emergency stop만 남긴다.** 단순 listener 제거 대신 패치를 선택하는 이유는 외부 DB까지 영향받는 등록 지점을 명확하게 제거하고, 갱신 실패를 설치·검증에서 드러낼 수 있기 때문이다(P01–P04/E06–E09/E30). 다음은 구현할 때의 구체적 설계이며 이번 조사에서는 적용하지 않았다.

1. **소유권과 patch.** `embedded-postgres@18.6.0-beta.19`의 실제 배포 진입점 `dist/index.js`에서 module-level `asyncExitHook(gracefulShutdown, {wait:5000})` 호출을 삭제하는 exact-version pnpm patch를 둔다. callback만 비우거나 disposer를 호출하는 패치로 대체하지 않는다. 다른 의존성의 exit-hook까지 전역 patch하지 않는다. upstream opt-out이 배포되면 이 패치를 공개 옵션으로 대체하되 import 무부작용 검증을 통과시킨다. 패치는 `patches/`에 두고 `pnpm-workspace.yaml`/lockfile의 exact patched dependency로 연결하는 **후속 구현 변경**이다. `allowUnusedPatches=false`, `ignorePatchFailures=false`로 적용 누락을 실패시킨다(E07/E30).
2. **최상위 coordinator.** `apps/server/src/main.ts`의 `stopping` 신호 루프를 단일 `shutdown(reason): Promise`로 바꿀 것을 권고한다. SIGINT/SIGTERM/SIGHUP과, 사용하는 경우 pm2 `'shutdown'` IPC를 여기서만 정상 종료로 변환한다. `packages/db`가 SIGHUP에서 독자적으로 DB를 닫고 exit하는 동작은 제거한다. 시작 실패·부분 초기화·init 중 신호도 같은 소유 자원을 정리하고, 중단 요청 뒤 새 서버 기동으로 진행하지 않게 한다. 단순 bool 대신 동일 Promise를 공유하여 명시적 close와 신호가 겹쳐도 정리 1회를 보장한다(E10/E14/E25).
3. **정상 순서.** `apps/server/src/app.ts`의 `startServer` 안 `stop`에서 먼저 stopping/readiness 상태를 내리고 신규 HTTP 명령·WebSocket upgrade·채널 입력·작업 admission을 차단한다. HTTP `server.close()`를 시작해 진행 요청을 drain하되, 요청이 쓰는 dispatcher/서비스/DB는 유지한다. 이미 수락한 요청이 새 작업을 늦게 넣을 수 없다는 경계를 확인한 뒤 기존 내부 순서인 새 깨우기 중지 → compaction → readiness 작업 → dispatcher(실제 CLI 프로세스 회수·실행 시도 종료 저장) → notifications → channel을 유지한다. WS는 정상 close에 유한 시간을 주고 잔류만 terminate한다. HTTP/WS 및 모든 DB 사용 작업의 완료 후에만 main이 `handle.close()`를 호출한다. DB handle은 pool.end → 자신이 띄운 cluster 정지 순서다. 외부 DB는 pool만 닫으며 서버 자체는 정지시키지 않는다. 각 단계의 실패는 모아서 보고하고 나머지 정리를 시도하며, main의 DB close는 finally 경로에 둔다. 실패가 있었다면 정상 종료 코드로 덮지 않는다. **closeAllConnections는 정상 drain 대신 항상 호출하지 말고**, 만료 때 server.close 뒤 사용한다. Node는 upgrade된 WS를 자동으로 닫지 않으므로 별도 회수가 필요하다(E03/E11/E25 및 아래 HTTP 계약).
4. **전체 시한과 코드.** 최초 요청 시점부터 기본 **30초 절대 예산**을 제안한다(산정 측정 전의 설계값). 정상 정리에 최대 25초, 마지막 5초는 실행자 취소/강제 회수와 DB emergency stop에 남긴다. 단계 timer를 각각 30초씩 더하지 않는다. 25초 경계에서 emergency 회수를 먼저 요청하고, 30초 watchdog의 최종 callback은 추가 async await·동기 stop 재대기 없이 최소 동기 진단 후 exit(1)한다. emergency 전달은 중복 방지하고 동기 fallback 비용도 마지막 5초에 포함한다. 정상 INT/TERM/명시 stop은 모든 close와 로그 flush 뒤 `process.exitCode=0`으로 자연 종료, SIGHUP 성공은 129, 정리 실패/fatal/시한 초과는 1로 제안한다. 두 번째 신호는 emergency stop 후 128+signal로 즉시 종료한다. 이 코드 정책은 생태계 단일 표준이 아니라 선택한 앱 정책이다. 정상 완료 후 watchdog은 unref하되 남은 handle이 있으면 절대 만료를 계속 감시한다. Windows 콘솔 HUP는 약 10초 제한 때문에 **8초 이내 예산**으로 줄이고, 완전한 drain을 보장하지 않는다(E01/E14/E21–E24/E32).
5. **비정상 종료 대비.** `packages/db/src/client.ts`의 `startEmbeddedCluster`/`startCluster`/`connect`와 `DatabaseHandle.close`에서 graceful stop을 멱등화하고, 소유 child가 이미 죽었으면 미래 exit를 기다리지 않게 한다. 기존 `exit` listener의 `void cluster.stop()`는 첫 동기 구간의 신호 전달만 기대하는 best effort임을 명시한다. 이를 **Promise 없는 emergencyStopSync**로 분리한다. POSIX에서는 보유 중인 child 참조에 SIGINT를 동기 전달하고, Windows에서는 소유 PID의 tree에 `spawnSync(taskkill, /pid <pid> /f /t, timeout=1초)`를 쓰는 최후 fallback을 제안한다. 이는 graceful DB close가 아니며 전달·프로세스 생성 실패를 동기 진단한다. PID·dataDir 소유권을 확인하고 무관한 프로세스를 멈추지 않는다. process.exit·기본 uncaught fatal에서는 이 fallback만 실행하고 DB 거래·파일 삭제·완료 기록을 시도하지 않는다. 정상 stop 성공 전에는 emergency 등록을 지우지 않으며, 시작 실패에도 생성한 child를 추적한다. uncaughtExceptionMonitor는 동기 진단에만 쓰고 기본 fatal 종료를 정상화하지 않는다. 비영속 dataDir 삭제는 child/후손 종료 확인 뒤 정상 경로에서만 한다(E01/E08/E09).
6. **OS와 외부 감독.** Ctrl+C가 앱과 같은 process group의 postgres에 동시에 전달되지 않도록 postmaster 기동만 별도 group/session으로 분리하는 adapter/patch를 권고한다(`detached`, Windows `windowsHide`; `unref`로 방치하지 않음). Windows 정상 DB stop은 현재 `taskkill /f /t` 대신 소유 바이너리의 `pg_ctl stop -D <dir> -m fast -w -t <잔여 초>`를 기다리는 경로로 보강하고 강제 tree kill은 만료 fallback으로 둔다. 바이너리 경로·실행 uid/gid·child identity는 adapter 계약으로 고정하고 확인 못 하면 시작/종료 실패를 드러낸다. systemd에서는 정상 TERM이 main에만 가고 만료 시 전체 group이 회수되는 mixed 방식, Docker/Kubernetes에서는 앱 전체 예산보다 큰 stop grace를 맞춘다(예: 앱 30초/외부 40초 이상; preStop·sync stop 비용도 포함). SIGKILL·native crash·Windows hard terminate에서도 **잔존 없음이 필수**라면, 앱과 독립된 owner/lease 회수 또는 OS containment를 이 설계의 필수 배포 구성으로 둔다. 앱 내부 hook만으로 그 보장을 표시하지 않는다(E08/E09/E24/E29/E31/E32).
7. **갱신 방어.** 외부 DB/embedded DB 양쪽의 fresh child process에서 import 전후 listener와 실제 신호 종료를 검증하는 회귀 경계를 추가한다. 패치 파일 적용만 성공해도 다른 경로에 hook이 생길 수 있으므로 의미 검증을 함께 둔다. 현재 private child field를 사용하는 `startCluster` 우회도 adapter 한 곳으로 제한하고 버전·형태 불일치 시 명시 실패시킨다. 이 연구는 코드 복사를 권고하지 않으며, upstream/PR 코드를 실제 복사한다면 AGENTS의 출처 SHA·파일 header·THIRD_PARTY_NOTICES 규칙을 구현 단계에서 적용한다.

HTTP 세부 계약: Node 24 [`server.close`](https://github.com/nodejs/node/blob/f7f273a9bb6445f6f7fb6349105e7532972045fb/doc/api/http.md#L1738-L1755)는 신규 연결을 중지하고 idle을 정리한다. [`closeAllConnections`](https://github.com/nodejs/node/blob/f7f273a9bb6445f6f7fb6349105e7532972045fb/doc/api/http.md#L1776-L1790)는 active도 강제 종료하며 upgrade socket은 제외하고 close 뒤 호출을 권고한다(공식 문서 주장). 따라서 소켓을 끊은 사실만으로 HTTP 비동기 handler의 DB 작업까지 끝났다고 간주하지 말고, 앱의 진행 작업 Promise도 drain 대상으로 삼아야 한다(추론).

## 한계와 미확인

- **확인한 것:** 공개 고정 소스·공식 문서·npm metadata/배포 파일·issue/PR 상태. 배포와 HEAD의 해당 파일 동일 여부, 메인의 결정 근거 재열람 결과는 캐시 `main-verification.md`에 기록했다. 소스 테스트를 읽은 것을 실행 통과로 표시하지 않았다.
- **실행하지 않은 것:** 제품/OSS 서버·실제 DB·CLI 에이전트·모델 API, 신호 재현, Windows/macOS/Linux 통합 시험, 패치 적용·설치. (a)–(e) 표의 ✓는 권고 설계의 제어 경로이지 제품 검증 통과가 아니다. 특히 현재 Windows taskkill 및 group 전달 문제 때문에 hook 제거만으로 (d)는 미충족이다.
- SIGKILL·OS 사망·event-loop block에 대한 유한 종료/고아 회수는 JS timer·exit hook으로 보장할 수 없다. synchronous fallback 자체도 OS 호출이 지연될 수 있으므로 외부 시한이 최종 상한이다. 정상 DB-last와 무조건 유한 종료를 비정상 경로에서도 동시에 요구할 수는 없다.
- embedded-postgres 검색은 캐시에 기록한 shutdown/exit-hook/signal/hook query 범위다. Paperclip 검색 133건 중 첫 100건 및 관련 개별 issue/PR만 확인했다. 모든 issue/플러그인/의존성의 부작용을 전수 확인한 것은 아니다. embedded-postgres-binaries 사용 제품은 별도 심층 추적하지 않았다.
- Ghost의 명시 DB pool 해제는 읽은 경로에서 확인 못 했다. Backstage의 root HTTP/DB 병렬 정리, n8n의 HTTP callback 미대기, Strapi의 즉시 socket 파괴를 이상적인 순서의 근거로 사용하지 않았다. 유명 구현의 사용 사실과 권고할 안전성을 분리했다.
- upstream HEAD·npm dist-tag·issue 상태는 변한다. Paperclip 미병합 PR의 autoShutdown을 공식 배포 옵션으로 오인하지 말고 후속 구현 착수 때 재확인해야 한다. PGlite/Java/Testcontainers 사례는 lifecycle 설계 비교이며 우리 SQL·드라이버·영속성·설치 호환성을 검증하지 않았다.
- 이번 변경은 이 보고서와 지정 조사 캐시뿐이다. 문서 지도·제품 코드·테스트·설정·git 조작·커밋·push·PR·issue 댓글은 수행하지 않았다. 제품 검사는 실행하지 않았으며 문서 검증 결과는 캐시 receipt에 남긴다.
