# #153 파일 경로 격리 파일 시스템별 검증 기록

`record_artifact`의 파일 경로 격리를 Linux·Windows·macOS의 파일 시스템 여덟 곳에서 실제로 확인한 결과다. 지금 동작·응답 코드는 [현재 구현 현황](../current-implementation.md), CI 실행 조건은 [CONTRIBUTING](../../CONTRIBUTING.md)이 기준이다.

기준: PR #176 head `fc23ac8`(GitHub이 `main` `19b6cfc` 위에 만든 병합 커밋 `905ab33`), [CI run 43215390688](https://github.com/babo-jeonguk/BaboJUBot/actions/runs/43215390688), 2026-11-12. 이후 커밋은 이 기록 등 문서만 바꿨다.

## 결론

- 여덟 볼륨 모두 다른 조직·조직 밖의 시험 바이트를 돌려준 사례가 없다. 결함 0, 미검증 0이다. 각 사례는 조직 A·조직 B·조직 밖에 서로 다른 바이트를 두고, 성공 응답도 고른 경로와 실제 보존 바이트를 본다.
- 확인한 차이 중 F5·F2·F4는 고쳤고, F1·F6은 안전한 제한으로 남겼다. F3은 재현되지 않았다.
- 링크·hard link·ACL이 없는 FAT32, 정션을 쓸 수 없는 SMB loopback의 해당 사례는 적용 불가로 따로 세었다. 적용 불가·제한은 통과 수에 넣지 않았다.

## 환경

모두 GitHub 호스팅 runner이고 Node 24.22.2다. 시험 전용 폴더·가상 디스크·디스크 이미지·공유만 만들었고, job 끝에 정리한 뒤 runner VM과 함께 폐기된다.

- Linux: Ubuntu 24.04(커널 7.0.0-1017-azure), `/dev/sda1` ext4, 일반 사용자 `runner`(uid 1001). 장치 노드(C18)만 `sudo -n mknod`로 만들고 읽기는 일반 사용자로 했다.
- Windows: Windows Server 빌드 26100, 관리자 권한(High Mandatory Level). NTFS는 runner 임시 볼륨 `D:`(8.3 짧은 이름 생성을 켬), FAT32는 `diskpart`로 만든 1 GiB VHDX(`R:`), SMB는 같은 컴퓨터의 NTFS 폴더를 공유해 `\\localhost\babojubot-files`로 연 SMB 3.1.1 loopback이다. 원격→로컬·원격→원격 symlink 평가는 기본값대로 꺼져 있다. 실제 NAS나 다른 SMB 서버는 시험하지 않았다.
- macOS: macOS 26.7.2(빌드 25G332). APFS는 runner 임시 폴더, 나머지는 `hdiutil`로 만든 256 MB 이미지(소유권 켬)다. 볼륨 종류는 `diskutil`의 File System Personality로 확인했다.

제한·적용 불가의 이유:

- C05(Linux·macOS): 절대 경로의 작업 폴더 부분에 `..`를 섞으면 밖으로 본다. Windows는 운영체제처럼 글자로 줄여 안쪽 파일이다.
- C14: F6과 같다.
- C26 NTFS·SMB: 파일 읽기 거부(ACL deny)는 관리자 계정에서도 운영체제와 우리 모두 거부했다(`file_unreadable`). 폴더 통과 거부는 운영체제가 무시하고(통과 검사 생략 권한) 우리는 `file_unreadable`로 더 좁게 거부한다. FAT32는 ACL을 저장하지 않아 적용 불가다.
- C32 NTFS·FAT32: 드라이브 작업 폴더를 관리 공유(`\\localhost\D$\…`)로 적으면 같은 파일이라도 별칭이라 밖으로 본다. SMB 작업 폴더의 `\\?\UNC\` 표기는 통과다.
- C33: F1과 같다.
- C34: NTFS·FAT32·SMB 모두 8.3 짧은 이름(`LONGFI~1.MD`, `LONGFO~1`)으로 안쪽 파일을 등록했다. NTFS는 바깥을 가리키는 정션의 짧은 이름(`LONGJU~1`)도 `path_outside_folder`로 거부했다.
- C35 SMB: Node가 공유에 만든 정션은 만든 뒤 운영체제도 보지 못한다(`lstat` ENOENT, 열기 ENOENT). 우리 읽기도 `file_not_found`로 거부했다. NTFS에서는 운영체제가 정션을 따라가 바깥·다른 조직 바이트를 여는 반면 우리 읽기는 `path_outside_folder`다.
- C36: F4와 같다. Windows의 대소문자 구분 폴더는 NTFS에서만 만들 수 있다(FAT32·SMB는 `setCaseSensitiveInfo` 거부).
- C16·C17: Windows에는 FIFO가 없고, Node는 경로 socket 대신 named pipe를 쓴다. C18 FAT32는 장치 링크를 만들 수 없고 장치 이름 거부는 C28이 본다.
- FAT32·SMB의 `dev`/`ino`는 0이 아니었다. SMB의 `dev`는 공유한 NTFS 볼륨과 같다. 두 볼륨에서도 확인 직후 다른 조직 폴더·파일로 옮겨 넣는 바꿔치기(C11·C12·C15)는 모두 `file_changed`·조직 신원 오류로 막혔다.

경합(C11·C12·C15·C16·C37)은 읽는 프로세스의 정해진 파일 작업 한 시점에 바꿔치기를 넣는 결정적 주입이다. 모든 시점을 차례로 바꿔치는 기존 경합 시험(`workspace-race.test.ts`)도 같은 볼륨에서 돌았다(FAT32는 링크로 바꿔치는 행을 건너뛰고 폴더째 옮기는 행만).

## CI 실행과 시간

파일 읽기 경계에 닿는 변경([판정](../../scripts/ci-changes.mjs))이면 `files / linux`·`files / windows`·`files / macos`가 함께 돌고, `ci / test`가 셋의 성공을 요구한다. 그 밖의 코드 PR은 셋이 건너뛰어지고 macOS·Windows job이 기본 볼륨에서 같은 시험(사례 표 포함)을 돈다. 같은 PR의 새 커밋은 이전 실행을 취소한다(기존 concurrency 설정). 각 job·볼륨 단계에 시한이 있고, 앞 볼륨이 실패해도 남은 볼륨·결과표·정리는 돈다.

- 일반 PR: 기본 볼륨의 시험은 사례 표를 더하고도 Windows 47–69초·macOS 22–38초로 기준(76초·37초) 안팎이다. 전체 실행 시간은 E2E(약 4–5분)가 정하므로 늘어난 대기는 1분 목표 안이다. 전체 검증이 돌지 않는 일반 코드 PR의 실제 run은 이 PR에서 관찰하지 못했고, 실행 조건은 `scripts/ci-test-gate.test.mjs`·`scripts/ci-changes.test.mjs`로 확인했다.
- 전체 검증: 가장 긴 macOS job이 5분 23초로 15분 목표 안이다. 병목은 대소문자 구분 APFS 이미지의 경합 시험과 이미지 떼기(병렬로 약 100초)다. 이미지 떼기를 생략하고 VM 폐기에 맡기면 약 1분 40초 줄지만 정리 시도를 남기려고 그대로 두었다.
- 실행 수: 파일 경계 PR은 job 세 개(약 9분 50초의 runner 시간)가 더 돈다. 그 대신 macOS·Windows job은 기본 볼륨 시험을 거듭하지 않는다.
- 판정: 처음 실행([run 43209747615](https://github.com/babo-jeonguk/BaboJUBot/actions/runs/43209747615))에서 `files / windows` 실패를 `ci / test`가 "files-windows did not finish as success"로 거부했고, 마지막 실행은 "All test suites and file-system verifications passed"였다.

## 처음 실행에서 고친 시험

- `nul.md` 시험 파일은 Windows에서 장치 이름이라 정상 거부됐다. 이름을 바꿨다(C24).
- 기존 경계 시험이 FAT32에서 링크를 만들지 못해 실패했다. 링크가 없는 볼륨에서는 링크가 필요한 시험만 건너뛴다.
- SMB에서 막 지운 항목 때문에 폴더 삭제가 늦어 다시 시도하게 했고, 공유에 만든 정션이 보이지 않는 것을 기능 판정에 반영했다.
- FAT32에서 `icacls`가 성공해도 거부 항목이 저장되지 않아, 저장 여부를 다시 읽어 적용 불가로 판정한다.

## 근거

외부 원문을 새로 열지 않았다. 기존 [경로 격리 조사](artifact-path-confinement.md)의 결정(Windows 이름 거부, 고정 폴더 안에서 한 칸씩 풀기)을 그대로 두었고, 이번 판단은 위 실제 환경의 관찰을 근거로 했다. F3의 cap-std 설명("Windows appears to disallow symlinks to paths with trailing slashes…")은 운영체제 비교 시험으로 대신 확인했다.

## 미검증 범위

- 실제 NAS·다른 SMB 서버·다른 Windows 계정(일반 사용자)·exFAT·ReFS·NFS·FUSE. SMB는 같은 Windows의 loopback이다.
- 대소문자 무시 ext4(casefold)와 다른 Linux 파일 시스템, 다른 macOS·Windows 판.
- 경합의 무작위 대량 반복. 결정적 주입과 기존 모든 시점 시험만 돌렸다.
- 전체 검증이 돌지 않는 일반 코드 PR의 실제 CI 실행(실행 조건은 단위 검사로만 확인).
