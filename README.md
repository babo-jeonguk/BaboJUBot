# BaboJUBot

연구 목표마다 독립적인 AI 조직을 구성하고, Research Lead와 작업자들이 협력하는 범용 연구 운영 프로젝트입니다. 초기 계획·팀 승인, 진행 관찰, 사용자 개입, 조직별 기억, 사용자 최종 검토를 지원하는 방향으로 개발합니다.

현재 상태는 **판 1 walking skeleton**입니다. [데모 시나리오](#데모-시나리오)로 조직 생성부터 사용자 최종 완료까지 판 1 흐름 전체를 대시보드에서 직접 눌러 볼 수 있고, Playwright E2E 하나가 이 흐름을 지킵니다. 대시보드의 새 연구 조직 dialog에서 조직 이름·연구 목표와, 정했다면 완료 기준을 적어 조직을 만들면 전용 Research Lead가 함께 생기고 `계획 수립` 단계로 시작하며, Event stream으로 사이드바와 홈에 바로 나타납니다. 목표·완료 기준은 사용자 입력으로 생성 Event에 남고, Lead는 생성 깨우기로 곧바로 깨어나 초기 연구 승인 요청을 준비하며 그 소식을 기본 대화로 알립니다. Lead 대화에 메시지를 보내면 Lead가 깨어나 실행 시도를 받고, 모델을 부르지 않는 가짜 프로바이더가 실행 시도별 토큰으로 조직 도구를 호출해 답장합니다. 활동·실행 시도 상세·에이전트 상세에서 그 실행 시도를 볼 수 있습니다. Lead와의 대화는 여러 개를 둘 수 있습니다. 조직과 함께 기본 대화가 생기고, 대화 목록의 `＋ 새 대화`로 언제든 새 대화를 시작합니다(첫 메시지를 보낼 때 생기고 제목은 첫 메시지를 줄인 것, 빈 대화는 남지 않음). Lead는 사용자 메시지에 그 메시지가 온 대화로 답하고(여러 대화의 메시지로 깨어난 실행 시도는 대화마다 답함), 승인 결정·작업 완료·heartbeat처럼 사용자 메시지 없이 스스로 알리는 메시지는 기본 대화로 보냅니다. 목록은 기본 대화를 맨 위에, 나머지를 마지막 활동 순으로 보이며 Lead가 답한 뒤 보지 않은 대화에 점을 붙입니다(본 위치는 화면이 보일 때 저장하고 Event를 남기지 않음). 다른 조직의 대화는 어느 경로에서든 404이고, 끝난 조직의 대화도 읽을 수 있으며 보내기 규칙은 같습니다. 실제 프로바이더 adapter와 실제 모델 호출은 아직 없습니다.

가짜 Lead는 생성으로 깨어나면 초기 연구 계획·팀 구성·연구 환경 명세·연구 흐름 템플릿을 하나의 초기 연구 승인 요청으로 올립니다. 사용자가 완료 기준을 비워 두었으면 Lead가 같은 요청에 완료 기준을 제안해야 하며(없으면 제품이 422 `completion_criteria_required`로 거부), 사용자가 정한 완료 기준은 요청으로 바꿀 수 없습니다(409 `completion_criteria_set`). 승인 요청 상세와 Inbox 상세는 제안한 기준에 `Lead 제안`을 붙여 보이고, 승인하면 그 기준이 조직의 완료 기준이 됩니다. 반려·수정 요청이면 완료 기준은 정해지지 않은 채 Lead가 다시 제안합니다. 목표를 생성 때 받기 전에 만든 `목표 설정` 조직은 예전처럼 Lead 대화의 `목표: …`·`완료 기준: …` 줄로 Lead가 목표를 기록합니다. 사용자는 Inbox에서 승인 요청 상세를 열어 승인·반려·수정 요청을 합니다. 승인하면 조직이 `연구 진행`이 되고 제안한 작업자들이 생기며, 반려·수정 요청은 `계획 수립`으로 돌아가 사유와 함께 Lead를 깨웁니다. 승인 전에는 작업 생성·작업자 추가 도구를 제품이 거부하고 Event log에 남깁니다. 각 에이전트는 [하네스 라이브러리](harness/README.md)에서 복사한 자기 Role·Soul·Skill 사본을 갖고(Lead는 조직 생성 때, 작업자는 승인 때나 연구 중 추가될 때), 에이전트 상세의 Role·Soul·Skill 탭에서 봅니다.

`연구 진행`에서는 Lead가 작업(담당·부모 작업)을 만들어 작업자에게 맡기고, 할당이 담당 작업자를 깨웁니다. 가짜 프로바이더는 승인 직후 작업자마다 작업 하나를 맡기며, 작업자는 착수 → Markdown 산출물 기록 → 자기 보고 요약과 함께 완료합니다. 작업 완료는 부모 작업 담당자를, 부모가 없으면 작업을 만든 에이전트를 깨우고(자기 자신은 깨우지 않음), 같은 조직 에이전트 간 메시지는 받는 에이전트를, 사용자의 작업 댓글은 담당자를 깨웁니다. 작업 상태는 `할당됨 → 진행 중 → 완료`입니다. 착수는 담당자만 할당됨에서 할 수 있고, 완료는 담당자와 Lead(조정)가 할당됨·진행 중 어디서든 한 번 할 수 있으며 다시 완료하면 409입니다. 산출물은 첫 판에서 Markdown·텍스트 본문을 DB에 그대로 둡니다. 대시보드의 조직 › 작업에서 목록·작업 상세(자기 보고·댓글 thread·산출물·연결된 연구 노드)·산출물 단건 보기를 Event stream으로 새로고침 없이 봅니다. Markdown 산출물과 에이전트·사용자가 쓴 긴 글(자기 보고·댓글·Lead 대화·계획·Role·Soul·Skill 사본 등)은 기호 대신 제목·목록·표로 그려 보이고, 원문 Markdown은 편집 폼에서 봅니다.

연구 지도는 연구 노드·주 연결(노드의 주 부모, 최대 하나)·보조 연결·작업의 연구 노드 연결(0~1)로 이루어집니다. 에이전트는 `연구 진행`에서 조직 도구로 노드를 만들고 고치며, 주 부모를 지정(주 부모가 없을 때만)·변경하고, 보조 연결을 더하고, 작업을 노드에 연결·재연결·해제합니다. 노드·보조 연결 종류는 조직 사본 연구 흐름 템플릿이 선언한 것만 받고, 주 연결 순환(자기 자신·후손을 주 부모로)과 자기 자신과의 보조 연결은 거부합니다. 보조 연결은 개수·순환·중복 제한이 없습니다. 노드 상태는 `제안됨 → 진행 중 → 완료/기각됨`이며 삭제 대신 `폐기`합니다. 폐기는 자손·연결·작업을 그대로 두고 폐기 취소하면 폐기 직전 상태로 돌아가며, 폐기된 노드는 다른 편집과 새 연결의 대상이 되지 않으며, 같은 폐기·폐기 취소를 다시 요청하면 바뀌는 것 없이 성공합니다. 구조 편집은 모두 조직 행 잠금 아래에서 최신 주 연결을 읽어 검사하므로 동시 편집도 순환을 남기지 않습니다. 편집마다 편집 기록(편집자·대상·요약)과 Event가 남고, 사용자 편집은 Lead를 깨웁니다. 가짜 작업자는 맡은 작업마다 템플릿의 첫 종류로 노드를 만들어 작업을 연결합니다.

대시보드의 조직 › 연구 지도는 React Flow와 Dagre로 주 연결 트리를 배치하고 보조 연결을 연한 점선으로 겹쳐 그리며, 같은 두 노드 사이의 보조 연결은 나란히 벌려 그립니다. 연결은 노드 아래 레이어에 한 번 그리고 선택한 노드 주변만 위에 강조해, 수백 노드에서도 화면 끌기와 선택이 지도를 다시 그리지 않습니다(성능 측정은 `MAP_PERF=1 pnpm test:e2e research-map-perf`). 노드를 고르면 오른쪽(1024px 미만에서는 아래) 상세 패널에서 종류·상태·주 부모와 하위·보조 연결(관계 ID별)·연결 작업과 산출물·편집 기록을 보고, 초기 연구 승인 뒤 최종 완료·중단 전까지 노드 추가·제목·상태 수정·주 부모 변경·보조 연결 추가를 명시 폼으로 합니다. 폐기는 되돌릴 수 있어 묻지 않고 바로 하고, 화면 아래 가운데에 그 노드 제목과 `폐기 취소`가 있는 토스트를 10초 동안(마우스를 올리거나 포커스가 있는 토스트만 멈춤) 띄우며, 패널의 `폐기 취소`도 그대로 있습니다. 토스트는 새것이 맨 아래에 쌓여 앞 토스트를 위로 밀고 저마다 제 시간에 닫히며, 한 번에 셋까지 보이고 넘친 토스트는 차례를 기다렸다가 자리가 나면 맨 아래에 나타나 그때부터 10초를 셉니다. 배치는 좌→우 하나이고 폐기한 노드는 흐리게 남습니다. 노드를 끌면 주 연결 하위 노드가 함께 움직이며, 끌어 옮긴 위치는 이 화면의 보기 상태라서 저장하지 않고 편집으로 기록하지도 않습니다(`자동 정렬로 되돌리기`로 지움). 화면에는 노드·관계 ID를 보이지 않습니다.

Lead는 `연구 진행`에서 완료 기준을 충족했다고 판단하면 요약과 근거 산출물(같은 조직의 산출물)을 묶어 결과를 제출하고, 조직은 `결과 검토 중`이 됩니다. 제출은 그때의 목표·완료 기준을 검토 기준으로 고정한 새 기록이며 Inbox와 조직 › 결과 검토에 나옵니다. 사용자는 결과 제출 상세에서 요약·완료 기준·근거 산출물(단건 페이지로 열림)을 보고 결정합니다. 수정 요청은 의견과 함께 `연구 진행`으로 돌리고 Lead를 깨우며, 다시 제출하면 직전 제출을 가리키는 새 제출이 되고 옛 제출의 내용과 결정은 그대로 남습니다. 최종 완료는 사용자 제어 명령으로만 일어나며 Lead의 조직 도구에는 최종 완료·승인 정책 변경 도구가 없습니다. 결과 검토 중에는 연구 쓰기 도구가 닫히지만 사용자 메시지·지도 편집으로 Lead가 깨어나 조회·답장은 할 수 있습니다. `최종 완료`(그리고 `일시정지`·`중단`) 조직에서는 실행 시도 admission이 깨우기 사유와 상관없이 새 실행 시도를 시작하지 않고 깨우기만 남겨 두며, 서버를 다시 시작해도 마찬가지입니다. 최종 완료 전에 이미 시작한 실행 시도는 끊지 않고 스스로 끝나게 두되 그 사이 연구 쓰기는 거부됩니다. 가짜 Lead는 사용자가 Lead 대화로 `결과 제출`을 부탁하면 완료한 작업의 산출물을 근거로 제출하고, 수정 요청을 받으면 의견을 요약에 적어 다시 제출합니다.

조직마다 승인 정책이 있고 항목은 `작업자 추가`·`GitHub에 올리기`이며 새 조직은 모두 꺼져 있습니다. `GitHub에 올리기`는 Lead 역할 지침으로 지키는 항목이라(켜져 있으면 올리기 전에 사용자에게 확인) 제품 코드가 GitHub 올리기를 막지 않고, Lead는 실행 맥락에서 지금의 정책을 읽습니다([ADR-0005](docs/adr/0005-approval-policy-enforcement-scope.md)). 사용자는 조직 › 설정의 항목별 스위치로만 바꾸고(누르면 그 항목만 바로 저장, 조직 도구에는 정책 변경이 없음), 바꿀 때마다 전후 값이 Event log에 남으며 다른 탭에도 새로고침 없이 반영됩니다. Lead는 `연구 진행`에서 하네스 라이브러리의 작업자 Role 이름과 프로바이더·모델 제안으로 작업자를 추가합니다. 정책이 꺼져 있으면 곧바로 Lead가 제안한 프로바이더·모델로 작업자와 그 작업자만의 사본이 생기고, 켜져 있으면 호출 때 읽은 Role·Soul·Skill 내용을 고정한 승인 요청만 Inbox에 올라가며 도구 결과는 `승인 대기`입니다. 정책은 조직 행 잠금 아래에서 읽으므로 정책 변경과 동시에 온 호출도 바뀌기 전이나 뒤의 정책 하나로 갈립니다. 사용자가 승인하면 그 내용으로 작업자가 생기고, 반려하면 아무것도 만들지 않으며, 어느 쪽이든 사유와 함께 Lead를 깨우고 연구 단계는 바뀌지 않습니다. 작업자 추가에는 수정 요청이 없고, 연구 단계가 바뀐 뒤에도 결정할 수 있습니다. 호출마다 별도 요청이라 여러 요청이 함께 기다릴 수 있고, 정책을 꺼도 이미 기다리는 요청은 사용자가 결정할 때까지 남습니다. 가짜 Lead는 Lead 대화의 `작업자 추가: <Role>` 부탁(Role이 없으면 `researcher`)으로 작업자를 추가합니다. `작업자 추가`·`결과 제출` 부탁은 메시지 전체가 그 명령(`… 해 주세요`·`… 부탁해요` 같은 끝맺음까지)일 때만 따르고, 부정문(`작업자 추가하지 마세요`)이나 다른 말이 섞인 메시지에는 답장만 합니다.

사용자는 조직 › 대시보드에서 조직을 일시정지·재개·중단하고, 에이전트 상세에서 에이전트 하나를 일시정지·재개합니다. 모두 즉시 효력이 있는 제어 명령이며 Event log에 남고 다른 탭에도 새로고침 없이 반영됩니다. 일시정지와 중단은 진행 중 실행 시도에 취소를 요청하고, 요청한 순간 그 실행 시도의 토큰은 읽기까지 막히며, 프로바이더가 정리를 끝내면 프로바이더가 무엇을 돌려주든 `취소됨`으로 끝납니다. 정리가 끝나기 전에는 그 에이전트의 다음 실행 시도가 시작되지 않습니다. 일시정지 중 생긴 깨우기는 남았다가 재개 때 에이전트별 실행 시도 하나로 전달되고, 사용자 제어로 취소된 실행 시도에 묶였던 입력은 다시 보내지 않습니다. 조직 일시정지는 최종 완료 전 어느 단계에서든 걸 수 있고 재개하면 직전 단계로 돌아가며, 에이전트 일시정지는 그 에이전트만 막고 조직을 재개해도 풀리지 않습니다. 중단은 되돌릴 수 없고 이후 어떤 실행 시도도 시작하지 않으며, 누르면 `조직을 중단할까요? 되돌릴 수 없습니다.`로 한 번 묻습니다(포커스는 `취소`). 최종 완료도 같은 모양으로 한 번 묻습니다. 최종 완료·중단 조직의 제어 버튼은 보이지만 누를 수 없고 서버도 409 `organization_closed`로 거부합니다. 일시정지 중에 초기 연구 승인이나 결과 검토를 결정하면 조직이 함께 재개되며(최종 완료는 곧바로 완료), 작업자 추가 결정은 일시정지를 풀지 않습니다. 중단된 조직의 초기 연구 승인·결과 결정은 받지 않고, 결정을 기다리던 그 요청은 Inbox에서도 빠집니다(이미 결정한 것은 남습니다). Lead 대화 입력창의 아이콘 버튼은 Lead 상태를 따라 바뀝니다. Lead가 쉬고 있으면 `보내기` 하나이고, 실행 중이면 입력이 빌 때 `실행 중단`, 입력이 있으면 `중단하고 보내기`와 `줄 세우기`(Enter)가 보이며, 그 실행 시도를 맡은 프로바이더가 끼워 넣기를 지원하면 그 사이에 `실행 중 끼워 넣기`가 더해집니다(지원하지 않으면 그리지 않음). 고른 방식은 메시지마다 새로 정합니다. `실행 중 끼워 넣기`는 메시지를 저장한 뒤 지금 실행 시도에 넣고, 프로바이더가 받으면 그 실행 시도가 받은 메시지로 대화에 놓이며 거절하면 줄 세운 메시지가 됩니다(`message.steered`). 넣는 동안의 메시지는 줄 세운 메시지가 아니라 고칠 수 없고 다음 실행 시도도 받지 않으며, 서버가 그사이 멈추면 다시 시작할 때 줄 세운 메시지로 돌아갑니다. `줄 세우기`는 메시지를 다음 실행 시도에 넘깁니다. `중단하고 보내기`는 실행 시도 중단 제어 명령과 메시지를 한 요청에서 함께 저장해 Event 두 개를 남기고, Lead의 진행 중 실행 시도를 취소한 뒤 그 메시지를 다음 실행 시도의 깨우기 사유로 전달합니다. 조직이나 Lead가 일시정지 중이면 메시지는 재개를 기다리므로, 일시정지가 취소한 실행 시도가 아직 정리 중이어도 중단할 실행 시도 없이 재개 뒤 먼저 전달됩니다. 그 실행 시도는 `중단하고 보내기` 메시지만 받고, 먼저 줄 세운 메시지와 다른 깨우기(승인 결정·작업 사건·heartbeat 등)는 그 실행 시도가 끝난 뒤의 실행 시도가 평소처럼 합쳐 받습니다. 실행 시도가 아직 받지 않은 메시지(일시정지로 기다리는 메시지 포함)는 대화가 아니라 입력창 바로 위 `줄 세운 메시지 N/20` 목록에 오래된 것부터 있고(`GET …/queued-messages`), 받으면 대화로 옮겨집니다. Lead 하나에 줄 세울 수 있는 메시지는 모든 대화를 합해 20개까지이며(contracts `maxQueuedMessages`), 가득 차면 보내는 버튼이 비활성이고 서버도 409 `queue_full`로 거부합니다. 항목에 마우스를 올리거나 keyboard focus하면(마우스 없는 화면은 늘) 오른쪽 위에 `고치기`(항목이 그 자리의 입력이 되어 Enter로 저장·Shift+Enter 줄바꿈·Esc 취소, 줄 속 위치와 전달 방식은 그대로, 비우면 저장할 수 없음)·`취소`(거두기)·`지금 보내기`(Lead가 실행 중이거나 조직·Lead가 일시정지 중일 때, 그 메시지를 `중단하고 보내기`로 바꿈. 일시정지 중이면 재개 뒤 먼저 전달되며, 입력창은 그대로 `보내기` 하나)가 보이고, 입력창이 비었을 때 ↑는 가장 최근 메시지를 거두고 그 글을 입력창 맨 앞에 되돌립니다. 서버는 `POST /api/organizations/:id/messages/:messageId/edit`·`…/withdraw`·`…/send-now`를 조직 → 에이전트 → 실행 시도 잠금 아래에서 처리해 admission과 직렬화하며, 실행 시도가 먼저 받았으면 409 `message_delivered`(화면은 `이미 전달된 메시지입니다` 토스트 뒤 대화로 옮겨 보임), 다른 조직 메시지는 404, 고치기·지금 보내기는 끝난 조직 409 `organization_closed`입니다. 일시정지 중 지금 보내기는 취소할 실행 시도 없이 전달 방식만 바꿉니다. 고치기는 `message.edited`(고치기 전 글 포함, 활동: `사용자가 줄 세운 메시지를 고쳤습니다`)를 남깁니다. 최종 완료·중단 조직은 사용자 메시지와 새 대화를 받지 않고(409 `organization_closed`) 입력창 자리에 `중단된 조직`·`최종 완료된 조직`만 보이며, 그 전에 줄 세운 메시지는 거두기만 됩니다. 대화는 Lead가 받은 순서입니다. 사용자 메시지는 실행 시도가 받은 순간(admission이 같은 transaction에서 매기는 `delivered_seq`, migration 0018)에 놓이므로 `지금 보내기`로 먼저 받은 메시지가 그보다 먼저 줄 세운 메시지보다 앞에 오고, 사용자 말풍선의 시각은 Lead에게 전해진 시각(그 실행 시도가 시작한 시각, `delivered_at`, migration 0019)입니다. 대화에 놓인 메시지는 받은 순서의 열쇠로 자른 쪽으로 읽습니다(`GET …/messages`는 최근 50개, `?before=`는 더 오래된 쪽, `?after=`는 새로 온 것). 화면은 위로 올리거나 `이전 메시지 보기`로 오래된 쪽을 붙이며 보던 자리를 지키고, 맨 아래에서 64px보다 멀어지면 아이콘 버튼 `맨 아래로`를 보입니다(누르면 부드럽게, 움직임 줄이기 설정이면 바로 내려감). 맨 아래 근처에서만 새 메시지를 따라 내려가고 그동안은 줄 세운 메시지 목록이나 입력창이 자라도 맨 아래에 남으며, 따라가는 동안 불러 둔 메시지가 100개를 넘으면 오래된 쪽을 덜어 내고(위를 읽는 동안은 덜어 내지 않음) 위로 올리면 다시 받습니다. 거둔 메시지는 지우지 않고 남지만(migration 0016 `withdrawn_at`) 대화·Lead 맥락에서 빠지고 그 깨우기는 지우며, `message.withdrawn`(활동: `사용자가 줄 세운 메시지를 취소했습니다`)을 남깁니다. 지금 보내기는 `message.sent_now`와 `agent.interrupted`를 남깁니다. `실행 중단`은 메시지 없이 진행 중 실행 시도만 취소하는 에이전트 제어 명령(`POST …/agents/:agentId/interrupt`)이며, 일시정지가 아니므로 이후 깨우기는 평소처럼 실행 시도를 시작하고, 취소할 실행 시도가 없으면(쉬는 중·이미 취소 정리 중) 아무것도 남기지 않습니다. 끝난 조직에서는 두 중단 모두 제어 명령이므로 보이지 않고 서버도 409로 거부합니다.

Lead 대화 메시지(보고·질문), 승인 요청(초기 연구 승인·작업자 추가), 결과 제출, 실패한 실행 시도는 그 기록·Event와 같은 transaction에 알림 outbox 항목을 남깁니다. 서버는 commit 뒤 Event를 신호로, 그리고 시작 때와 5초마다 outbox를 확인해 보낼 차례인 알림을 짧게 가져가(claim) transaction 밖에서 채널로 보내고, 그 claim이 그대로일 때만 결과를 남깁니다. 전송이 실패하면 1초부터 두 배씩(최대 5분) 미뤄 다시 보내고, 정산 전에 서버가 멈추면 claim이 만료된 뒤 다시 보냅니다. 첫 판의 채널은 가짜 채널뿐이며 알림마다 전송 기록 하나를 남깁니다(`GET /api/channels/fake/messages`, outbox 상태는 `GET /api/notifications`). 가짜 채널의 기록에는 답장할 수 있습니다(`POST /api/channels/fake/messages/:id/reply`). Lead 메시지 알림에는 글로 답하면 그 메시지가 있는 대화에 사용자 메시지로 들어가고(`{ body, delivery? }`, 고르지 않으면 줄 세우기), 승인 요청·결과 제출 알림에는 대시보드와 같은 결정 입력(`{ decision, note? }`)으로 답합니다. 답의 조직·원본은 답의 내용이 아니라 알림에서만 정하고, 대시보드와 같은 저장·거부 규칙과 응답 코드를 거칩니다(자기 서버를 HTTP로 다시 부르지 않음). 실행 시도 실패 알림의 답, 승인 요청·결과 제출에 대한 글 답은 422 `reply_not_allowed`이며, 끝난 조직의 메시지·결정은 대시보드와 같은 규칙으로 409 `organization_closed`입니다. 거부한 답은 아무것도 남기지 않습니다. 채널 답마다 서버 로그 한 줄(채널, 알림 ID, 답 종류, 받음 또는 거부 이유)이 남고 답의 글 내용은 적지 않습니다. 채널은 서버 시작 설정에서 목록으로 받지만 지금은 하나만 허용합니다. 사용자 메시지·정상 완료·사용자 취소·서버 재시작은 알리지 않고, 이 판 전의 사건은 소급해 보내지 않습니다.

Inbox는 레일·768px 미만 상단 바의 Inbox 버튼과 홈의 `주의 필요` 칸으로 여는 패널 하나입니다(1280px 이상은 본문 오른쪽 340px, 그보다 좁으면 항목을 고르면 닫히는 drawer). 승인 요청·결과 제출(결정한 뒤에도 결정 상태와 함께 남음)과 실패한 실행 시도(실행 시도마다 하나, 뒤 실행 시도가 성공해도 남음)를 한 목록에 두고, 범위(전체 조직 / 현재 조직)와 필터(주의 필요·전체·읽지 않음·보관됨)마다 개수를 보입니다. 주의 필요는 결정 대기 항목과 보관하지 않은 읽지 않은 실패이며 레일·조직 아바타의 수도 같은 판정입니다. 전체는 결정한 항목을 포함해 보관하지 않은 모든 항목입니다. 읽음·보관은 원본과 따로 저장하는 정리 상태라 결정·단계·깨우기를 바꾸지 않고, 바꿀 때마다 Event log에 남아 다른 탭도 따라옵니다. 결정을 기다리지 않는 항목(결정한 승인 요청·결과 제출, 실패)은 보관할 수 있고, 결정을 기다리는 승인 요청·결과 제출은 보관할 수 없습니다(서버가 422 `archive_not_allowed`로 거부). 이 판 전에 실패한 실행 시도와 정리한 적 없는 결정한 항목은 읽음으로 보입니다. 항목을 고르면 Inbox 상세(`/inbox/<조직>/<종류>/<ID>`)가 열려 요약을 보고 그 자리에서 결정하거나(원래 상세와 같은 결정 폼·같은 명령), `원래 화면에서 자세히 보기`로 승인 요청·결과 제출·실행 시도 상세에 가서 전체 내용을 봅니다. 결정하면 그 자리에 결정 기록이 남고 다음 항목으로 넘어가지 않습니다. 항목을 열면 읽음이 되고(결정 대기 항목은 결정할 때까지 주의 필요에 남음), 패널 행 앞의 조직 아바타를 누르면 그 행이 체크되고, 하나라도 체크돼 있는 동안 모든 행이 아바타 대신 체크박스를 보이며, 나타나는 `모두 읽음`으로 체크한 항목만 읽음으로 바꿉니다. 읽은 실패는 `읽지 않음`으로 되돌릴 수 있고(승인 요청·결과 제출은 결정 여부가 주의를 정하므로 되돌리지 않음), 이 버튼과 보관은 패널 행에 마우스를 올리면 오른쪽 위 아이콘으로, 상세에서는 글자 버튼으로 있습니다. 메시지 앱(가짜 채널) 알림의 링크도 승인 요청·결과 제출·실패는 Inbox 상세, Lead 메시지는 그 메시지가 속한 대화(`/orgs/<조직>/chat/<대화>`)로 갑니다. 레일의 전역 설정에는 프로바이더 adapter·연구 환경 템플릿·비밀값·메시지 앱 연결의 자리만 있습니다. 가짜 Lead는 `실패 연습` 부탁을 받으면 아무것도 쓰지 않고 실행 시도를 실패로 끝냅니다.

조직 › 대시보드는 조직 제어와 결정 대기 항목 아래에 지표(상태별 작업·실행 시도·산출물 수, 14일 실행 성공률), 14일 차트(시작한 날 기준 실행 시도의 지금 상태별 수, 끝난 날 기준 성공률, 만든 날 기준 작업의 지금 상태별 수, 기록한 날 기준 산출물 수), 최근 활동 10개를, 오른쪽에 실행 중인 에이전트를 보입니다. 모두 서버 요약 하나(`GET /api/organizations/:id/dashboard?timeZone=`)를 한 읽기 snapshot에서 만들어 수와 목록이 서로 맞고, 다른 조직의 기록은 세지 않습니다. 날짜는 브라우저 시간대(서버 Postgres의 시간대 자료에 없는 이름이면 UTC, 화면에 밝힘)의 달력 날짜로 자르며 오늘(지금까지)을 포함한 14일이고, 기록이 없는 날도 0으로 그립니다(서머타임으로 23·25시간인 날도 하루). 작업 차트는 그날의 과거 상태가 아니라 그날 만든 작업의 지금 상태입니다. 성공률은 완료 / (완료 + 실패)이며 취소·서버 재시작은 세지 않고, 끝난 시도가 없으면 0%가 아니라 `—`이며 그날의 취소·서버 재시작 수는 따로 보입니다. 실행 시도의 성공은 연구의 최종 완료가 아닙니다. 실행 중인 에이전트는 진행 중 실행 시도 전부이며 취소를 요청받아 정리 중인 것도 끝날 때까지 `취소 중`으로 남습니다. 차트 막대는 hover·keyboard focus로 그날의 수를 보이고 `숫자로 보기` 표가 같은 값을 모두 담습니다. 홈은 에이전트 로비입니다. 위에 주의 필요·작업 중(취소 정리 중은 뺀 수, 정리 중은 따로)·조직 수를 보이고, 아래에 연구 조직마다 방 하나를 조직을 만든 순서로 놓습니다. 방은 주의·실행 상태가 바뀌어도 움직이지 않고 새 조직은 맨 뒤에 붙으며, 최종 완료·중단 조직만 맨 아래 접힌 `끝난 조직`의 불 꺼진 작은 방으로 옮겨 갑니다. 방 머리는 이름·단계·주의 수·목표 한 줄·`작업 중 N / M명`·마지막 활동 시각을 보이고 누르면 조직 화면으로 갑니다. Research Lead는 왼쪽 큰 책상, 작업자는 들어온 순서로 정한 고정 자리(한 줄에 여섯까지, 넘으면 줄을 고르게 나눠 아래로 자람)에 앉고, 캐릭터를 누르면 그 에이전트 화면으로 갑니다. 상태는 자리 대신 모습으로 보입니다: 작업 중이면 앉아서 모니터에 글이 흐르고(마우스를 올리거나 keyboard focus하면 머리 위 말풍선이 맡은 작업 제목, 없으면 깨어난 이유를 말함), 사용자 결정을 기다리는 Lead는 일어서서 `계획 승인`·`작업자 추가 승인`·`결과 검토` 물음표 말풍선을 띄우며, 마지막 실행 시도가 실패했으면 걱정하는 얼굴과 빨간 ✕ 화면, 일시정지(조직·에이전트)면 책상에서 졸고, 쉬는 에이전트는 방의 라운지 소파로 가 책상에는 이름표와 빈 의자만 남습니다. Lead 포함 여섯 명까지의 방은 반 폭, 일곱 명부터 한 줄 전체를 씁니다. 움직임 줄이기 설정이면 움직이지 않습니다. 방에 필요한 조직·에이전트 상태(들어온 순서, 실행 중 여부, 일시정지, 마지막 실행 실패, 붙잡은 작업, 기다리는 결정)는 `GET /api/overview` 하나가 조직 수와 상관없이 SQL 세 개를 한 읽기 snapshot에서 실행해 냅니다. 모두 Event가 오면 다시 불러오고, 대시보드는 응답이 자른 오늘이 끝나는 시각(그 시간대의 다음 자정, 서버가 `nextDayAt`으로 알림)에도 서버 시계 기준으로 다시 불러옵니다. 조직 › 활동의 에이전트 필터는 주소(`?agent=`)에 남아 실행 중 카드의 `활동 보기`로 바로 옵니다. 가짜 Lead는 `실행 유지 연습` 부탁을 받으면 아무것도 쓰지 않고 취소될 때까지 실행 시도를 끝내지 않습니다.

사용자 API에는 로그인이 없습니다. 로컬 신뢰 운영이며 같은 기기에서 도는 프로그램은 사용자와 구별되지 않습니다([전체 구조](docs/architecture.md#제품-불변-조건-강제-위치)).

사용자는 에이전트 상세 › Role·Soul·Skill 탭에서 그 에이전트의 사본 하나를 편집·저장·취소합니다. 저장은 본문 전체와 편집을 시작한 revision 번호를 보내며, 조직 행 잠금 아래에서 사본·새 revision(번호·편집자·서버 시각·전체 본문)·Event·편집 사유의 Lead 깨우기를 한 transaction으로 남깁니다. 같은 내용의 저장도 revision을 남깁니다. 그사이 다른 저장이 있었으면 `revision_conflict`로 거부하고 편집 내용은 화면에 남으며, 최종 완료·중단 조직은 거부하고, 다른 조직의 에이전트·사본·revision은 없는 것처럼 404입니다. Skill은 라이브러리와 같은 frontmatter(디렉터리 이름과 같은 name, description)를 지켜야 저장됩니다. 복사로 생긴 처음 내용이 revision 1(편집자 `복사로 생김`)이고(migration 0009 전 사본도 그렇게 채움), 복사 출처는 편집해도 바뀌지 않습니다. 같은 Role의 다른 에이전트 사본과 하네스 라이브러리는 그대로입니다. 진행 중 실행 시도는 시작할 때 받은 지침으로 끝나고, 그 에이전트의 다음 실행 시도는 바뀐 사본 내용의 bundle 버전을 받아 이전 세션 없이 시작합니다. bundle 버전은 내용에서만 정하므로 같은 내용 저장이나 중간 실행 없이 원래 내용으로 돌아온 경우에는 세션을 이어 갑니다. revision 목록과 예전 revision 본문은 읽기 전용이며 되돌리기·diff와 사본 편집 조직 도구는 없습니다. 저장하지 않은 편집이 있으면 다른 파일·화면으로 옮기거나 새로고침할 때 버릴지 묻습니다.

#54 전에 만든 개발 DB의 조직은 Lead 사본이 없어 지침 bundle 버전 없이 실행됩니다. 사본이 필요하면 `.babojubot/postgres`를 지우고 새로 만듭니다. 구조는 [전체 구조](docs/architecture.md)를 따릅니다.

조직 › 에이전트는 Research Lead를 위에, 작업자를 생긴 순서대로 아래 한 줄에 두고 잇는 조직도입니다(React Flow). 카드마다 에이전트 얼굴·이름·역할·상태가 보이고 카드 전체가 에이전트 상세로 가는 링크이며, 실행 중인 작업자로 가는 연결은 흐릅니다. 두 명이 한 줄에 들어가지 않는 폭(390px 등)에서는 Lead 아래로 작업자를 들여 쌓아 넘치지 않습니다. 에이전트 상세에서 이름을 눌러 바꾸고(Enter·포커스 이동은 저장, Esc는 취소) 얼굴을 눌러 색·눈·입·액세서리 프리셋을 고르며 미리 봅니다. 둘 다 `PATCH /api/organizations/:id/agents/:agentId`로 저장하며 조직 행 → 에이전트 행 잠금 아래에서 바꾸고 `agent.profile_changed` Event를 같은 transaction에 남깁니다(다른 탭은 이 Event로 다시 불러옴). 이름은 앞뒤 공백을 지운 1~40자이고 제어 문자를 받지 않으며(422), Lead가 이름으로 팀원을 가리키므로 같은 조직의 다른 에이전트와 대소문자만 달라도 겹치는 이름은 409 `name_taken`입니다. 새 작업자 이름(`<Role 표시 이름> N`)도 같은 규칙으로 Lead를 포함한 조직의 모든 이름을 피해 정하고(초기 팀 승인·작업자 추가 모두), DB unique index(조직, `lower(name)`)가 경합을 막습니다. migration 0017은 그 전에 겹친 이름을 가장 먼저 들어온 에이전트만 두고 뒤에 ` 2`·` 3`…을 붙여 풉니다. 다른 조직의 에이전트는 404이고, 연구 진행에 닿지 않는 표시 정보라 어느 단계에서든 바꿀 수 있습니다. 바꾼 이름은 다음 실행 시도의 팀 맥락에 갑니다. 얼굴을 고르지 않은 에이전트는 ID에서 정한 기본 얼굴이라 migration 0013 전 에이전트도 채우지 않고 서로 다른 얼굴로 보입니다. 얼굴은 가만히 있을 때 깜빡이고, 포인터가 가까이 오면 눈동자가 따라보며, 실행 중이면 말하듯 들썩이고, 마지막 실행 시도가 실패했으면 걱정하고, 일시정지면 좁니다. 움직임 줄이기 설정이면 표정만 바꾸고 움직이지 않습니다.

에이전트 상세에서 heartbeat를 켜고 끄며 간격(분)을 바꿉니다. 새 에이전트는 꺼져 있고 간격은 하네스 Role의 기본값(`role.json`의 `heartbeatMinutes`, Lead 60분·연구원 30분)이며(migration 0008 전에 생긴 에이전트도 같은 값으로 채움), 화면에 서버가 정한 다음 heartbeat 시각이 보입니다. 서버는 주입한 시계로 몇 초마다 지난 heartbeat를 찾아 `heartbeat` 사유의 깨우기를 남기고, 실행 시도는 다른 깨우기와 같은 admission이 만들므로 기다리는 다른 깨우기와 실행 시도 하나로 합쳐집니다. 대기 중인 heartbeat 깨우기가 있으면 새로 쌓지 않고, 서버가 멈췄던 동안 지난 heartbeat는 한 번으로 합치며, 다음 heartbeat는 깨운 때부터 간격만큼 뒤입니다. 켜거나 간격을 바꾸면 그때부터 간격만큼 뒤에 깨우고, 끄면 더 깨우지 않습니다(이미 남은 heartbeat 깨우기는 다른 깨우기처럼 전달됨). 조직·에이전트 일시정지 중에는 깨우지 않고 재개 뒤 예정이 지나 있으면 한 번 깨우며, 최종 완료·중단 조직에서는 설정도 바꿀 수 없습니다. 가짜 프로바이더는 heartbeat로만 깨어나면 맥락만 읽고 답장하지 않습니다.

에이전트는 조직 도구 `write_memory`·`recall_memory`로 조직 기억(같은 조직 에이전트가 함께 회수)과 에이전트 기억(쓴 에이전트만 회수)을 쓰고 꺼냅니다. 범위의 조직·에이전트와 출처(쓴 에이전트·실행 시도)는 실행 시도별 토큰에서만 정하며 입력에는 조직을 고르는 값이 없으므로, 다른 조직이나 같은 조직의 다른 에이전트 기억은 회수되지 않습니다. 첫 판 Memory port는 기법 없이 저장과 회수만 합니다. 회수는 최근에 쓴 것부터 최대 50개이며, 검색어는 대소문자를 가리지 않는 글자 그대로의 부분 문자열입니다(`%`·`_`도 그 글자). 기억을 쓰면 내용 없이 `memory.written` Event가 남습니다. 기억을 보는 대시보드 화면·명시적 공유·기억 기법은 기억 이슈에서 정합니다.

서버가 실행 시도 도중 멈추면 그 실행 시도는 `서버 재시작`으로 끝나고 받은 깨우기는 다시 대기해 새 실행 시도·새 토큰으로 전달됩니다. 정상 종료는 프로바이더를 취소한 뒤 바로 그렇게 저장하고, 프로세스가 죽었으면 다음 시작 때 프로바이더를 부르기 전에 실행 시도마다 종료·깨우기 복원·Event를 한 transaction으로 저장합니다. 끝난 실행 시도의 상세는 받았던 깨우기를 그대로 보여 줍니다. 사용자 제어로 이미 취소를 요청받은 실행 시도는 그 취소대로 `취소됨`으로 끝나고 입력을 다시 보내지 않습니다. 다시 받은 실행 시도가 이미 남긴 답장·작업·기억 등을 되풀이하지 않도록 모든 쓰기 조직 도구는 `Idempotency-Key` header를 받습니다. 키와 처음 결과는 효과와 같은 transaction에 남고, 그 에이전트의 같은 키는 처음 결과를 다시 돌려주며 기록·Event·깨우기를 새로 남기지 않습니다. 같은 키로 다른 도구나 다른 입력을 보내면 409 `idempotency_conflict`이고, 키와 결과는 지우지 않습니다. Role·단계 규칙은 같은 키여도 먼저 검사합니다. 가짜 프로바이더는 받은 깨우기 묶음과 도구별 쓰기 순서로 키를 정하므로 새 깨우기가 섞여 다시 받으면 새 효과가 됩니다. 초기 연구 승인 요청·결과 제출(예전 조직은 목표 기록도)처럼 단계를 바꾸는 쓰기 뒤에 멈췄으면, 가짜 Lead는 다시 받은 깨우기와 저장된 단계·목표로 이미 한 쓰기를 알아보고 건너뛰어 그 흐름의 남은 단계부터 이어 갑니다. 예전 조직에서 다시 대기한 깨우기에 다른 목표 메시지가 합쳐져도 기록한 목표의 흐름을 이어 가고, 다른 목표는 반영하지 않았다고 답장에 밝힙니다. 조직 도구 밖의 외부 효과는 막지 않으며, 실제 프로바이더가 키를 정하는 방식은 실제 adapter 판에서 정합니다.

서버는 이름 붙은 프로바이더 연결 여러 개를 받고, 실행 시도마다 그 에이전트의 연결에 맡깁니다. 지금 연결은 가짜 프로바이더뿐이며 `pnpm dev`는 `가짜 프로바이더` 하나, E2E 서버는 같은 adapter의 연결 둘(`BABOJUBOT_FAKE_PROVIDERS=2`)을 띄웁니다. 에이전트마다 프로바이더와 모델(비우면 `기본 모델`, 실행 시도 요청의 모델이 비어 프로바이더가 기본 모델을 씀)이 있고, migration 0021 전에 생긴 에이전트는 가짜 프로바이더입니다. 연결마다 모델 목록을 내며 받아 오지 못하거나 빈 목록이면 연결의 고정 목록을 씁니다. 전역 설정에서 Lead 기본·작업자 기본 프로바이더·모델을 정합니다. Lead 기본값은 이후에 만드는 Lead가 복사하고(새 연구 조직 창의 Lead 칸도 이 값으로 채워짐), 작업자 기본값은 Lead가 작업자의 프로바이더를 비운 요청에 쓰입니다(이미 있는 에이전트와 이미 올라온 요청은 그대로). Lead는 조직 도구 `list_providers`로 작업자 기본값과 연결마다 이름·모델 목록을 읽고(동시 실행 상한은 담지 않음), 초기 연구 승인 요청의 팀 구성 줄과 작업자 추가에 프로바이더·모델을 제안합니다. 프로바이더를 비우면 요청할 때의 작업자 기본값이 그 제안으로 고정되고(승인 전에 기본값을 바꿔도 그대로), 모델만 적거나 등록되지 않은 연결·모델은 422(`unknown_provider`·`unknown_model`)입니다. 승인 요청 상세와 Inbox 상세의 결정 영역에는 승인하면 생길 작업자마다 프로바이더·모델 Select가 Lead 제안으로 채워져 있어, 사용자가 작업자마다 바꾸고(`변경` 배지·되돌리기, 화면을 떠나도 초안 유지) 승인합니다. 요청은 Lead가 올린 그대로 남고, 승인하면 결정에 작업자마다의 값(`decidedWorkers`)이 함께 저장되며 그 값으로 작업자가 생깁니다. 결정 뒤에는 작업자마다 `Lead 제안`과 `결정`을 나란히 보이고 다른 칸에만 `변경`을 붙입니다. migration 0022 전에 결정한 요청에는 이 기록이 없고, 그 전에 올라온 대기 요청은 결정 때의 작업자 기본값을 씁니다. 에이전트 상세의 `프로바이더`에서 사용자만 바꾸며, 다음 실행 시도부터 적용되고 진행 중인 실행 시도는 그대로 끝납니다. 프로바이더를 바꾸면 모델은 `기본 모델`이 되고, 다음 실행 시도는 이전 세션을 이어받지 않습니다(모델만 바꾸면 이어 감). 실행 시도 목록 행과 상세에는 admission이 고정한 `프로바이더 · 모델`이 보이고, 바꾼 일은 `agent.provider_changed` Event로 활동에 남습니다. 연결마다 동시 실행 상한(기본 2, 0은 무제한)을 전역 설정의 stepper로 바꿉니다. 조직이 달라도 같은 연결의 진행 중 실행 시도가 상한에 닿으면 깨우기는 실행 시도 없이 기다렸다가 자리가 나면(실행 시도 종료·상한 증가) 시작하고, 상한을 줄여도 진행 중인 실행 시도는 끊지 않습니다. 에이전트당 실행 시도 하나는 그대로입니다. 전역 설정은 조직 Event로 남기지 않고, 다른 탭에는 Event stream의 `settings_changed` 신호로 다시 불러오게 합니다.

프로바이더 연결은 끼워 넣기·세션 이어가기·재개 때 지침 다시 넣기·실행 시도별 토큰·비용 보고·미리 압축 지원을 기본값 없이 모두 선언하고(빠지면 서버 시작 오류), 공통 검사(`describeRuntimeContract`)가 선언과 동작이 맞는지 확인합니다. 연결마다 모델을 부르지 않는 준비 확인이 `준비됨`·`준비안됨`·`알수없음`과 이유 코드를 내며, 서버 시작·전역 설정 화면 열기·`다시 확인`·제품 로그인이 필요해 실패한 실행 시도 뒤에 확인해 저장합니다(migration 0023, 실행 시도는 확인을 기다리지 않고 다른 연결로 대신 돌리지 않음). 전역 설정의 연결 행에는 배지·이유·`다시 확인`과, 이유가 제품 로그인 없음일 때만 `로그인 명령 복사`가 있고, 새 연구 조직 창·승인 표·에이전트 설정의 프로바이더 칸 옆에도 배지가 보입니다(준비안됨 연결도 고를 수 있음). Lead의 `list_providers` 결과에도 준비 상태가 붙습니다. 세션은 (에이전트, 작업)마다 저장합니다. 받은 깨우기가 모두 한 작업(작업 배정·완료·댓글)이면 그 작업의 세션, 섞였거나 작업이 없으면 에이전트 세션을 이어 가고, 세션을 만든 연결이나 지침 bundle 버전이 다르면 새 세션입니다. 에이전트의 프로바이더를 바꾸면 그 에이전트의 세션이 모두 비워지고(모델만 바꾸면 그대로), 바꾸기 전에 시작한 실행 시도가 늦게 끝나도 세션을 되살리지 않습니다. 이어 가지 못하는 세션이면 프로바이더가 같은 실행 시도 안에서 새 세션으로 시작하고 진행 활동으로 알립니다. 실행 시도 상세의 `사용량` 표는 입력·출력·캐시 읽기·캐시 쓰기 토큰과 비용(`추정`)을 각각 값 또는 흐린 `보고 안 됨`으로 보입니다. 가짜 프로바이더는 이 모두를 설정으로 바꿀 수 있고(`BABOJUBOT_FAKE_PROVIDER_SETTINGS`, E2E 서버의 `fake-2`는 끼워 넣기 없음·제품 로그인 없음), 실제 프로바이더 연결은 판 2 후속 이슈입니다.

실행 시도 admission·종료 저장의 DB 오류는 100ms부터 최대 5초 간격의 backoff로 서버 종료까지 재시도합니다. 종료 결과 저장이 실패하면 같은 결과를 보관해 다시 저장하며 프로바이더를 다시 호출하지 않습니다. 서버 종료는 backoff 대기를 취소합니다. 종료까지 DB 장애가 이어지거나 프로세스가 죽으면 메모리의 종료 결과는 보존되지 않으며, 다음 시작 때 남은 실행 시도는 위처럼 `서버 재시작`으로 끝나고 입력을 다시 처리합니다.

조직 도구마다의 사실은 contracts의 도구 목록 한 곳에 있고 서버 경로·가짜 프로바이더의 도구 client·Role·단계 판정이 이 목록을 씁니다([전체 구조](docs/architecture.md#agent--control-plane-조직-도구)). Role·단계별 "지금 쓸 수 있는 도구 목록"도 같은 판정으로 만들지만 아직 실행 시도 요청에 싣지는 않습니다. 에이전트 지침과 도구 설명은 영어이고 사용자가 보는 조직 기록은 한국어로 쓰게 합니다([언어 원칙](docs/features.md)). 이 전환 뒤에 만든 조직·작업자만 영어 지침을 받고 기존 사본은 그대로입니다. 실행 시도 요청은 서버의 조립 module 하나가 만들며 workspace는 아직 없습니다. 프로바이더 adapter의 약속은 adapter마다 같은 공통 검사(`@babojubot/runtime/runtime-contract`)가 확인하고, 가짜 프로바이더가 가짜 도구 HTTP 서버를 상대로 통과합니다.

## 개발 시작

Node.js 24.x, pnpm 10.33.0 및 Git을 사용합니다. GitHub 이슈 작업에는 인증된 `gh`가 필요합니다.

```bash
pnpm install
pnpm dev          # 서버(http://127.0.0.1:3100, 가짜 프로바이더 데모 시나리오)와 대시보드(http://127.0.0.1:5173)
pnpm test         # 패키지별 Vitest. 서버·DB 테스트는 실행마다 embedded Postgres 하나를 띄우고 테스트마다 DB를 복제합니다.
pnpm test:e2e     # Playwright E2E(대시보드는 프로덕션 빌드로 띄움). 처음 한 번 `pnpm --filter @babojubot/web exec playwright install chromium`
pnpm typecheck
pnpm lint
pnpm check        # Markdown 로컬 링크 검사
```

### 데모 시나리오

`pnpm dev`의 서버는 기본으로 가짜 프로바이더를 씁니다. 실제 모델·유료 API·자격 증명 없이 대시보드(http://127.0.0.1:5173)에서 판 1 흐름을 처음부터 끝까지 해 볼 수 있습니다. 개발 DB(`.babojubot/postgres`)는 지우지 않으므로 전에 만든 조직도 그대로 보입니다.

1. 레일의 `＋`(새 연구 조직)를 누르고 조직 이름, 연구 목표 `공개 자료로 오류 유형을 정리한다`, 완료 기준 `유형 목록과 근거 메모`를 적어 만듭니다.
2. Lead 대화가 열리고, 생성으로 깨어난 Lead가 초기 연구 승인을 요청했다고 답합니다. 완료 기준을 비워 두면 Lead가 목표에서 만든 기준을 같은 요청에 제안합니다.
3. Inbox에서 초기 연구 승인 요청을 열어 계획·팀·연구 환경 명세를 보고 승인합니다. 작업자 2명이 생기고 Lead가 한 명에 작업 하나씩 맡깁니다.
4. 조직 › 작업에서 끝난 작업의 자기 보고·산출물과 연결된 연구 노드(누르면 연구 지도)를 봅니다. 산출물이 있어도 연구는 `연구 진행` 그대로입니다.
5. 조직 › 에이전트의 조직도에서 Lead 아래 작업자 2명을 보고, 카드를 눌러 에이전트 상세로 갑니다. 이름을 눌러 바꾸고(Enter 저장, Esc 취소) 얼굴을 눌러 꾸밀 수 있으며, heartbeat를 켜고 끌 수 있습니다. 조직 › 설정에서 `작업자 추가` 승인 정책을 켭니다.
6. 조직 › 대시보드에서 조직을 일시정지하고 Lead 대화에 `작업자 추가: researcher`를 보냅니다. 메시지는 입력창 위 `줄 세운 메시지`에 남습니다. 재개하면 Lead가 작업자 추가 승인을 요청하고, Inbox에서 승인하면 조직도의 작업자가 3명이 됩니다.
7. Lead 대화에 `결과 제출 부탁해요`를 보내면 Lead가 산출물을 근거로 결과를 제출합니다. Inbox에서 결과 제출을 열어 요약·완료 기준·근거 산출물을 보고(전체 내용은 `원래 화면에서 자세히 보기`) `최종 완료`를 확정합니다. 의견을 적어 수정 요청하면 Lead가 다시 제출합니다.

[데모 흐름 E2E](apps/web/e2e/demo-flow.spec.ts)가 같은 순서를 화면 조작으로 지킵니다(`pnpm test:e2e demo-flow`). 그 밖에 Lead 대화의 `실패 연습`·`실행 유지 연습` 부탁으로 실패한 실행 시도와 실행 중인 에이전트를 볼 수 있고, 작업 댓글로 같은 부탁을 하면 그 작업의 작업자가 그렇게 합니다(홈의 걱정하는 얼굴·작업 말풍선 확인용). 위 흐름은 모두 기본 대화에서 진행되며, 대화 목록의 `＋ 새 대화`로 다른 주제를 보내면 가짜 Lead가 그 대화에 답하고, 승인 직후 분담·작업 완료 보고처럼 스스로 알리는 메시지는 기본 대화에 옵니다.

`pnpm install`은 `@embedded-postgres/linux-x64`의 postinstall만 실행합니다(`pnpm-workspace.yaml`의 `onlyBuiltDependencies`). 이 script가 Postgres native library의 symlink를 만들기 때문에 `--ignore-scripts`로 설치하면 embedded Postgres가 뜨지 않습니다. 다른 OS·아키텍처에서는 해당 `@embedded-postgres/*` 패키지를 같은 목록에 추가합니다.

[CI](.github/workflows/scaffold.yml)는 `main` 대상 PR의 생성·갱신·재개와 `main` push에서 문서 검사·타입·lint·테스트·빌드·E2E를 실행합니다. 바뀐 파일이 Markdown뿐이면 문서 검사만 돌리고 나머지 검사는 건너뛴 채 성공으로 표시합니다.
기능 브랜치 push만으로는 중복 실행하지 않고, 같은 PR의 오래된 실행은 취소합니다.
`main`의 필수 검사는 workflow의 `ci / …` job 전체이며, 실행 환경과 검사 이름은 workflow를 기준으로 합니다.
표준 GitHub-hosted runner를 쓰는 공개 저장소의 실행 시간은 무료입니다([GitHub 과금 문서](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
실패한 E2E의 trace 등 결과물만 3일 보관하며 artifact·cache 저장 공간 한도는 별도로 관리합니다.

데이터베이스는 `DATABASE_URL`이 있으면 그 외부 Postgres에 연결만 하고, 없으면 embedded Postgres를 `.babojubot/postgres`(`BABOJUBOT_HOME`으로 변경)에 띄웁니다. 둘 다 시작할 때 같은 migration을 적용합니다. 운영은 `pnpm build` 후 `DATABASE_URL=… pnpm start`로 서버가 빌드한 대시보드까지 제공합니다. 그 밖의 설정(`PORT`, `HOST`, `EMBEDDED_POSTGRES_PORT`, `BABOJUBOT_FAKE_PROVIDERS`)은 [`apps/server/src/main.ts`](apps/server/src/main.ts) 머리에 있습니다. 스택은 [ADR-0004](docs/adr/0004-paperclip-aligned-stack.md)를 따릅니다.

패키지별 책임은 [전체 구조](docs/architecture.md#패키지-구성), 수정할 코드와 테스트의 위치는 [코드 지도](docs/agents/code-map.md)에서 확인합니다.
