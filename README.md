# BaboJUBot

연구 목표마다 독립적인 AI 조직을 구성하고, Research Lead와 작업자들이 협력하는 범용 연구 운영 프로젝트입니다. 초기 계획·팀 승인, 진행 관찰, 사용자 개입, 조직별 기억, 사용자 최종 검토를 지원하는 방향으로 개발합니다.

현재 상태는 **판 1 walking skeleton**입니다. 대시보드에서 연구 조직을 만들면 전용 Research Lead가 함께 생기고 `목표 설정` 단계로 시작하며, Event stream으로 사이드바와 홈에 바로 나타납니다. Lead 대화에 메시지를 보내면 Lead가 깨어나 실행 시도를 받고, 모델을 부르지 않는 가짜 실행기가 실행 시도별 토큰으로 조직 도구를 호출해 답장합니다. 활동·실행 시도 상세·에이전트 상세에서 그 실행 시도를 볼 수 있습니다. 실제 실행기 adapter와 실제 모델 호출은 아직 없습니다.

Lead 대화에 `목표: …`와 `완료 기준: …` 줄을 보내면 가짜 Lead가 목표를 기록해 조직을 `계획 수립`으로 넘기고, 초기 연구 계획·팀 구성·연구 환경 명세·연구 흐름 템플릿을 하나의 초기 연구 승인 요청으로 올립니다. 사용자는 Inbox에서 승인 요청 상세를 열어 승인·반려·수정 요청을 합니다. 승인하면 조직이 `연구 진행`이 되고 제안한 작업자들이 생기며, 반려·수정 요청은 `계획 수립`으로 돌아가 사유와 함께 Lead를 깨웁니다. 승인 전에는 작업 생성·작업자 추가 도구를 제품이 거부하고 Event log에 남깁니다. 각 에이전트는 [하네스 라이브러리](harness/README.md)에서 복사한 자기 Role·Soul·Skill 사본을 갖고(Lead는 조직 생성 때, 작업자는 승인 때나 연구 중 추가될 때), 에이전트 상세의 Role·Soul·Skill 탭에서 봅니다.

`연구 진행`에서는 Lead가 작업(담당·부모 작업)을 만들어 작업자에게 맡기고, 할당이 담당 작업자를 깨웁니다. 가짜 실행기는 승인 직후 작업자마다 작업 하나를 맡기며, 작업자는 착수 → Markdown 산출물 기록 → 자기 보고 요약과 함께 완료합니다. 작업 완료는 부모 작업 담당자를, 부모가 없으면 작업을 만든 에이전트를 깨우고(자기 자신은 깨우지 않음), 같은 조직 에이전트 간 메시지는 받는 에이전트를, 사용자의 작업 댓글은 담당자를 깨웁니다. 작업 상태는 `할당됨 → 진행 중 → 완료`입니다. 착수는 담당자만 할당됨에서 할 수 있고, 완료는 담당자와 Lead(조정)가 할당됨·진행 중 어디서든 한 번 할 수 있으며 다시 완료하면 409입니다. 산출물은 첫 판에서 Markdown·텍스트 본문을 DB에 그대로 둡니다. 대시보드의 조직 › 작업에서 목록·작업 상세(자기 보고·댓글 thread·산출물·연결된 연구 노드)·산출물 단건 보기를 Event stream으로 새로고침 없이 봅니다.

연구 지도는 연구 노드·주 연결(노드의 주 부모, 최대 하나)·보조 연결·작업의 연구 노드 연결(0~1)로 이루어집니다. 에이전트는 `연구 진행`에서 조직 도구로 노드를 만들고 고치며, 주 부모를 지정(주 부모가 없을 때만)·변경하고, 보조 연결을 더하고, 작업을 노드에 연결·재연결·해제합니다. 노드·보조 연결 종류는 조직 사본 연구 흐름 템플릿이 선언한 것만 받고, 주 연결 순환(자기 자신·후손을 주 부모로)과 자기 자신과의 보조 연결은 거부합니다. 보조 연결은 개수·순환·중복 제한이 없습니다. 노드 상태는 `제안됨 → 진행 중 → 완료/기각됨`이며 삭제 대신 `폐기`합니다. 폐기는 자손·연결·작업을 그대로 두고 폐기 취소하면 폐기 직전 상태로 돌아가며, 폐기된 노드는 다른 편집과 새 연결의 대상이 되지 않으며, 같은 폐기·폐기 취소를 다시 요청하면 바뀌는 것 없이 성공합니다. 구조 편집은 모두 조직 행 잠금 아래에서 최신 주 연결을 읽어 검사하므로 동시 편집도 순환을 남기지 않습니다. 편집마다 편집 기록(편집자·대상·요약)과 Event가 남고, 사용자 편집은 Lead를 깨웁니다. 가짜 작업자는 맡은 작업마다 템플릿의 첫 종류로 노드를 만들어 작업을 연결합니다.

대시보드의 조직 › 연구 지도는 React Flow와 Dagre로 주 연결 트리를 배치하고 보조 연결을 연한 점선으로 겹쳐 그리며, 같은 두 노드 사이의 보조 연결은 나란히 벌려 그립니다. 연결은 노드 아래 레이어에 한 번 그리고 선택한 노드 주변만 위에 강조해, 수백 노드에서도 화면 끌기와 선택이 지도를 다시 그리지 않습니다(성능 측정은 `MAP_PERF=1 pnpm test:e2e research-map-perf`). 노드를 고르면 오른쪽(1024px 미만에서는 아래) 상세 패널에서 종류·상태·주 부모와 하위·보조 연결(관계 ID별)·연결 작업과 산출물·편집 기록을 보고, 초기 연구 승인 뒤 최종 완료·중단 전까지 노드 추가·제목·상태 수정·주 부모 변경·보조 연결 추가·폐기와 폐기 취소를 명시 폼으로 합니다. 노드를 끌어 옮긴 위치는 이 화면의 보기 상태라서 저장하지 않고 편집으로 기록하지도 않습니다.

Lead는 `연구 진행`에서 완료 기준을 충족했다고 판단하면 요약과 근거 산출물(같은 조직의 산출물)을 묶어 결과를 제출하고, 조직은 `결과 검토 중`이 됩니다. 제출은 그때의 목표·완료 기준을 검토 기준으로 고정한 새 기록이며 Inbox와 조직 › 결과 검토에 나옵니다. 사용자는 결과 제출 상세에서 요약·완료 기준·근거 산출물(단건 페이지로 열림)을 보고 결정합니다. 수정 요청은 의견과 함께 `연구 진행`으로 돌리고 Lead를 깨우며, 다시 제출하면 직전 제출을 가리키는 새 제출이 되고 옛 제출의 내용과 결정은 그대로 남습니다. 최종 완료는 사용자 제어 명령으로만 일어나며 Lead의 조직 도구에는 최종 완료·승인 정책 변경 도구가 없습니다. 결과 검토 중에는 연구 쓰기 도구가 닫히지만 사용자 메시지·지도 편집으로 Lead가 깨어나 조회·답장은 할 수 있습니다. `최종 완료`(그리고 `일시정지`·`중단`) 조직에서는 실행 시도 admission이 깨우기 사유와 상관없이 새 실행 시도를 시작하지 않고 깨우기만 남겨 두며, 서버를 다시 시작해도 마찬가지입니다. 최종 완료 전에 이미 시작한 실행 시도는 끊지 않고 스스로 끝나게 두되 그 사이 연구 쓰기는 거부됩니다. 가짜 Lead는 사용자가 Lead 대화로 `결과 제출`을 부탁하면 완료한 작업의 산출물을 근거로 제출하고, 수정 요청을 받으면 의견을 요약에 적어 다시 제출합니다.

조직마다 승인 정책이 있고 첫 판의 항목은 `작업자 추가` 하나이며 새 조직은 꺼져 있습니다. 사용자는 조직 › 설정의 체크박스로만 바꾸고(조직 도구에는 정책 변경이 없음), 바꿀 때마다 전후 값이 Event log에 남으며 다른 탭에도 새로고침 없이 반영됩니다. Lead는 `연구 진행`에서 하네스 라이브러리의 작업자 Role 이름으로 작업자를 추가합니다. 정책이 꺼져 있으면 곧바로 작업자와 그 작업자만의 사본이 생기고, 켜져 있으면 호출 때 읽은 Role·Soul·Skill 내용을 고정한 승인 요청만 Inbox에 올라가며 도구 결과는 `승인 대기`입니다. 정책은 조직 행 잠금 아래에서 읽으므로 정책 변경과 동시에 온 호출도 바뀌기 전이나 뒤의 정책 하나로 갈립니다. 사용자가 승인하면 그 내용으로 작업자가 생기고, 반려하면 아무것도 만들지 않으며, 어느 쪽이든 사유와 함께 Lead를 깨우고 연구 단계는 바뀌지 않습니다. 작업자 추가에는 수정 요청이 없고, 연구 단계가 바뀐 뒤에도 결정할 수 있습니다. 호출마다 별도 요청이라 여러 요청이 함께 기다릴 수 있고, 정책을 꺼도 이미 기다리는 요청은 사용자가 결정할 때까지 남습니다. 가짜 Lead는 Lead 대화의 `작업자 추가: <Role>` 부탁(Role이 없으면 `researcher`)으로 작업자를 추가합니다. `작업자 추가`·`결과 제출` 부탁은 메시지 전체가 그 명령(`… 해 주세요`·`… 부탁해요` 같은 끝맺음까지)일 때만 따르고, 부정문(`작업자 추가하지 마세요`)이나 다른 말이 섞인 메시지에는 답장만 합니다.

사용자는 조직 › 대시보드에서 조직을 일시정지·재개·중단하고, 에이전트 상세에서 에이전트 하나를 일시정지·재개합니다. 모두 즉시 효력이 있는 제어 명령이며 Event log에 남고 다른 탭에도 새로고침 없이 반영됩니다. 일시정지와 중단은 진행 중 실행 시도에 취소를 요청하고, 요청한 순간 그 실행 시도의 토큰은 읽기까지 막히며, 실행기가 정리를 끝내면 실행기가 무엇을 돌려주든 `취소됨`으로 끝납니다. 정리가 끝나기 전에는 그 에이전트의 다음 실행 시도가 시작되지 않습니다. 일시정지 중 생긴 깨우기는 남았다가 재개 때 에이전트별 실행 시도 하나로 전달되고, 사용자 제어로 취소된 실행 시도에 묶였던 입력은 다시 보내지 않습니다. 조직 일시정지는 최종 완료 전 어느 단계에서든 걸 수 있고 재개하면 직전 단계로 돌아가며, 에이전트 일시정지는 그 에이전트만 막고 조직을 재개해도 풀리지 않습니다. 중단은 되돌릴 수 없고 이후 어떤 실행 시도도 시작하지 않습니다. 최종 완료·중단 조직의 제어 버튼은 보이지만 누를 수 없고 서버도 409 `organization_closed`로 거부합니다. 일시정지 중에 초기 연구 승인이나 결과 검토를 결정하면 조직이 함께 재개되며(최종 완료는 곧바로 완료), 작업자 추가 결정은 일시정지를 풀지 않습니다. 중단된 조직의 초기 연구 승인·결과 결정은 받지 않고 Inbox에서도 빠집니다. Lead 대화에서는 전달 방식으로 `다음 실행 시도에 반영`(기본)이나 `중단하고 반영`을 고릅니다. `중단하고 반영`은 실행 시도 중단 제어 명령과 메시지를 한 요청에서 함께 저장해 Event 두 개를 남기고, Lead의 진행 중 실행 시도를 취소한 뒤 그 메시지를 다음 실행 시도의 깨우기 사유로 전달합니다. 끝난 조직에서는 제어 명령이므로 고를 수 없습니다.

Lead 대화 메시지(보고·질문), 승인 요청(초기 연구 승인·작업자 추가), 결과 제출, 실패한 실행 시도는 그 기록·Event와 같은 transaction에 알림 outbox 항목을 남깁니다. 서버는 commit 뒤 Event를 신호로, 그리고 시작 때와 5초마다 outbox를 확인해 보낼 차례인 알림을 짧게 가져가(claim) transaction 밖에서 채널로 보내고, 그 claim이 그대로일 때만 결과를 남깁니다. 전송이 실패하면 1초부터 두 배씩(최대 5분) 미뤄 다시 보내고, 정산 전에 서버가 멈추면 claim이 만료된 뒤 다시 보냅니다. 첫 판의 채널은 가짜 채널뿐이며 알림마다 전송 기록 하나를 남깁니다(`GET /api/channels/fake/messages`, outbox 상태는 `GET /api/notifications`). 가짜 채널의 승인 요청 알림에는 승인 결정으로 답할 수 있고(`POST /api/channels/fake/messages/:id/reply`), 답은 전송 기록이 가리키는 조직·승인 요청으로 대시보드와 같은 승인 결정 HTTP 명령을 보내 그 응답을 그대로 돌려줍니다. 사용자 메시지·정상 완료·사용자 취소·서버 재시작은 알리지 않고, 이 판 전의 사건은 소급해 보내지 않습니다.

Inbox는 레일·768px 미만 상단 바의 Inbox 버튼과 조직 카드의 `주의 n →`로 여는 패널 하나입니다(1280px 이상은 본문 오른쪽 340px, 그보다 좁으면 항목을 고르면 닫히는 drawer). 결정을 기다리는 승인 요청·결과 제출과 실패한 실행 시도(실행 시도마다 하나, 뒤 실행 시도가 성공해도 남음)를 한 목록에 두고, 범위(전체 조직 / 현재 조직)와 필터(주의 필요·전체·읽지 않음·보관됨)마다 개수를 보입니다. 주의 필요는 결정 대기 항목과 보관하지 않은 읽지 않은 실패이며 레일·조직 아바타의 수도 같은 판정입니다. 전체는 보관하지 않은 모든 항목입니다. 읽음·보관은 원본과 따로 저장하는 정리 상태라 결정·단계·깨우기를 바꾸지 않고, 바꿀 때마다 Event log에 남아 다른 탭도 따라옵니다. 보관은 끝난 일인 실패한 실행 시도에만 있으며, 결정을 기다리는 승인 요청·결과 제출은 보관할 수 없고(서버가 422 `archive_not_allowed`로 거부) 결정하면 Inbox에서 빠집니다. 이 판 전에 실패한 실행 시도는 읽음으로 들어옵니다. 항목을 고르면 Inbox 상세(`/inbox/<조직>/<종류>/<ID>`)가 열려 요약을 보고 그 자리에서 결정하거나(원래 상세와 같은 결정 폼·같은 명령), `원래 화면에서 자세히 보기`로 승인 요청·결과 제출·실행 시도 상세에 가서 전체 내용을 봅니다. 결정하면 그 자리에 결정 기록이 남고 다음 항목으로 넘어가지 않습니다. 항목을 열면 읽음이 되고(결정 대기 항목은 결정할 때까지 주의 필요에 남음), 패널에서는 항목을 체크하면 나타나는 `모두 읽음`으로 체크한 항목만 읽음으로 바꿉니다. 읽은 항목은 `읽지 않음`으로 되돌릴 수 있고, 실패의 보관은 패널 행과 상세에 있습니다. 메시지 앱(가짜 채널) 알림의 링크도 승인 요청·결과 제출·실패는 Inbox 상세, Lead 메시지는 대화로 갑니다. 레일의 전역 설정에는 실행기 adapter·연구 환경 템플릿·비밀값·메시지 앱 연결의 자리만 있습니다. 가짜 Lead는 `실패 연습` 부탁을 받으면 아무것도 쓰지 않고 실행 시도를 실패로 끝냅니다.

조직 › 대시보드는 조직 제어와 결정 대기 항목 아래에 지표(상태별 작업·실행 시도·산출물 수, 14일 실행 성공률), 14일 차트(시작한 날 기준 실행 시도의 지금 상태별 수, 끝난 날 기준 성공률, 만든 날 기준 작업의 지금 상태별 수, 기록한 날 기준 산출물 수), 최근 활동 10개를, 오른쪽에 실행 중인 에이전트를 보입니다. 모두 서버 요약 하나(`GET /api/organizations/:id/dashboard?timeZone=`)를 한 읽기 snapshot에서 만들어 수와 목록이 서로 맞고, 다른 조직의 기록은 세지 않습니다. 날짜는 브라우저 시간대의 달력 날짜로 자르며 오늘(지금까지)을 포함한 14일이고, 기록이 없는 날도 0으로 그립니다(서머타임으로 23·25시간인 날도 하루). 작업 차트는 그날의 과거 상태가 아니라 그날 만든 작업의 지금 상태입니다. 성공률은 완료 / (완료 + 실패)이며 취소·서버 재시작은 세지 않고, 끝난 시도가 없으면 `—`입니다. 실행 시도의 성공은 연구의 최종 완료가 아닙니다. 실행 중인 에이전트는 진행 중 실행 시도 전부이며 취소를 요청받아 정리 중인 것도 끝날 때까지 `취소 중`으로 남습니다. 차트 막대는 hover·keyboard focus로 그날의 수를 보이고 `숫자로 보기` 표가 같은 값을 모두 담습니다. 홈은 조직 수와 실행 중인 실행 시도 수(`GET /api/overview`, 모든 조직을 SQL 하나로 셈)를 보이고, 조직 카드에도 그 조직의 수를 보입니다. 화면의 `실행 중`은 조직 제어와 같이 취소 정리 중을 뺀 수이며 정리 중은 따로 보입니다. 모두 Event가 오면 다시 불러오고, 날짜가 바뀌는 자정에도 다시 불러옵니다. 조직 › 활동의 에이전트 필터는 주소(`?agent=`)에 남아 실행 중 카드의 `활동 보기`로 바로 옵니다. 가짜 Lead는 `실행 유지 연습` 부탁을 받으면 아무것도 쓰지 않고 취소될 때까지 실행 시도를 끝내지 않습니다.

사용자 API에는 로그인이 없습니다. 로컬 신뢰 운영이며 같은 기기에서 도는 프로그램은 사용자와 구별되지 않습니다([전체 구조](docs/architecture.md#제품-불변-조건-강제-위치)).

사용자는 에이전트 상세 › Role·Soul·Skill 탭에서 그 에이전트의 사본 하나를 편집·저장·취소합니다. 저장은 본문 전체와 편집을 시작한 revision 번호를 보내며, 조직 행 잠금 아래에서 사본·새 revision(번호·편집자·서버 시각·전체 본문)·Event·편집 사유의 Lead 깨우기를 한 transaction으로 남깁니다. 같은 내용의 저장도 revision을 남깁니다. 그사이 다른 저장이 있었으면 `revision_conflict`로 거부하고 편집 내용은 화면에 남으며, 최종 완료·중단 조직은 거부하고, 다른 조직의 에이전트·사본·revision은 없는 것처럼 404입니다. Skill은 라이브러리와 같은 frontmatter(디렉터리 이름과 같은 name, description)를 지켜야 저장됩니다. 복사로 생긴 처음 내용이 revision 1(편집자 `복사로 생김`)이고(migration 0009 전 사본도 그렇게 채움), 복사 출처는 편집해도 바뀌지 않습니다. 같은 Role의 다른 에이전트 사본과 하네스 라이브러리는 그대로입니다. 진행 중 실행 시도는 시작할 때 받은 지침으로 끝나고, 그 에이전트의 다음 실행 시도는 바뀐 사본 내용의 bundle 버전을 받아 이전 세션 없이 시작합니다. bundle 버전은 내용에서만 정하므로 같은 내용 저장이나 중간 실행 없이 원래 내용으로 돌아온 경우에는 세션을 이어 갑니다. revision 목록과 예전 revision 본문은 읽기 전용이며 되돌리기·diff와 사본 편집 조직 도구는 없습니다. 저장하지 않은 편집이 있으면 다른 파일·화면으로 옮기거나 새로고침할 때 버릴지 묻습니다.

#54 전에 만든 개발 DB의 조직은 Lead 사본이 없어 지침 bundle 버전 없이 실행됩니다. 사본이 필요하면 `.babojubot/postgres`를 지우고 새로 만듭니다. 구조는 [전체 구조](docs/architecture.md)를 따릅니다.

에이전트 상세에서 heartbeat를 켜고 끄며 간격(분)을 바꿉니다. 새 에이전트는 꺼져 있고 간격은 하네스 Role의 기본값(`role.json`의 `heartbeatMinutes`, Lead 60분·연구원 30분)이며(migration 0008 전에 생긴 에이전트도 같은 값으로 채움), 화면에 서버가 정한 다음 heartbeat 시각이 보입니다. 서버는 주입한 시계로 몇 초마다 지난 heartbeat를 찾아 `heartbeat` 사유의 깨우기를 남기고, 실행 시도는 다른 깨우기와 같은 admission이 만들므로 기다리는 다른 깨우기와 실행 시도 하나로 합쳐집니다. 대기 중인 heartbeat 깨우기가 있으면 새로 쌓지 않고, 서버가 멈췄던 동안 지난 heartbeat는 한 번으로 합치며, 다음 heartbeat는 깨운 때부터 간격만큼 뒤입니다. 켜거나 간격을 바꾸면 그때부터 간격만큼 뒤에 깨우고, 끄면 더 깨우지 않습니다(이미 남은 heartbeat 깨우기는 다른 깨우기처럼 전달됨). 조직·에이전트 일시정지 중에는 깨우지 않고 재개 뒤 예정이 지나 있으면 한 번 깨우며, 최종 완료·중단 조직에서는 설정도 바꿀 수 없습니다. 가짜 실행기는 heartbeat로만 깨어나면 맥락만 읽고 답장하지 않습니다.

에이전트는 조직 도구 `write_memory`·`recall_memory`로 조직 기억(같은 조직 에이전트가 함께 회수)과 에이전트 기억(쓴 에이전트만 회수)을 쓰고 꺼냅니다. 범위의 조직·에이전트와 출처(쓴 에이전트·실행 시도)는 실행 시도별 토큰에서만 정하며 입력에는 조직을 고르는 값이 없으므로, 다른 조직이나 같은 조직의 다른 에이전트 기억은 회수되지 않습니다. 첫 판 Memory port는 기법 없이 저장과 회수만 합니다. 회수는 최근에 쓴 것부터 최대 50개이며, 검색어는 대소문자를 가리지 않는 글자 그대로의 부분 문자열입니다(`%`·`_`도 그 글자). 기억을 쓰면 내용 없이 `memory.written` Event가 남습니다. 기억을 보는 대시보드 화면·명시적 공유·기억 기법은 기억 이슈에서 정합니다.

서버가 실행 시도 도중 멈추면 그 실행 시도는 `서버 재시작`으로 끝나고 받은 깨우기는 다시 대기해 새 실행 시도·새 토큰으로 전달됩니다. 정상 종료는 실행기를 취소한 뒤 바로 그렇게 저장하고, 프로세스가 죽었으면 다음 시작 때 실행기를 부르기 전에 실행 시도마다 종료·깨우기 복원·Event를 한 transaction으로 저장합니다. 끝난 실행 시도의 상세는 받았던 깨우기를 그대로 보여 줍니다. 사용자 제어로 이미 취소를 요청받은 실행 시도는 그 취소대로 `취소됨`으로 끝나고 입력을 다시 보내지 않습니다. 다시 받은 실행 시도가 이미 남긴 답장·작업·기억 등을 되풀이하지 않도록 모든 쓰기 조직 도구는 `Idempotency-Key` header를 받습니다. 키와 처음 결과는 효과와 같은 transaction에 남고, 그 에이전트의 같은 키는 처음 결과를 다시 돌려주며 기록·Event·깨우기를 새로 남기지 않습니다. 같은 키로 다른 도구나 다른 입력을 보내면 409 `idempotency_conflict`이고, 키와 결과는 지우지 않습니다. Role·단계 규칙은 같은 키여도 먼저 검사합니다. 가짜 실행기는 받은 깨우기 묶음과 도구별 쓰기 순서로 키를 정하므로 새 깨우기가 섞여 다시 받으면 새 효과가 됩니다. 목표 기록·초기 연구 승인 요청·결과 제출처럼 단계를 바꾸는 쓰기 뒤에 멈췄으면, 가짜 Lead는 다시 받은 깨우기와 저장된 단계·목표로 이미 한 쓰기를 알아보고 건너뛰어 그 흐름의 남은 단계부터 이어 갑니다. 다시 대기한 깨우기에 다른 목표 메시지가 합쳐져도 기록한 목표의 흐름을 이어 가고, 다른 목표는 반영하지 않았다고 답장에 밝힙니다. 조직 도구 밖의 외부 효과는 막지 않으며, 실제 실행기가 키를 정하는 방식은 실제 adapter 판에서 정합니다.

실행 시도 admission·종료 저장의 DB 오류는 100ms부터 최대 5초 간격의 backoff로 서버 종료까지 재시도합니다. 종료 결과 저장이 실패하면 같은 결과를 보관해 다시 저장하며 실행기를 다시 호출하지 않습니다. 서버 종료는 backoff 대기를 취소합니다. 종료까지 DB 장애가 이어지거나 프로세스가 죽으면 메모리의 종료 결과는 보존되지 않으며, 다음 시작 때 남은 실행 시도는 위처럼 `서버 재시작`으로 끝나고 입력을 다시 처리합니다.

## 개발 시작

Node.js 24.x, pnpm 10.33.0 및 Git을 사용합니다. GitHub 이슈 작업에는 인증된 `gh`가 필요합니다.

```bash
pnpm install
pnpm dev          # 서버(http://127.0.0.1:3100)와 대시보드(http://127.0.0.1:5173)
pnpm test         # 패키지별 Vitest. 서버·DB 테스트는 임시 embedded Postgres를 띄웁니다.
pnpm test:e2e     # Playwright smoke(대시보드는 프로덕션 빌드로 띄움). 처음 한 번 `pnpm --filter @babojubot/web exec playwright install chromium`
pnpm typecheck
pnpm lint
pnpm check        # Markdown 로컬 링크 검사
```

`pnpm install`은 `@embedded-postgres/linux-x64`의 postinstall만 실행합니다(`pnpm-workspace.yaml`의 `onlyBuiltDependencies`). 이 script가 Postgres native library의 symlink를 만들기 때문에 `--ignore-scripts`로 설치하면 embedded Postgres가 뜨지 않습니다. 다른 OS·아키텍처에서는 해당 `@embedded-postgres/*` 패키지를 같은 목록에 추가합니다.

[CI](.github/workflows/scaffold.yml)는 `main` 대상 PR의 생성·갱신·재개와 `main` push에서 문서 검사·타입·lint·테스트·빌드·E2E를 실행합니다. 바뀐 파일이 Markdown뿐이면 문서 검사만 돌리고 나머지 검사는 건너뛴 채 성공으로 표시합니다.
기능 브랜치 push만으로는 중복 실행하지 않고, 같은 PR의 오래된 실행은 취소합니다.
`main`의 필수 검사는 workflow의 `ci / …` job 전체이며, 실행 환경과 검사 이름은 workflow를 기준으로 합니다.
표준 GitHub-hosted runner를 쓰는 공개 저장소의 실행 시간은 무료입니다([GitHub 과금 문서](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
실패한 E2E의 trace 등 결과물만 3일 보관하며 artifact·cache 저장 공간 한도는 별도로 관리합니다.

데이터베이스는 `DATABASE_URL`이 있으면 그 외부 Postgres에 연결만 하고, 없으면 embedded Postgres를 `.babojubot/postgres`(`BABOJUBOT_HOME`으로 변경)에 띄웁니다. 둘 다 시작할 때 같은 migration을 적용합니다. 운영은 `pnpm build` 후 `DATABASE_URL=… pnpm start`로 서버가 빌드한 대시보드까지 제공합니다. 그 밖의 설정(`PORT`, `HOST`, `EMBEDDED_POSTGRES_PORT`)은 [`apps/server/src/main.ts`](apps/server/src/main.ts) 머리에 있습니다. 스택은 [ADR-0004](docs/adr/0004-paperclip-aligned-stack.md)를 따릅니다.

패키지별 책임은 [전체 구조](docs/architecture.md#패키지-구성), 수정할 코드와 테스트의 위치는 [코드 지도](docs/agents/code-map.md)에서 확인합니다.

## 검증 기준

| 변경 | 완료 시 확인할 검사 |
| --- | --- |
| 모든 변경 | `git diff --check`, `pnpm check`. 문서만 바뀌면 로컬 기본 검사로 충분 |
| 제품 코드 | `pnpm test`, `pnpm typecheck`, `pnpm lint`와 변경 계약의 시나리오 |
| 빌드·실행 환경 | `pnpm build`와 관련 실행 확인 |
| 브라우저 동작 | 관련 E2E와 실제 화면·조작 확인 |

- 여러 행에 해당하면 합쳐 적용합니다. 조직 상태·승인·조직 분리 계약 변경은 해당 핵심 시나리오를 검증합니다.
- 검사마다 SHA·명령 또는 CI run·결과를 기록하고 실패 출력·종료 코드도 보존합니다. 미실행 환경·시나리오는 구분하고 PR이 있으면 본문에 모읍니다.
- 같은 코드의 검증은 재사용할 수 있습니다. 이전 SHA를 근거로 쓰면 이후 diff와 적용 이유를 남기고, 변경·실패·환경 차이에 맞춰 재검사합니다. 실패는 원인을 확인해 해소합니다.
- 로컬 검사 선택과 별개로 PR·main의 CI는 위에 설명한 검사를 실행합니다. 병합 판단은 [병합 절차](docs/agents/pr-merge.md)를 따릅니다.

## 문서

[문서 지도](docs/README.md)에서 기능·구조·용어·개발 운영·인터뷰·조사 문서를 질문별로 찾습니다.

실제 실행 인스턴스의 파일·기억·실험 결과는 Git에서 제외하는 `.babojubot/` 아래 또는 설정된 외부 저장소에 둡니다. 최종 저장 방식은 후속 이슈에서 결정합니다.

상위 프로젝트의 구조를 참고해 독립적으로 작성합니다. 코드 재사용 시 해당 버전·파일·의존성의 라이선스를 확인합니다. BaboJUBot 자체의 배포 라이선스는 아직 선택하지 않았습니다.
